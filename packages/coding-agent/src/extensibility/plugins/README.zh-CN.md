# plugins/ —— 这个目录怎么组织

一个平铺目录里曾放着 51 个模块，没有任何可见分组：挂载管线挨着市场安装器，
再挨着一种外部补丁格式的解析器。下面的分组按**模块负责什么**划分，新增模块的
规则是：放进「它的职责变了就得跟着改」的那个组。

| 目录 | 职责 |
|---|---|
| `runtime/` | 装载与挂载一个插件：入口形态、插件拿到的 cordis 原语、挂载管线、会话级加载器、插件类型词表。 |
| `hmr/` | 判断已装载插件的源码在磁盘上变了（单一实现，两条插件轨道共用）。 |
| `management/` | 安装、列出、启停、卸载与诊断插件：安装器、包管理器、市场自动更新、安装状态机、构建批准、doctor 与能力报告。 |
| `profile/` | 用层组合出 profile：profile 组合、补丁编辑、运行时配置锁、清单区块、注册表配置与回退。 |
| `dsh/` | **DSH 文件格式契约**：读 `cordis.patch.yml`、折叠其层栈、`!!js` 表达式处理、bundle 声明、名字解析。 |
| `compat/` | 旧版 Pi 扩展兼容层：模块装载 shim、虚拟模块声明、插件兼容门与其豁免存储。 |
| `shared/` | 没有插件特定含义的模块：特性括号说明符解析器、git URL 解析、git 包缓存、独占挂载声明。 |
| `marketplace/` | 市场目录：抓取、缓存、注册表与条目列举。 |

`index.ts` 是 barrel，重新导出公开面。

## 关于 `dsh/` 这个命名

这些模块**不是从 DSH 拷来的源码**。它们读并翻译 DSH 的磁盘格式——补丁文件、
bundle 清单、包名——`dsh-` 前缀是为了让名字说明它处理的是哪种外部格式。只是
恰好被一起归进来、但本身没有 DSH 含义的模块属于 `shared/`，说明符解析器和 git
辅助函数因此被移了出去。

这些模块带着它们所对齐的 DSH 源码的行号引用
（`deepseek-harness/packages/boot/app-boot/src/profile-context.ts:63-74` 等）。
那些引用是维护契约：DSH 改了格式时，靠引用找到改动点。它们不是实现的副本，
这里没有任何东西是从 DSH 生成的。
