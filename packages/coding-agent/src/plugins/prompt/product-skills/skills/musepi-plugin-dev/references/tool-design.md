# 工具设计：面向模型的那一面

工具是模型唯一能看见的接口。描述、参数和结果一起构成契约。

## 描述写什么

- **一句话说清它做什么**，不重复工具名。
- **说清前置条件与代价**：需要什么状态、会不会执行宿主代码、是否要用户同意。
- **说清返回什么**：列表还是单条、是否分页、哪些字段是下一步要用的。
- **第三方文本要标注**：市场标题、插件描述这类内容不是指令，写进描述里，模型才不会照着别人的文案行动。

不写：实现细节、内部类名、为什么这样设计。

## 参数

- 必填项越少越好；能用默认值的地方给默认值。
- 分页参数写明范围与默认值（`offset` 从 0 起、`limit` 1 到 100，默认 25）。
- 枚举的每个取值在 `describe` 里说清后果，而不是只说名字。

## 结果

- 结构化字段优于拼装字符串：模型要能取其中一项继续下一步。例如市场版本带 `install: { target, registry? }`，下一步直接交给 `install_bundle`。
- 失败返回可行动的说明，而不是一句「失败」。目标不可达时给出下一步。
- 分页结果带 `total` 与 `nextOffset`（末页为 `null`），模型才知道要不要继续翻。

## 危险动作

会执行宿主代码、写盘、或放行风险的动作，要与只读动作分开：

- 只读的浏览单独成工具，任何会话都能用；
- 有副作用的动作要求自动批准的会话，否则返回「让用户去做」，并说明去哪里做。

## 命名

- 工具名用 `snake_case`，动词在前或按域前缀（`cordis_define`、`plugin_manager`、`plugin_market`）。
- 同一族的工具共享前缀，模型才能从名字判断它们相关。
