# ADR: Live dictation in the composer

- Status: accepted

## English

## 13. Live dictation lands in the composer

- **The volatile preview is painted where the words will land.** `use-dictation` hands each `partial` to the editor (`ComposerEditorHandle.setPreview`), and the editor paints it at the caret as a `previewField` widget — muted, wrapping, `ignoreEvent()` so it never steals the caret. The document is untouched: `value`, `onChange`, the draft store, the undo history and the send path never see a guess. This is the GUI form of the TUI editor's `setVolatileText`, and it is deliberately a *display* channel rather than an edit: a preview is replaced on every decode, so committing it would leak half a sentence into whatever the user sends next.
- **The status strip no longer repeats the transcript.** `VoiceStatusStrip` keeps the phase, the clock, the level meter and the Esc hint; the words live in the input. One fact, one place — the strip used to echo the same text a few pixels above the editor.
- **Two channels, named in the worker protocol.** `stream_utterance` means "the caller already delimited this run" and is decoded once into a committed segment; `stream_preview` means "this is the still-growing run" and yields a volatile `partial`. Previews coalesce, so a newer one replaces an undecoded older one, and a finalized segment supersedes any preview of the same run.
- **Why text used to appear only after stopping.** The voice frontend ran its own energy endpointer and then fed each delimited run into `sttClient.startStream`, whose worker ran a *second* endpointer over that same audio. A run arrives with no trailing silence, so the inner endpointer never committed it and everything waited for `stream_stop`. Ungated sessions now skip the frontend endpointer entirely: raw frames go to the worker, whose own segmentation commits each run as the speaker pauses. Gated sessions (speaker verification or enhancement, which can only judge a finalized run) keep the frontend endpointer and send its runs as `stream_utterance`, with the growing run as `stream_preview`.
- **The first preview was dropped too.** `onPartial` used to require a current frontend result, and that result only existed after the first commit — so nothing could be shown until one full sentence had already landed. A preview now carries the id its commit will take and is emitted before any segment exists.
- **The preview borrows the transcript's own entrance effect.** Newly recognized characters enter through `advanceTail` with `TAIL_RENDERERS`'s preset (the 逐字动效 setting), so dictation and a streaming reply share one motion language instead of two near-identical animations. `advanceTail` is append-only and remembers what the container holds, which is only sound on a STABLE element — CodeMirror reuses the element across widget instances, so the widget adopts the element's actual content before advancing; treating a reused element as empty appended the new guess onto the old one (`hellohel`).
- **The placeholder yields to the preview.** The hint was drawn whenever `value` was empty, and a preview never writes to the document — so an empty composer with live dictation painted the hint and the transcript into the same box. The condition is now "empty AND no preview", and a real document edit makes the hint eligible again (a retired preview must not leave an empty box with no hint).
- **One fact per element: the strip states the act, the button only shows state.** The dictation strip had grown into a status bar restating what was already on screen — a second pulsing mic orb with two RMS rings beside a 13-bar RMS wave (the same level drawn twice, 40px apart) — plus "recognized text will appear here", which stopped being true the moment the transcript started landing at the caret. It is now one tinted band, the shape KiroCrew uses: live dot, phase word, elapsed clock and ONE level meter, with Esc-cancel opposite. Transcribing keeps the band (the request is in flight, Esc still cancels) but drops the clock and the meter, because a moving meter over a finished capture claims something untrue.
- **The mic button carries state, never a loop.** The glyph had `gui-mic-pulse` — an endless 1s opacity breath — sitting beside a meter that was already moving, which read as a control stuck in animation. It is a plain icon now: tinted while recording, a spinner while transcribing, no loop. An intermediate pass moved the clock and meter INTO the button as an expanding capsule; that was tried in `fe275c7f7`, reverted by direction ("a 30px capsule is a motion budget, not a copy budget", §5n), and re-introduced by mistake here — the reference clients agree with the original call: KiroCrew keeps a plain icon while its strip carries the meter, and OpenMausBot's mic has no counters at all.
- **Text and background are a pair, not one token.** The band's ink is the danger colour mixed toward body text, and the meter's fill is the pure danger colour: the raw token is tuned for small red text on a neutral surface, so using it for both left the light theme's grey card washed out and sank the meter's moving part into its own track.
- **The band shares the editor's left axis.** The strip carried `margin: 0 2px; padding: 0 4px` while the editor's text column sits at the frame's 10px plus `.cm-content`'s 2px, so the dot started 2px right of the sentence beneath it. Both now resolve to the same x.
- **Dictating retires the input hint entirely.** The "what you could type" placeholder competed with the instruction that matters at that moment (speak); the composers now pass no placeholder away from idle. This also closes the window the preview-based rule left open: between pressing the mic and the first recognized word there is no preview yet, and the hint used to reappear there.
- **Dictation writes ONE region, and writes only its delta.** Each hypothesis and each committed segment describes the same spot, so the region is frozen once (the document and caret before dictation) and re-derived from that snapshot with `dictationSplice` — the equivalent of KiroCrew's `spliceDictationText`, `before + lead + dictated + trailing + after`, separators added only against a side that has words. Two earlier shapes were wrong and both are covered by tests now: appending commits to the end of the draft while painting the hypothesis at the caret (a continuous utterance scattered its own words, and a phrase could land inside other content), and replacing the whole document on every update (CodeMirror rebuilt everything, so the per-character entrance effect replayed the entire draft instead of animating the new glyphs). The write now replaces `[from, to)` of the dictated block only — measured: six new characters, six characters inserted. Cancelling restores the frozen document verbatim rather than deleting the range, because the write may own a separating space on either side (`before after` collapsing to `beforeafter` is the same bug KiroCrew documents).
- **A dictation write is verified before it is dispatched, and the region never outlives its dictation.** Two failures came from the same missing guard. A frozen region offset was handed straight to CodeMirror after the document had been replaced wholesale (an in-flight hypothesis, then the user selects everything and types over it), so the editor threw `Invalid change range 4 to 9 (in doc of length 5)` — out of a `dispatch`, which takes the whole render tree down, not just the composer. Every write now checks the range still fits the live document and DROPS the write when it does not: guessing where the words belonged is how a draft gets corrupted, while leaving it alone only costs that hypothesis. `setSelectionRange` and `replaceRange` clamp for the same reason. Second failure: the ending only wrote when nothing had been committed yet, and nothing retired the decorated range — so after a few start/stop cycles the last phrase stayed painted as a guess forever ("stopped, but it still looks like a preview") and re-armed as a splice target for the next cycle. `commitDictation()` now retires the region on every outcome that keeps the words. The recognizer finalizes each sentence from raw audio and returns their joined text, so it replaces the region outright instead of being merged with streamed previews.

- **Global dictation has two presentations, not two competing panels.** Inside MusePi the global accelerator drives the focused composer and keeps its existing state strip, mic state, and in-place preview without opening the HUD. Outside it shows only the compact non-focusable HUD: finalized text plus the active partial wraps to at most three lines, with one cancel action. The trigger setting offers Press twice and Hold to talk; the latter is Windows-only and releases on either the main key or a required modifier.

## 中文

## 13. 流式听写直接落在输入框里

- **可变预览画在字要去的地方。** `use-dictation` 把每次 `partial` 交给编辑器（`ComposerEditorHandle.setPreview`），编辑器以 `previewField` widget 画在光标处——弱化颜色、可换行、`ignoreEvent()` 不抢光标。文档一个字都不动：`value`、`onChange`、草稿存储、撤销栈与发送路径都看不到猜测文本。这是 TUI 编辑器 `setVolatileText` 的 GUI 形态，而且刻意做成**显示通道**而非编辑：预览每次解码都会被替换，若写进文档，半句话就会漏进用户下一次发送的内容里。
- **状态条不再复述转写文本。** `VoiceStatusStrip` 只留阶段、计时、音量条与 Esc 提示；文字在输入框里。一个事实一处归属——此前状态条会把同一段文字重复显示在编辑器上方几像素处。
- **两条通道，在 worker 协议里各自命名。** `stream_utterance` 表示「调用方已切好这段」，只解码一次并落为定稿句；`stream_preview` 表示「这段还在生长」，产出易变 `partial`。预览是合并式的：新的替换尚未解码的旧的，而定稿句会顶掉同一段的任何预览。
- **为什么以前要等停止才出字。** 语音前端自己跑能量断句，再把每段已切好的音频交给 `sttClient.startStream`，而 worker 又对同一段音频跑了**第二次**断句。已切好的音频结尾没有静音，内层断句永远等不到定稿，全部积压到 `stream_stop`。现在未开闸门的会话跳过前端断句：原始帧直接交给 worker，由它自己的断句在说话人停顿时逐句落稿。开启闸门的会话（说话人校验或语音增强，只能对定稿音频判定）保留前端断句，把切好的段以 `stream_utterance` 送入，正在生长的那段走 `stream_preview`。
- **第一段预览也曾被丢掉。** 过去 `onPartial` 要求已存在当前前端结果，而该结果只有第一次落稿之后才有——所以在一句完整的话落稿之前什么都显示不出来。现在预览携带它将要占用的 id，并在任何定稿句出现之前就能发出。
- **预览借用消息流式渲染自己的入场动效。** 新识别出的字通过 `advanceTail` 按「逐字动效」设置入场，因此听写与流式回复共用同一套动效语汇，而不是两套几乎一样的动画。`advanceTail` 是增量式的，并且记住容器里已有什么，这只有在容器**稳定**时才成立——CodeMirror 会在 widget 实例之间复用同一个元素，所以 widget 先以元素实际内容为准再推进；把复用元素当成空容器，新猜测就会追加到旧文本之后（`hellohel`）。
- **占位提示让位给预览。** 提示原先只在 `value` 为空时绘制，而预览从不写入文档——于是空输入框叠上实时听写时，提示与转写文字被画进了同一个盒子。现在条件是「为空且无预览」，而真正的文档编辑会让提示重新可用（已撤销的预览不能留下一个没有提示的空输入框）。
- **一个事实一个元素：状态条说明"正在做什么"，按钮只表达状态。** 听写状态条此前长成了一条重复播报的状态栏——第二个脉冲麦克风光球配两层随音量缩放的环，旁边还有 13 根同样随音量缩放的声波（同一份电平在 40px 内画了两遍），再加上「识别文字会显示在这里」——而这句话在文字真的落到光标处那一刻就不成立了。现在它是一条带色横条，形态与 KiroCrew 一致：活动圆点、阶段词、已用时间与**一个**电平条，右端是 Esc 取消。转写时保留横条（请求仍在飞、Esc 仍可取消），但撤掉计时与电平——采集已经结束，还在动的电平条等于撒谎。
- **麦克风按钮只承载状态，不做循环动画。** 图标上原挂着 `gui-mic-pulse`（1 秒无限明暗呼吸），旁边又是一条本来就在跳动的电平条，读起来像控件卡在动画里。现在它是普通图标：录音时变红、转写时换成转圈，不再循环。中间有一版把计时与电平塞进按钮做成展开胶囊——那是 `fe275c7f7` 试过、已按方向推翻的方案（§5n「30px 胶囊是动作预算，不是文案预算」），这次被我错误地加了回来；参考实现也支持最初的判断：KiroCrew 保持普通图标、把电平放在状态条里，OpenMausBot 的麦克风则完全没有计数。
- **文字与底色是一对，不是同一个 token。** 横条的墨水色是把 danger 朝正文色混合的结果，电平条的填充用纯 danger：原始 token 是为中性底上的小红字调的，两者共用一个色值会让亮色主题的灰卡片发闷，并让电平的跳动部分沉进自己的轨道。
- **这条横条与编辑器共用左轴。** 状态条带着 `margin: 0 2px; padding: 0 4px`，而编辑器文本列在 frame 的 10px 加 `.cm-content` 的 2px 处，于是圆点比下面那句话右移了 2px。现在两者落在同一个 x 上。
- **听写期间整体撤掉输入提示。** 「你可以输入什么」这类占位提示与该时刻真正要说的（请说话）互相竞争，所以两个 composer 在非 idle 时不再传占位符。这也补上了按预览判断那条规则留下的窗口：按下麦克风到识别出第一个字之间还没有预览，提示原本会在这段重新露出来。
- **听写只写一个区间，且只写差量。** 每个假设与每个落稿段描述的是同一处位置，所以区间只冻结一次（听写开始前的文档与光标），再用 `dictationSplice` 从该快照重算——等价于 KiroCrew 的 `spliceDictationText`：`before + 分隔 + 口述 + 分隔 + after`，只在有词的一侧补空格。此前两种形态都是错的，现在都有测试覆盖：落稿追加到草稿末尾而假设画在光标处（连续说话时自己的词被打散，甚至插进别人的文本中间），以及每次更新都整篇替换文档（CodeMirror 重建全部内容，导致逐字入场动效重放整段草稿而不是只演新字）。现在只替换听写块所在的 `[from, to)`——实测新增 6 个字符就只插入 6 个字符。取消时按冻结原文整体恢复而非删除区间，因为写入可能拥有两侧的分隔空格（`before after` 退化成 `beforeafter`，正是 KiroCrew 注释里记录的同一个坑）。
- **写入前先校验，且区间绝不比这次听存活得更久。** 两个故障出自同一个缺失的守卫。冻结的区间偏移被直接交给 CodeMirror，而文档此前被整段替换过（一个还在飞的假设，接着用户全选并覆盖输入），于是编辑器抛出 `Invalid change range 4 to 9 (in doc of length 5)`——它从 `dispatch` 里抛出，会带走整棵渲染树，不只是输入框。现在每次写入都先确认区间仍落在当前文档内，不符就**放弃这次写入**：猜位置会毁掉草稿，不动只是丢掉这一个假设。`setSelectionRange` 与 `replaceRange` 出于同样原因做边界钳制。第二个故障：结束流程只在尚未落稿时写入，且没有任何地方撤销装饰区间——几次启停之后，最后一句永远保持猜测态（停止后仍像预览），还会被下一轮当成改写目标。现在 `commitDictation()` 在每次保留文字的结局里撤销区间。识别器从原始音频逐句定稿并返回各句连接后的文本，因此直接整体替换该区间，而不与流式预览合并。

- **全局听写有两个呈现位置，而不是两个互相竞争的面板。** 在 MusePi 内，全局快捷键驱动当前输入框，沿用现有状态条、麦克风状态与就地预览，不再打开 HUD；在软件外只显示不抢焦点的紧凑 HUD，各句定稿与当前预览最多换行三行，并保留一个取消动作。触发设置提供「按两次」与「按住说话」，后者仅支持 Windows，松开主键或任一必需修饰键都会结束。
