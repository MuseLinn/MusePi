# MusePi i18n Architecture

English | [中文](i18n.zh-CN.md)

> **Living document** (established 2026-08-16) — covers the two independent i18n systems in this repo: the **renderer side** (guest-client, GUI/tray/collab Web) and the **TUI** (coding-agent). The vocabulary was split into per-domain modules on 2026-08-16, with compile-level parity on the en side and a plugin registration seam. The implementation is authoritative.

## The Two Systems

| | guest-client (`packages/client-core/src/i18n`) | coding-agent (`packages/coding-agent/src/i18n`) |
|---|---|---|
| Consumers | GUI main window/tray/bubble, collab Web UI | TUI, daemon (reuses the same module) |
| Placeholders | **Named parameters** `{count}` (validated via template literal type extraction) | **Positional parameters** `{0}` (legacy convention, not migrated) |
| Key typing | Strict `TranslationKey = keyof typeof zhCN` (typos/missing params are compile errors) | Loose (`key: string`); migrated feature namespaces carry a zh key set and en parity |
| en mapping | Yes (`en-US/` domain files, compile-level parity) | Feature namespace modules have en parity; the legacy dictionary is still English passthrough |
| Vocabulary | 12 domains + feature namespaces (`zh-CN/` + `en-US/`) | 13 domains + feature namespaces (`zh-CN/` + `en-US/`) |
| Plugin seam | `registerTranslations(locale, map)` + `tLoose(key, params)` | `registerTranslations(locale, map)` |

Shared conventions: un-migrated copy uses the English source text as the key; a migrated feature owns a feature namespace module whose zh dictionary defines the key set and whose en dictionary is checked against it. `t()` falls back to the key itself on a miss and runs only at render/call time, never at module load.

## Vocabulary Split (guest-client)

- Domain modules: `zh-CN/{shell,composer,sessions,context,collab,transcript,settings,agents,tools,pet,guest}.ts` (each domain exports `XxxKey = keyof typeof x`), with an isomorphic `en-US/` tree.
- Barrels (`zh-CN/index.ts` / `en-US/index.ts`) merge everything into flat maps and **throw at module load on cross-domain duplicate keys** (a replacement for silent spread overrides); the TUI's `zh-CN/index.ts` has the same guard.
- **en compile-level parity**: each en domain file uses `export const x = { … } as const satisfies Record<ZhKey, string>` — a missing or extra en key is a compile error (negative verification: injecting an extra key into shell.ts → TS2353). Stronger than tests; every new zh key must be accompanied by en.
- Tests: `guest-client/src/i18n/i18n.test.ts` (key-set parity, cross-domain duplicate guard, registration override/isolation, new locales) + `guest-client/test/i18n.test.ts` (lookup/replacement/fallback/passthrough/no leftover positional parameters). Tests calling `setLocale` must restore the initial value in `afterAll` (bun test runs files sequentially in one process).

### Feature namespaces (dsh organisation)

Touched features move their copy out of the flat domain file into a feature namespace module, matching dsh's `locale/settings.ts` shape:

- `zh-CN/settings-compaction.ts` exports the dictionary and `SettingsCompactionKey = keyof typeof …`; it is the key-set source of truth.
- `en-US/settings-compaction.ts` is `satisfies Record<SettingsCompactionKey, string>`, so a missing or extra en key is a compile error.
- Both barrels spread the module into the flat map `t()` resolves, and the module-load duplicate guard covers it.
- Keys are stable semantic paths (`settings.compaction.threshold.title`, `.desc`, `.option.default`), never English sentences.
- Schema-driven settings put those keys directly in `ui.label`, `ui.description`, `ui.group` and option copy; GUI and TUI both resolve them through `t()`. Un-migrated rows keep the English source text until their feature is touched.
- `verify-schema-labels-i18n.ts` accepts both forms because it checks the string against both zh dictionaries.

Migration rule: when a setting is edited, move its copy to the owning feature namespace and do not add new English source-text keys. The compaction settings are the reference migration.

## Plugin Seam

- `registerTranslations(locale, map)`: registers/overrides copy for a locale at runtime. The guest-client version triggers `emit()` so the UI re-renders immediately; the TUI version has no subscribers — `t()` reads the registry on every call, so it is naturally immediate. Neither persists (restarts revert to the core vocabulary).
- `tLoose(key, params)` (guest-client only): for plugin-owned keys not in the core vocabulary (core `t` only accepts `TranslationKey`; the TUI's `t` never restricted keys in the first place).
- Brand-new locales are supported (e.g. a plugin registering `fr-FR`); unregistered keys for that locale fall back to the raw key text.

### Plugin display text (manifest, not a key)

A plugin's own **name and description** are not UI keys: they are package data, so they travel as a `LocalizedPluginText` map (`{ en, [locale] }`) that each reader resolves for its own language — the GUI through `extensionDisplayName()` (`apps/desktop/src/lib/slot-host.tsx`), the TUI through `getLocale()` in `extension-list.ts` / `inspector-panel.ts`.

- The package ships `locale/<tag>.json` next to its `package.json`: `{ "meta": { "title": "…", "description": "…" } }`. The file name **is** the language tag (`zh-CN.json`, `ja.json`).
- `musepi.label` / `musepi.description` stay as the `en` fallback (dsh's `package.json` `name` role): a package with no locale files keeps today's single string, so adopting this is incremental.
- The daemon never picks a language — it ships the map (`displayNameI18n` / `descriptionI18n`) and one snapshot serves a zh-CN TUI and an en-US GUI at once.
- Resolution order: exact tag → language subtag → `en` → the caller's fallback. Matching is case-insensitive (file names keep the author's casing); see `resolveLocalizedText()` in `packages/wire/src/plugin-config.ts`.

### What `ctx.setLabel` is (and why it is not translated)

Three names exist for a plugin, each with one job:

| Name | Home | Readers | Language |
| --- | --- | --- | --- |
| `musepi.label` | package manifest | extension inventory the **model** sees (`prompts/system/extensions-inventory.md`, order 25), legacy `plugins.list`, and the `en` fallback | one, English |
| `locale/<tag>.json` | package directory | every **interface**: extension center, capability-center diagnostics, session card plugin list, TUI list and detail | per interface locale |
| `ctx.setLabel(...)` | runtime call | overrides the manifest label for a plugin that picks its name while loading | one |

`setLabel` is not UI copy. Its consumer is a prompt section composed once per session, so a name that followed the interface language would rewrite the prompt when a display toggle changes and invalidate prompt caching — and the same session can be watched by a zh-CN TUI and an en-US GUI at the same time. First-party plugins therefore declare the name once, in the manifest; the loader seeds `Extension.label` from it (`readExtensionPluginLabel` in `plugin-manifest.ts`), and `test/extension-label.test.ts` fails if a bundled plugin adds a second declaration.

## Maintenance Guide

1. **Editing copy**: find the domain or feature namespace matching the feature area (settings is largest at 2137 keys, then tools/pet); do not merge back into a single file.
2. **Adding a key**: migrated features add it to their feature namespace (`zh` first, `en` in the same change); legacy rows add a zh domain key and sync the en domain. Keys in feature namespaces are semantic paths; legacy keys stay English source text. Use named parameters like `{name}`, not `{0}`.
3. **No duplicate keys across domains**: duplicates throw when the barrel loads (the error names both domains).
4. **GUI dynamic keys** (schema-driven labels, runtime error strings, `tag.${…}` concatenation): use explicit `as TranslationKey`; plugin/extension copy goes through `registerTranslations` + `tLoose`.
5. **TUI**: leave `{0}` positional parameters untouched; when adding a new domain module, update the import/spread/guard parts of `zh-CN/index.ts` accordingly.
