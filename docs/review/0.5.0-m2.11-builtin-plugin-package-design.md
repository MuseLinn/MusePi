## 0. TL;DR

dsh 的插件化不只是「每个能力一个 cordis 插件」，还有**包组织层**：按部署形态切
bundle（base / headless / web-app / sdk-app / acp-app / sdk-minimal），每个
bundle 一份 `cordis.patch.yml` 以 `- insert:` 行把插件挂进 profile，行上带
`disabled: !!js "<条件表达式>"` 与 `config:`；包内再经子插件行（`- insert:` 嵌套）
组织可独立启停的组件。本文把这一层完整吸收：给出 MusePi 的 bundle 分层、内置
插件包清单（8 类内置 → N 个包）、组件组织、patch 落点与分批收编序。

## 1. dsh 插件包组织解剖（真码核实）

### 1.1 一 npm 包 = 一 cordis 插件

`packages/skill/tool-skill` 为范式：

- `package.json`：`main: lib/index.js`，peerDependencies 声明
  `@deepseek-ai/dsh-agent` / `dsh-llm` / `dsh-tools` / `cordis`（workspace 协议）。
- `src/index.ts` 四件套：`export const name`（注册表键 / 错误归因）、
  `export const inject = ['agents','tools','skills']`（服务依赖，cordis 解析）、
  `export const Config: z<Config>`（schemastery schema，default/min/max 校验）、
  `export function apply(ctx, config)`（装配入口，零 imperative 服务查找）。
- 声明合并：`declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap ... }`
  —— 插件给宿主接口增量声明，TS 层面把插件面织进宿主类型。

### 1.2 bundle 层 = 部署形态 × cordis.patch.yml

`packages/bundle/` 下六个 bundle，每个一份 `cordis.patch.yml`：

| bundle | 形态 | 内容取向 |
|---|---|---|
| `base` | 一切形态共享 | 95 插件行：llm/session/agent/skills/compaction/sandbox/settings/plugin-manager… |
| `headless` | 无 UI | base + 无客户端面 |
| `web-app` | 浏览器客户端 | client-ui-\* / client-modules / cordis-client-runner / api-\* controller |
| `sdk-app` / `sdk-minimal` | 嵌入式 | 面向 SDK 消费者的最小集 |
| `acp-app` | ACP 协议 | 面向 Zed 等外部客户端 |

patch 语义（`base/cordis.patch.yml` 头注释原文要点）：

- 每个 patch 以**一个 `- insert:` 块**覆盖目标行的**整个 config**（不 merge）——
  值随形态不同的行不下放 base，由各自 mode bundle 完整重述，单行最多
  「一层 bundle + 用户层」两个作者。
- 行序无加载语义（激活由服务可用性驱动），分组只为读者。
- `disabled: !!js "!ctx.get('profileContext')"` —— 禁用条件是**表达式**，
  随 ctx 求值，不是静态布尔。
- 子插件（组件）：bundle 插件的 patch 行里再嵌 `- insert:` 子行，每子行
  独立 npm 包、独立 loader entry、独立 fiber、独立 config —— 可单独启停、
  单独 reload（此前已核实并与我们 components 机制对齐，见 §3）。

### 1.3 客户端也是 cordis

`web-app` bundle 里 `dsh-cordis-client-runner` / `dsh-client-modules` /
`dsh-client-ui-*` 同走 cordis fiber —— 宿主与客户端一套插件语法，UI 插件的
注册面（settings.section / rail 项 / 渲染器）就是 cordis effect。

## 2. MusePi 现状对照

- 已有（不重复造）：三件套契约、trust 分级、回退保护三件套、组件子 fiber、
  兼容性预检、管理页五段式 —— 均见 M2 设计稿与收编进度表（第一/第二/组件对齐/
  回退保护②刀已落地）。
- `builtin-registry.ts` 登记 8 类内置（style/shell、skills、magic-keyword、
  theme、tool-render、voice、terminal、browser/computer/lsp），但它们是
  **注册表行**，不是**插件包**——没有包边界、没有 bundle 分层、没有 patch 落点。
- 部署形态：桌面客户端（Electron GUI）+ TUI + headless daemon + SDK 嵌入，
  对应 dsh 的 web-app/headless/sdk 多形态问题同构——bundle 分层对我们是
  真需求，不是过度设计。

## 3. 目标形态：MusePi bundle 分层 + 插件包清单

### 3.1 bundle 分层（三个部署 bundle）

| bundle | 形态 | 对应 dsh |
|---|---|---|
| `musepi-base` | daemon 必备（TUI/headless/SDK 共有） | base + headless |
| `musepi-gui` | 桌面客户端（Electron 渲染进程面） | web-app |
| `musepi-tui` | TUI 专属面（仪表盘/announcement） | （dsh 无，我方特有） |

分层规则照抄 dsh：patch 整块覆盖 config；值随形态不同的行不下放 base；行序
无语义；用户 profile patch（`~/.musepi/profile/cordis.patch.yml`）是最后一层，
last write wins。

### 3.2 内置插件包清单（8 类内置 → 包）

| 包 id | 源内置 | bundle | 组件（components） | 收编序 |
|---|---|---|---|---|
| `musepi:shell-style` | 样式/桌面壳（settingsMirror） | gui | — | 已登记，包化随 gui bundle |
| `musepi:skills-bundled` | bundled skills 标注（6） | base | 每 skill 一组件（annotate-only，禁走自身行） | 已登记，包化 = 换皮 |
| `musepi:magic-keywords` | magic keywords（settingsMirror） | base | 每 keyword 一组件 | 已登记，包化 = 换皮 |
| `musepi:themes` | modes 主题包 | gui | 每主题一组件 | 已登记，包化 = 换皮 |
| `musepi:tool-render` | 卡片工具渲染（63 wire 名快照） | gui | 每渲染器一组件（big-ticket 项可单禁） | 已登记，包化 = 换皮 |
| `musepi:voice` | STT/TTS（settingsMirror） | gui | `stt` / `tts` 两组件（已落地独立启停） | ✅ 已是事实插件 |
| `musepi:terminal` | 终端 L2 服务 + provider | base | provider 三组件：`bun-pty` / `node-pty` / `auto` | 第三刀（设计稿 §2） |
| `musepi:browser` | 托管浏览器 | gui | `view` / `inspector` / `tabs` | 第四刀 |
| `musepi:computer` | 电脑控制（settingsMirror enabled） | base | — | 第四刀 |
| `musepi:lsp` | LSP 服务 | base | 每语言服务器一组件 | 第五刀 |

「已登记，包化 = 换皮」的五项：注册表行已有 settingsMirror/annotate 语义，收编
动作 = 给每行补三件套 manifest（name/inject/Config）并把 `disabledExtensions`/
设置键映射改写为 patch 行 disabled 表达式，行为不变、语法统一。

### 3.3 patch 行形态（我方 YAML 方言）

```yaml
# ~/.musepi/bundles/musepi-base.cordis.patch.yml（随包分发，只读）
- insert:
    - id: terminal
      name: '@musepi/plugin-terminal'
      config:
        provider: auto
        scrollbackBytes: 1048576
    - id: terminal/provider/bun-pty
      name: '@musepi/plugin-terminal-provider-bun-pty'   # 子插件 = 组件
      disabled: false
```

disabled 条件表达式（dsh `!!js` parity）我方用 **JMESPath 式安全求值子集**或
直接 TS 闭包序列化限制——落地时按 spike 的隔离约束选其一（遗留问题 §5.1）。

### 3.4 builtin-registry 与包的关系

注册表行**派生自**包清单（单一事实源 = 包的 manifest），不再两处手写：
`builtin-registry.ts` 退化为 `BUILTIN_PACKAGES.map(row)` 的投影 + 既有
settingsMirror 兼容读（老设置键 → patch config 迁移一次性 upgrade 脚本）。
契约测试守「注册表行集 == 包清单行集」。

## 4. 分批收编序（接收编进度表）

| 刀 | 内容 | 依赖 |
|---|---|---|
| 第三刀 | 终端 provider 收编（设计稿 §2）+ `musepi:terminal` 包落地 | 无 |
| 包化换皮刀 | 五项「已登记」内置补 manifest、注册表改投影 | 第三刀验证包语法 |
| 第四刀 | browser / computer 包化 | 包化换皮刀 |
| 第五刀 | lsp 包化 + components=语言服务器 | 第四刀 |

| 客户端 cordis 化 | gui 插件的 UI 注册面走 cordis effect（dsh client runner parity） | bundle 切层刀 |

## 5. 遗留问题

5.1 disabled 条件表达式的求值载体（!!js 等效物）与 spike 沙箱约束的相容性。
5.2 用户 profile patch 层的编辑面：手写 YAML 之外是否给 GUI 引导编辑器
（dsh 亦无 GUI 编辑器，先手写 + 文档示例）。
5.3 `musepi-tui` bundle 是否值得独立成层，还是 tui 专属行并入 base
（倾向并入：TUI 与 daemon 同进程，无独立部署形态）。
