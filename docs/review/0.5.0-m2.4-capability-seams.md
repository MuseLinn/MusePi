## 0. 方法与术语

- **能力域**：本稿的盘点单元——一类"可被 agent/插件/壳消费的内置能力"及其注册面。
- **接缝**：一个能力域对外的四件事——**输入**（谁以什么形状调进来）、**输出**（返回什么/广播什么）、**生命周期**（何时建立/销毁、可逆性）、**启停与冲突**（怎么关、重名怎么办）。M2-2.4 要求每个内置能力显式声明这四件事，供 agent 检视。
- 路径缩写（根 = `c:/Users/unive/projects/harness-engineering/musepi-omp`）：
  - `ca/` = `packages/coding-agent/src/`
  - `pa/` = `packages/agent/src/`
  - `cc/` = `packages/client-core/src/`
  - `cp/` = `packages/collab-proto/src/`
- 盘点口径：每域回答四问——**有没有声明？声明在哪（文件:行号）？声明了什么字段？缺口是什么？**

## 2. 各域详述

### 2.1 daemon L2 服务（RPC 面）——纪律已落地，作为模板

**现状**：P1 服务抽取（2026-09-25 收官）已建立本仓唯一的结构化缝声明：

- 接口契约：`ca/daemon/services/types.ts:13-27`——`DaemonService { key, routes?, start?, stop? }`；`routes` 字面量即本服务认领的 RPC 路由声明（输入面），`start/stop` 即生命周期。
- 头注释纪律：`types.ts:9-11` 明文「每个 DaemonService 实现的头注释必须声明自己的接缝——输入（RPC 路由/事件）、输出（返回值/广播）、生命周期（start/stop 的副作用与可逆性）」。实践样板：`schedule-service.ts:22-42`（输入七路由 + taskHandle 桥、输出落盘与广播、start/stop 可逆性、范围边界四段）。
- 强制机制已存在：`ca/daemon/services/route-coverage.test.ts:127-166` 路由覆盖快照测试——从 server.ts 源码抽取全部 `case`（:37-45），逐一断言被某服务 `routes` 认领或登记 `LEGACY_ROUTES`（`legacy-routes.ts:12-208`，195 条），两清单不相交（:135-139）；另钉 6 条 session tree 契约路由不许消失（:28-35）。**新增 RPC 不登记即 CI 红**。
- 注册表：`ca/daemon/services/registry.ts:14-53`——`HostServices` 聚合 `routeTable()`，重复认领抛错。

**缺口**：
1. 头注释纪律只覆盖三段（输入/输出/生命周期），**缺「启停语义」与「冲突处理」两段**（对比 §3 提案的六字段）。
2. 12 个服务中仅 2 个实现了 `start/stop`（ScheduleService `schedule-service.ts:88/95`、MarketplaceService stop `marketplace-service.ts:145`）——`stop?` 可选意味着"可逆性"声明常被省略。
3. 残留 195 条 legacy 路由在 server.ts:1109 巨型 switch 内联实现，无缝声明（深纠缠区：session.* 约 59、debug.* 12、memory.* 10 等）——P2 迁移时按服务逐域补齐即可，不构成本单工作。
4. RPC 契约无中央 schema：客户端全弱类型 `rpc<T>(method: string, params?: unknown)`（`cc/lib/client.ts:81`）——协议权威事实上由 routes + LEGACY_ROUTES + 快照测试三处字符串共同承载。这是已知架构现状（collab-proto 是纯传输层，`cp/index.ts:9-12`），本单不提案改协议。

## 3. 接缝声明格式提案

一个内置能力的接缝声明（**Capability Seam Statement**）建议含六字段，每字段一行可检视：

```markdown
<!-- seam: <名称> | ns: <命名空间前缀或"无"> | since: <版本> -->
- 输入：调用方以什么形状进来（RPC 路由 / 工具调用 / 事件 / 文件发现 / 插槽注册）
- 输出：返回什么、广播什么事件、落盘什么
- 生命周期：何时建立/销毁；可逆性（stop 是否完全回滚 start 的副作用）
- 启停：走哪条覆盖层通道——disabledExtensions / 专用 settings 键 / 常驻不可禁用（说明理由）
- 冲突：重名/撞键时覆盖、抛错还是跳过；命名空间如何隔离
- 检视入口：类型/注册表/权威清单的 文件:行号
```

**逐字段依据**：

1. **名称 + 命名空间前缀**：七域的前缀实践不统一——`mcp__<server>_<tool>`（工具域强制）、`hook:`/`skill:`（展示 id 约定）、`extension:<name>`（启停 id）、`panel.tab.`/`settings.item.`（插槽族）、`custom_message:<t>`（无前缀）。声明里显式写前缀，把"有前缀"从巧合变成契约。开放串空间（customType、entryKinds）必须标注"开放"并给建议前缀。
2. **输入/输出/生命周期**：沿用 L2 服务头注释三段（`services/types.ts:9-11` 已落地的措辞），让 daemon 域与其它域格式同构——这是本提案最重要的对齐点。
3. **启停语义**：对齐 M2-2.3 覆盖层结论（全部走 disabledExtensions/mcp.json denylist/镜像设置键等覆盖层，不动文件）。三档枚举：`overlay:disabledExtensions`（可禁用扩展）、`overlay:settings-key`（工具/命令的 `<x>.enabled` 键）、`always-on`（常驻不可禁，需写理由——如 transcript 内建渲染）。**新增能力默认走覆盖层，选 always-on 必须在声明里说明为什么**。
4. **冲突处理**：四档枚举（reject 拒绝 / overwrite 覆盖 / skip-warning 跳过告警 / host-wins 宿主优先），并要求写明选择理由。现状四域四种行为（§2.6），不要求改行为——**先声明现状，收敛与否另立决策**（§6 决策点 4）。
5. **检视入口**：机器可查的 文件:行号（类型定义 + 权威清单），这是"供 agent 检视"的关键——agent 读声明即可跳到注册表核对。

**示例**（以 ScheduleService 为例，把现有头注释改写成六字段）：

```markdown
<!-- seam: ScheduleService | ns: cron.* | since: 0.5.0-P1 -->
- 输入：RPC cron.list/upsert/runs/nextRuns/delete/toggle/runNow（7 条，schedule-service.ts:65）；会话创建时领走 schedule_task 工具桥
- 输出：RPC 返回值原样；crons.json / cron-runs.json 落盘；onCronsChanged 经 EventService 扇出
- 生命周期：start 加载任务+启动 30s 扫描器；stop 清扫描器（可逆）

- 冲突：任务 id 唯一，upsert 覆盖式更新（validateCronTask 拒非法 schedule）
- 检视入口：services/types.ts:13 / schedule-service.ts:22 / crons.ts
```

## 4. 声明载体提案（三方案）

| 方案 | 形态 | 利 | 弊 |
|---|---|---|---|
| **A. 代码内结构化注释**（推荐） | 每域权威注册表文件头部 + 每个 L2 服务文件头部写 §3 格式的结构化注释块；另在 `docs/review/`（或 docs/）留一份**索引页**列七域声明锚点 | ① 与代码同生命周期——改代码必经该文件，忘记同步的概率最低；② L2 服务域已实践（`types.ts:9-11` + 12 个服务头注释），零新机制；③ agent 检视即读代码，无需二次映射；④ 行号天然保真 | 行号会漂移（但"检视入口"指向的是文件与符号，非精确行锚，漂移可容忍）；索引页需人工同步（可在 checklist 里挂一条） |
| B. 独立 YAML（如 `docs/capability-seams.yaml`） | 结构化字段，可被脚本消费 | 机器可读性最好，未来可自动 diff/校验 | ① 与代码双写必漂移——无强制同步机制时 YAML 沦为第二事实源（M2-2.10 审计已证明注释与实现漂移的真实性）；② 需要新造解析/校验脚本，成本前置 |
| C. extensions-dev.md 附章 | 文档集中一章 | 对扩展作者可见性好 | ① 它是**扩展视角**文档，而接缝声明的读者首先是**仓内开发与 agent**；② 内置能力大多与扩展无关（bash 工具、cron 服务不需要扩展作者知道）；③ 文档与代码双写漂移问题同 B |

**推荐 A，兼收 C**：代码注释为权威事实源；`extensions-dev.md` 加一小节指到各域锚点（不复制内容，只给索引），扩展作者与仓内开发者各取所需。B 的 YAML 化留作远期——若未来 CI 需要机器消费（决策点 3 的升级路径），届时可从注释块用脚本提取升格，而非现在双写。

## 5. 强制机制提案

### 5.1 现有基础

L2 服务域已有 CI 强制（route-coverage 快照测试，`route-coverage.test.ts:127-166`）+ 头注释约定（`types.ts:9-11`，无 CI 检查，靠评审）。本提案把这一模式推广为「**轻 checklist 全域覆盖 + CI 只守已机器可守的点**」。

### 5.2 方案对比

| 方案 | 内容 | 利 | 弊 |
|---|---|---|---|
| **评审 checklist 轻量版**（推荐，立即做） | AGENTS.md「Code Quality」节加一条：*新增内置能力（新 L2 服务/新 BUILTIN_TOOLS 条目/新斜杠命令域/新 register* 方法/新 widget/新插槽族）必须在对应权威注册表头部带 §3 六字段缝声明，并在 `docs/` 索引页登记锚点* | 零基础设施；与「Central Utilities」「Prompts」等既有纪律条目同形态；对 7 域全覆盖 | 靠人自觉，遗漏率不为零 |
| CI 检查（升级路径，条件触发） | 可机守的子集自动化：① 工具域——`BUILTIN_TOOLS` 新增条目缺对应 `isToolAllowed` 门控键登记时告警（现有快照测试同思路扩到 tools）；② RPC 域——route-coverage 已有；③ 渲染域——card-tools 契约测试已有 | 硬门禁 | 头注释的六字段语义**无法机守**（注释是散文，不是结构）；全域上 CI 需要为每个域造解析器，成本高、误报风险大 |

### 5.3 推荐

1. **现在**：AGENTS.md 加一条 checklist（§5.2 方案一）+ `docs/` 落索引页。L2 服务头注释从三段扩到六字段时顺手做（不强制回头补写存量 12 个服务的后两段——新改动触及哪个服务就补哪个）。
2. **升级 CI 的触发条件**（满足其一时再立项，不做预告）：
   - checklist 两次以上失效（评审发现新增能力缺声明）；
   - L2 服务数或 `BUILTIN_TOOLS` 条目数显著增长（P2 cordis 化批量迁移时）；
   - 出现机器可消费结构（如方案 B YAML 化落地）。
3. **CI 范围限定**：即使升级，CI 只守**结构闭包**（清单不漏项、路由有归属、契约测试不漂移），**不守注释语义**——语义靠评审，这是 dsh capability seams 纪律的本来形态（文档纪律而非 lint 规则）。

## 6. 评审决策点（请小袁总批复）

1. **七域清单与勘误**：§1 的七个能力域是否认可？特别两处：hooks 域已按实际代码勘误（16 事件 TOML 引擎属 pi-muselinn-harness，本仓是 TS 模块 + shell 脚本两种载体）；channels 确认为独立域（IM 通道，未 L2 服务化）。
2. **声明载体**：推荐方案 A（代码内结构化注释 + docs 索引页）——是否批准？YAML 化（方案 B）是否留作远期不立项？
3. **强制机制**：推荐 AGENTS.md checklist 一条（§5.3）——是否批准？升级 CI 的三个触发条件是否认可？
4. **启停语义基线**：新增能力默认走覆盖层、选 always-on 必须写理由（§3 字段 3）——是否立为纪律？**存量 ~20 个 `<tool>.enabled` settings 键不迁移**（它们是 overlay:settings-key 档的合法形态，迁移无收益）——是否同意？
5. **冲突语义收敛**：扩展 register* 面四种冲突行为并存（覆盖/抛错/跳过/后者胜，§2.6）——本单只要求"声明现状"，是否需要另立专项收敛（例如统一为 reject 优先）？建议：**不收敛，先声明**；收敛属行为变更，应待真实冲突事故再议。
