> 状态：**调研结论 + 吸收建议**（未开工）。调研对象 `GCWing/OpenBitFun` @ `v1.0.6`（`602584253`，2026-10-15），对照线 `v0.2.19`（`32f242769`，2026-08-28）。

> 方法：两棵只读 git worktree + 直接读源码；未 build、未 install、未运行安装器。凡未运行时验证的结论标 **[静态]**；凡推断标 **[推断]**。

## 0. 结论摘要

1. **它不是"给 NSIS 换皮"，是换掉了安装器本身。** OpenBitFun 的安装器是一个**独立的 Tauri 2 + React 应用**：主应用产物在 `build.rs` 里打成 zip、用 `include_bytes!` 嵌进安装器 exe，安装时解压 + 逐文件 SHA-256 复核 + 写注册表/快捷方式；外层只有一层 Tauri NSIS 壳负责"把安装器 exe 放到用户机器上"。截图里那套界面就是这个 React 应用的首屏（`LanguageSelect` + 左侧 42% 品牌区 + 版本号 + 单选 + "继续"）。
2. **真正值得吸收的不是"界面长得好看"，是三处契约**：① 构建期就拒绝不完整 payload（`build.rs` 写死必需文件表，release profile 下校验目录和打出来的 zip）；② `--preview` 在**原生边界**做命令白名单（不是藏按钮）；③ 首启偏好走 handoff 文件，安装器从不写主配置。
3. **但"安装器形态"不该照搬。** 我们已经有 Electron 壳，再做一层 Tauri 安装器＝多一条 Rust 工具链 + 多一套签名/卸载/CI 面。更划算的是把"选择语言/主题/provider"留在应用内（`OnboardingOverlay` 已经做了三件事），安装器只负责落地文件。**handoff 文件只有在"安装器真的收集配置"时才有输入端**——这是决策的分岔点，不是默认要抄的组件。
4. **"1.0 才有自定义安装器"是误判。** `BitFun-Installer` 在 v0.2.0 就有 53 个文件（起源提交 `4615af9f`，2026-02-17）；5 步状态机、6 个页面、JSON manifest、Tauri2+React、NSIS target 在 0.2.x 就已定型，且 0.2.19 与 1.0.6 的 `STEPS` 数组逐字相同。1.0 的安装器变化是**改版 + 加严 + 品牌化**，不是从零引入。
5. **顺带发现我们自己的两个真缺陷**：① Windows 产物无代码签名（`gui-release.yml:69` 只有 macOS 的 secret 判断）；② 首启选的语言不写 daemon（`OnboardingOverlay.tsx:1150-1157` 只写 `localStorage`），而每次 boot 用 daemon 的 `settings.locale`（默认 `en-US`）覆盖渲染层 —— 首启选中文、重启后可能被打回英文 **[静态，代码路径闭合，未跑 GUI]**。

## 1. 事实基线（先纠正两个前提）

### 1.1 两条血统不相关，不能当演进读

```

git rev-list --max-parents=0 v0.2.19  →  439030a05 / 6cf29e3af  (本地 shallow 边界)
git merge-base v0.2.19 v1.0.6         →  空（exit 1）

```

新线里存在**同一 subject 的成对提交**（`feat: add BitFun-Installer module` = `afed0d84` / `4615af9f`，两棵树 `git diff --shortstat` = `4 files changed, 0 insertions(+), 0 deletions(-)`，只差被 gitignore 的产物）。即 1.0 是把 0.2.x 历史**重放/重写**一遍再继续的线。

## 2. 安装器是怎么做的（按数据流）

### 2.1 一句话架构

```
Build:  pnpm installer:build
          ├─ pnpm desktop:build:exe            → target/release/openbitfun-desktop.exe（+ frontend/dist 等）
          ├─ scripts/build-installer.cjs      → OpenBitFun-Installer/src-tauri/payload/ + payload-manifest.json
          ├─ src-tauri/build.rs               → OUT_DIR/embedded_payload.zip（release 下强制校验）
          └─ tauri build --no-bundle          → src-tauri/target/release/openbitfun-installer.exe

Runtime: openbitfun-installer.exe
          ├─ install   解压嵌入 zip → 校验 size/SHA-256 → 写注册表/快捷方式 → 写 handoff JSON
          ├─ uninstall 同一 exe 复制成 uninstall.exe，靠 exe 名 / --uninstall <path> 切模式 → 删文件 → 自删
          └─ preview   --preview 只放行 5 个只读命令
主应用下次启动：消费 handoff → 校验 → 落盘 app.json → 删除 handoff
```

### 2.2 代码规模与归属（先分清"自己的"和"借的"）

| 区域 | 规模 | 归属 |
|---|---|---|
| `src-tauri/src/installer/commands.rs` | 2017 行 | 自有（IPC + 安装/卸载主流程） |
| `extract.rs` / `registry.rs` / `shortcut.rs` / `types.rs` | 102 / 191 / 91 / 163 行 | 自有 |
| `src-tauri/src/preview.rs` | 54 行 | 自有（preview 白名单） |
| `src/hooks/useInstaller.ts` + 6 个 page | 356 行 + 66~462 行/页 | 自有；组件来自 design-system |
| UI 原子组件 / 主题 token | — | **借**：`@openbitfun/ui`、`@openbitfun/theme-openbitfun` |
| 模型连通性测试 / 列模型 | — | **借**：`openbitfun-ai-adapters` crate |
| provider 模板 | — | **借**：`src/shared/ai-provider-catalog/providers.json`（15 家） |
| 带锁 JSON 写入 | — | **借**：`openbitfun-services-core::json_file_store` |

一句话：**自有代码 ≈ 2.5k 行 TS + 2.5k 行 Rust**，其余是复用主仓库的 design-system 与 crate。这个比例很健康——说明"自绘安装器"真正的成本不在界面，而在**安装语义**（解压、校验、注册表、快捷方式、卸载、回滚）。

### 2.3 构建链（我们对它最感兴趣的部分）

`scripts/build-installer.cjs`（367 行）三段式：

| 阶段 | 行为 |
|---|---|
| Step 1 | `fast` → `desktop:build:release-fast`；否则 `desktop:build:exe`；`--skip-app-build` 跳过 |
| Step 2 | 清空 `payload/` → 复制主 exe（重命名固定）→ 复制 exe 同级运行文件（排除自身/`.cargo-*`/`.pdb/.d/.exp/.lib/.ilk`）→ 复制 6 个运行目录（`resources, locales, swiftshader, mobile-web, frontend, flashgrep`）→ 写 `payload-manifest.json` |
| Step 3 | `--dev` → `tauri:dev`；`fast` → `tauri:build:exe:fast`；默认 `tauri:build:exe` |

**三个值得抄的细节：**

1. **精确 profile 解析，拒绝静默回退**。期望路径 = `target/{release|release-fast}/openbitfun-desktop.exe`，可用 `--app-exe` 或 `OPENBITFUN_INSTALLER_APP_EXE` 覆盖；release 模式下找不到就 `exit 1` 并提示"先构建该 profile"。这是构建脚本最容易出事的地方（静默用了昨天的产物），它用"要么精确命中要么失败"解决。
2. **manifest 每文件记 `{path, size, sha256}`**，路径统一正斜杠、相对 payload 根。
3. **构建期硬门禁**：6 个必需文件必须同时存在于 manifest 和磁盘；主 exe ≥ 5MB；manifest 非空。

`build.rs`（166 行）把 payload 打成 zip 嵌进 exe：

- `payload/` 缺失 → 生成**空 zip**（`tauri dev` 时 Rust 侧写 placeholder 继续，方便调 UI）；
- `PROFILE != "debug"` 时**先校验目录**再打 zip；
- 打完**再打开 zip 校验一次条目齐全**（防止归档阶段丢文件）；
- 目录项按文件名排序 → 确定性产物；
- `cargo:rustc-env=EMBEDDED_PAYLOAD_AVAILABLE=1|0`；
- 消费端一行：`include_bytes!(concat!(env!("OUT_DIR"), "/embedded_payload.zip"))`。

→ **收益：单文件安装器，运行时不依赖外部 payload 目录。**

**CI 里唯一不能乱序的约束**（`.github/workflows/desktop-package.yml:367-398`）：

1. Tauri 打完 bundle 会把裸 exe 还原成**未签**状态；
2. 所以先重签裸 exe，注释明写 "before the custom installer snapshots and hashes its payload"；
3. 再 `OPENBITFUN_INSTALLER_APP_EXE=... pnpm run installer:build:only`；
4. 再签安装器 exe；
5. 发布前改名 `OpenBitFun_<version>_windows-x86_64-installer.exe` 并写进 updater manifest 的 `manual_installers`。

即：**manifest 的哈希必须对"最终要发布的已签名二进制"取。** 这条对我们做 OTA/安装清单同样成立。

### 2.4 运行期：安装主流程（`commands.rs:483-664`）

| # | 动作 | 失败 |
|---|---|---|
| 0 | `prepare_install_target(path)` + 记录 `install_dir_was_absent` | 返回错误码 |
| 1 | `create_dir_all`，5% | 回滚 |
| 2 | 嵌入 payload 预检 + 读 manifest + 解压 | 回滚 |
| 3 | 否则遍历 6 个候选路径（`resource_dir/payload.zip\|payload`、`resource_dir/resources/...`、`exe_dir/...`） | 逐个跳过 |
| 4 | 全失败：debug 写 `placeholder` 继续；release 报"checked: …" | 回滚 |
| 5 | 逐文件比对 size + SHA-256 | 回滚 |
| 6 | 把自己复制成 `<install>/uninstall.exe` | 回滚 |
| 7 | 写 `HKCU\Software\OpenBitFun Team\OpenBitFun` 默认值（对齐 Tauri NSIS `MANUPRODUCTKEY`） | 回滚 |
| 8 | 写卸载项（Add/Remove Programs） | 回滚 |
| 9 | 可选桌面/开始菜单快捷方式 | 回滚 |
| 10 | 写 handoff.language，92% | 回滚 |
| 11 | 记 last_install_path，100% | — |

回滚是**粗粒度但正确**的：按 flag 逆序清注册表/快捷方式，且**只在安装目录原本不存在时**才 `remove_dir_all`。flag 结构 4 个布尔（manufacturer / uninstall / desktop / startmenu）。

**诚实定位**：manifest 与 payload 在同一个 exe 里，所以 size/SHA 校验是"防损坏、防解压 bug、防构建错配"，**不是信任锚**。信任来自 CI 的 Authenticode 签名。

### 2.5 路径校验：错误码设计（我认为这是投入产出最高的一块）

`prepare_install_target`（`commands.rs:1214-1259`）按顺序：

| 顺序 | 检查 | 错误码（`INSTALL_PATH::` 前缀） |
|---|---|---|
| 1 | 绝对路径 | `not_absolute` |
| 2 | 不是盘根 | `filesystem_root` |
| 3 | 已存在须是目录 | `path_not_directory` |
| 4 | 追加 `OpenBitFun` 子目录（最后一段已是则不加） | — |
| 5 | 已存在且非空 → 必须已有主 exe（即覆盖安装） | `directory_must_be_empty_or_openbitfun` |
| 6 | 在"已存在目录或最近祖先"写 probe 文件再删 | `directory_not_writable` / `parent_not_writable` |
| 7 | 读目录失败 | `inspect_directory_failed` |

前端把 `INSTALL_PATH::snake_case` 映射到 i18n key，并对两个 not_writable 额外显示"以管理员身份运行"提示。**稳定错误码 + 前端本地化**这个分层，比"直接把 Rust 的英文错误串显示给用户"高一个档次。

### 2.6 preview 模式：在原生边界做能力裁剪

```rust
.invoke_handler(move |invoke| {
    if preview_only && !preview::allows_command(invoke.message.command()) {
        invoke.resolver.reject("Installer UI preview does not execute this operation.");
        return true;
    }
    handler(invoke)
})
```

- 开关 = 进程参数含 `--preview`；
- 白名单只有 5 个只读命令 + `close_installer`：`get_launch_context` / `get_default_install_path` / `get_existing_installation` / `get_disk_space` / `close_installer`；
- 连**会写 probe 文件**的 `validate_install_path` 都拒；
- `get_launch_context` 在 preview 下立即返回，**跳过任何会创建配置目录的 helper**；
- 自带测试同时断言"拒绝写/进程/网络/未知命令"和"放行只读"。

→ 效果：UI 设计师可以完整走一遍所有页面（标题栏有页面切换器），但物理上改不了机器。这是"预览模式"的正确做法——白名单在原生侧，不在 UI 侧。

### 2.7 首启配置交接（handoff）—— 最有复用价值的接缝

原则：**安装器不写 `app.json`**，只写一个交接文件；主应用下次加载配置时消费、校验、落盘、删除。

| 项 | 值 |
|---|---|
| 位置 | `dirs::config_dir()/<namespace>/config/installer-config-handoff.json` |
| 结构 | `{ language?, appearance_selection?, model? }`（None 不序列化） |
| 写入 | `JsonFileStore::update_locked`（跨进程 `<file>.lock`，读-改-写原子） |
| 安装器自有状态 | 同目录 `installer-state.json`：`{ last_install_path }` |

三个命令分别写同一文件的不同字段：`set_theme_preference` / `set_model_config` / install 时的 language。语言先规范化到 canonical id（`zh→zh-CN`、`zh-Hant-*→zh-TW`、`en→en-US`，别名表**由 i18n 契约生成**，按 alias 长度降序匹配以保证 `zh-Hant` 优先于 `zh`）。

消费方（`manager.rs:294-382`）：启动时 `consume_installer_config_handoff` → 加锁读 → 合并 `app.language` / `appearance.selection` / 模型（固定 id `installer:default`，`context_window` 写死、`default_models.primary` 与 `.fast` 都指向它）→ `normalize` + `reconcile` + `validate`，**不合法就报错且不写** → 原子落盘 → 删 handoff（删不掉只 warn，下次再消费，幂等）。

历史债：0.2.19 的安装器是**直接读改写 app.json** 的（`ensure_app_config_path()` + `read_or_create_root_config` / `write_root_config`），会和主应用配置写入竞争。1.0 改成 handoff 后，`manager.rs` 里仍留着 `try_repair_sparse_installer_config` 来修复那些被老安装器写坏的"稀疏 app.json"——这正好说明**直写主配置是错的**。

### 2.8 i18n：三层"生成 + 切片 + 审计"

1. **单一契约生成多端**：`src/shared/i18n/contract/locales.json` → `scripts/generate-i18n-contract.mjs` 一次产出 8 个文件，包括安装器的 TS 契约（`uiCode/appCode/nativeName/continueLabel/aliases/contentFallbacks`）和 Rust 侧别名表（供语言规范化）。理由：5 个 surface × 3 locale 的 id/别名/回退链必须一致，手写必漂移；但"共享契约 ≠ 共享 bundle"，安装器不许 import web-ui 语言包。
2. **从主应用语言包切片同步**：两个 sync 脚本在 `predev/prebuild` 前置跑，只覆盖 `model.*` 与 `themeSetup.themeNames.*` 子命名空间；安装器自有文案（`options.*`/`uninstall.*`/`errors.installPath.*`/`steps.*`/`preview.*`）手写。
3. **审计门**：以 `en.json` 为基线做 key 奇偶 + 占位符奇偶，动态 key 白名单。

**风险点**：sync 脚本的 `get()` fallback 是**英文硬编码**，上游 key 改名时脚本不失败，只会把英文写进 zh/zh-TW；而审计只查 key 集合奇偶，查不出英文串混进中文。

### 2.9 design-system 是 1.0 的独立收成

`design-system/`（696 文件）= `@openbitfun/design-tokens` + `@openbitfun/theme-openbitfun` + `@openbitfun/ui` + `token-engine` + `design-lab`，引入提交 `a33d5fdcd`（2026-08-25，早于 1.0.0-beta）。安装器的 `App.tsx` 顶层是 `<DesignSystemProvider>`，`--preview` 的页面切换器直接用它的 `Select`，主题实时预览是把 token 投影成 15 个 CSS 变量。

→ 截图那种"干净、克制、无渐变"的观感，来自**统一 token + 统一组件**，不是安装器自己调出来的。这一点对我们尤其重要：我们已经有 `client-core` 的共享渲染组件与 `docs/gui-design.md` 的 token 体系，缺的是"安装器也用同一套"。

## 3. 1.0 相对 0.2.x 到底改了什么

### 3.1 纠偏：安装器不是 1.0 才有的

| tag | 安装器文件数 |
|---|---|
| v0.2.0 | 53 |
| v0.2.5 | 64 |
| v0.2.9 ~ v0.2.19 | 66 |
| v1.0.6 | 70（改名 `OpenBitFun-Installer/`） |

5 步状态机逐字相同：

```
0.2.19 BitFun-Installer/src/hooks/useInstaller.ts:52
1.0.6  OpenBitFun-Installer/src/hooks/useInstaller.ts:53
  const STEPS: InstallStep[] = ['lang', 'options', 'progress', 'model', 'theme'];
```

6 个页面、窗口 760×560 / min 700×480、Tauri 2 + React、`bundle.targets:["nsis"]` 两边一致。

### 3.2 真正的 4 条实质变化

| # | 变化 | 0.2.19 | 1.0.6 |
|---|---|---|---|
| 1 | **payload 校验加严** | `PayloadManifestFile` 只有 `{path}`（0.2.19 `commands.rs:66-69`），构建脚本写的 `size`/`sha256` 被 serde 静默忽略；`verify_installed_payload(&install_path)` 只查主 exe 存在且 ≥5MB | `PayloadManifestFile` 有 `{path,size,sha256}` 三字段（1.0.6 `commands.rs:82-87`）；逐条比对 size + 流式 SHA-256（`:1787-1844`）；新增 `validate_payload_manifest`（路径非空/去重/格式/必需路径齐全，`:1639-1662`）；`build.rs:8` 硬编码 6 个必需文件并在 release 下校验目录（`:36`）与打出来的 zip（`:43`） |
| 2 | **handoff 取代直写 app.json** | 安装器直接读改写 `<config>/bitfun/config/app.json` | 写 `installer-config-handoff.json`，主应用消费后删除；安装器侧有测试断言"不创建 app.json" |
| 3 | **新增 `--preview` 沙箱** | 无 | 原生边界白名单 + 前端 `previewOnly` 短路所有写操作 |
| 4 | **改版（视觉 + 组件）** | 内联 style 大段、手算 `STEP_NUMBERS`（"2/4"）、硬编码版本号 `Version 0.2.15`、零测试 | design-system 组件 + `StepIndicator` + `BrandMark` + 主题 bootstrap（防 FOUC）+ 首批安装器测试 |

安装/卸载/注册表逻辑**基本没动**（`registry.rs`/`shortcut.rs` 只有品牌字符串改动）。

### 3.3 Data Migrator：加了又撤，是负面教材

- `b5d1532ef`（09-07）把迁移器打进安装器 payload；
- `e2677e056`（09-09）撤掉打包要求；

### 3.4 用户可见的 5 条（1.0 相对 0.2.x）

1. **四种 Harness 模式**：Minimal / Standard / Ultimate / Creative，取代 0.2.x 的 `agentic/plan/ultra/team/multitask/cowork`；Plan 降级成 skill。
2. **跨设备远程控制 + 移动端一等公民**：独立 `mobile-v*` tag 与发布工作流、`src/apps/mobile` 增量最大（A=758 文件）。
3. **数据不兼容 + 独立 Data Migrator**：README 原文 "not data-compatible with legacy 0.2.x"。
4. **design-system 独立成 workspace**：GUI 与安装器共同消费。
5. **安装器改版**：品牌化 + 步骤条 + design-system + 更严校验 + preview。

内部重构（crate 边界重排、flow-chat 呈现层抽包、vendored `tao`/`eioc`）对"吸收什么"无信息量。

### 3.5 一个值得单独存档的兼容设计

`bb92758d7`（09-20）把旧更新源**固化成仓库 fixture**：1.x 客户端读 `latest-v1.json` / `linux-binaries-v1.json`，0.2.x 客户端继续读 `latest.json` / `linux-binaries.json`，后者被钉死成"0.2.20 通知版"（platforms 全指向 v0.2.19 产物，notes 写"不要点后台下载，请手动下载 1.x 并用 Data Migrator 迁移"）。CI 用 `cmp` 对上传后的资产做字节比对，fixture 漂移即失败。

→ **旧客户端永不静默升级到不兼容的大版本。** 这条对任何做破坏性升级的产品都适用，成本极低。

## 4. 值得吸收 / 不该照抄

### 4.1 值得吸收（按投入产出排序）

| # | 能力 | 为什么 | 与栈无关？ |
|---|---|---|---|
| 1 | **构建期 payload 硬门禁** | `build.rs` 把必需文件表写成常量，release 下先校验目录再校验 zip。比 CI 脚本自查或运行期报错都便宜，且不依赖脚本正确性 | ✅ 任何打包链都能做 |
| 2 | **签名先于清单快照的顺序** | Tauri 打完 bundle 会还原未签裸 exe，所以"重签裸 exe → 打包安装器 → 签安装器"。否则清单哈希与发布的二进制不符 | ✅ 概念通用 |
| 3 | **路径校验的稳定错误码 + 前端本地化** | `INSTALL_PATH::snake_case` → i18n；probe 文件验可写；提权提示。我们 NSIS 现在只有系统报错 | ✅ 任何栈 |
| 4 | **preview 在原生边界裁剪** | 白名单在 Rust/IPC 层而不是 UI 层；连"会写 probe 文件"的校验都拒；且跳过创建配置目录 | ✅ 任何栈 |
| 5 | **handoff 文件解耦"安装器"与"配置真相"** | 安装器不需要知道主配置 schema，不会写坏；跨进程文件锁；消费即删、幂等 | ✅ 任何栈 |
| 6 | **精确 profile 解析，拒绝静默回退** | `--app-exe` / env 覆盖 + 找不到就 exit 1 | ✅ |
| 7 | **回滚 flag + "目录原本不存在才删"** | 粗粒度但正确的回滚边界 | ✅ |
| 8 | **卸载器 = 自身副本 + exe 名/参数双入口 + 重试自删** | 免维护第二个二进制 | ✅ Windows |
| 9 | **已安装检测的 UI 化** | Disclosure 展示版本/路径 + "运行卸载器"，focus/visibilitychange 刷新 | ✅ |
| 10 | **主题实时预览** | 整窗即预览，radio + 三色色块，不做缩略图 | ✅ |
| 11 | **i18n 单一契约生成多端** | 解决"多 surface × 多 locale 的元数据一致性"；与我们"按域拆分 + en 编译期对齐"互补 | ✅ |
| 12 | **旧更新源固化成 fixture** | 旧客户端永不静默升级到不兼容版本 | ✅ |

### 4.2 不该照抄（都有实据）

1. **三份重复的必需文件常量 + source-grep 测试**：`REQUIRED_PAYLOAD_FILES` 在 cjs / build.rs / commands.rs 各写一遍，靠测试**读源码正则匹配**来锁一致。这违反我们"禁 source-grep 测试"的规则；正确做法是单一 JSON 源三处消费 + 运行时断言。
2. **IPC 契约里塞前端专属字段**：`InstallOptions` 的 `themePreference` / `modelConfig` / `launchAfterInstall` 随 IPC 过一遍，Rust 一个都不读（`start_installation` 只用 `install_path/desktop_shortcut/start_menu/app_language`）。
3. **死状态机分支**：`canConfirmProgress` 只在 start 时置 false，全库无置 true 之处 → Progress 页"完成态 + 继续按钮"不可达；`installationCompleted` 只写不读。安装成功后前端直接 `setStep('model')`，用户永远看不到"安装完成"。
4. **假进度**：卸载先跑 1.8s 动画从 0 爬到 85%，动画结束才真正 `invoke('uninstall')`；安装解压段 15%→50% 之间毫无反馈（payload 上百 MB）。
5. **release 版零诊断信息**：Rust `log` crate 从未初始化（无 `env_logger` / `tauri-plugin-log` / `set_logger`），前端 `console` 又被 terser `drop_console` 删掉 → 用户报安装失败时**没有任何日志可查**。这是最容易在自家照抄时一起继承的坑。
6. **README 当规格会做错**：README 宣称 "right-click context menu, PATH integration"，但代码里这两个**只在卸载时删除、安装时从不注册**（注释直接写 "no longer registered on install"）；`UninstallString` 文档说有 `--uninstall <path>`，实际只写 `"<dir>\uninstall.exe"`（靠 exe 名兜住）。
7. **请求 URL 推导双实现**：TS 与 Rust 各一份 `openai/responses/anthropic/gemini` 拼接，注释自承 "Copied from main app settings"。漂移后 UI 预览 URL 与实际请求不一致。
8. **覆盖安装无逐文件回滚**：目录原本存在就整目录保留，升级失败会留下新旧混合版本；不比版本、不拦降级。
9. **磁盘空间只在 UI 门控**：API 失败即视为 `available: u64::MAX, sufficient: true`；`start_installation` 内部不再校验。
10. **安装器不检测主应用是否在运行**：全库无进程检测（对比我们 NSIS 的 `customCheckAppRunning` 是真的需要）。
11. **`%TEMP%` 可预测文件名的自删脚本**：可用，但不是安全模板。
12. **废弃功能的 i18n 键不清理**：`complete.migrateLegacyData*` 仍留在三份 locale 里，审计只查奇偶不查未用。

## 5. MusePi 落差与落地方案

### 5.1 我们现在的样子（一句话）

**只有 44 行 `.nsh` 补丁的 electron-builder NSIS assisted 安装器**：两个宏——`customInstall`（无条件重建桌面/开始菜单快捷方式，绕过 electron-builder 的 `KeepShortcuts` 与 `isUpdated` 双门控，否则 OTA 后桌面图标不补建）+ `customCheckAppRunning`（用 PowerShell 按 `$INSTDIR` 路径过滤进程，避免误杀 TUI/CLI 的 `musepi.exe`）。

**首启向导完全在应用内**（`OnboardingOverlay` 三步：语言+外观 / 模型供应商 / 完成），可 Esc/× 直接跳过，完成标记只写 `localStorage`。**安装器与应用首启之间没有任何数据接力。**

i18n 不能给 NSIS 复用：词表是 TS 源码 + `localStorage`/`navigator` 运行时，en 侧靠 `as const satisfies Record<ZhKey,string>` 编译期对齐。

### 5.3 三种吸收路线（我的建议是 B）

| 档 | 内容 | 成本 | 收益 | 建议 |
|---|---|---|---|---|
| **A. NSIS 自绘页** | electron-builder 官方钩子内做品牌欢迎页 + 语言页（`MUI_CUSTOMFUNCTION_GUIINIT` + nsDialogs + GDI+），不带 DLL/7-Zip 管线 | ~500-700 行 NSIS，无新工具链 | 首屏/完成页品牌化；但安装期收集的配置仍需 handoff 才能到应用 | 可选，作为"观感"档 |
| **B. 应用内首启 + 轻量安装器**（推荐） | 安装器保持 NSIS（只加产物清单校验 + 路径校验 + 品牌位图）；把"选语言/主题/provider"留在应用内，但**修好 handoff 缺失的那一半**：语言落 daemon、向导加版本号、安装器若能写首启答案则读入预填 | 小-中（改 4-5 个文件 + 1 个 CI 步） | 直接命中真缺陷（#9/#10/#12/#13），不动打包链 | **首选** |
| **C. Tauri 独立安装器** | 照搬 OpenBitFun 形态 | 大：新包 + Rust 工具链进 CI + 签名 + 卸载器 + 一条新的平台失效面 | 唯一性收益是"单文件 exe + 内嵌 payload + preview"；但我们是 Electron，payload 就是 asar 目录，内嵌收益低 | 不建议 |

**为什么 B**：OpenBitFun 那个形态成立的前提是"它本来就是 Tauri 应用，安装器复用同一套 Rust crate 和 design-system"。我们的栈是 Electron，做 Tauri 安装器等于开第二条原生工具链；而我们已经有一个做得不错的三步首启向导（ZCode 风格双栏、可跳过、可重开）。**真正缺的不是"更多界面"，是"安装器与首启之间的契约"和"产物可信"**。

关键判断：**handoff 文件只在"安装器真的收集配置"时才有输入端。** 如果走 B，可以先用"安装器写答案文件（NSIS 也能写 JSON/注册表）+ 应用读入预填"的最小形态试水；如果确认价值不大，就只修 #12（语言落 daemon）——那一个改动就能消掉"首启选中文重启被打回英文"这个真实缺陷。

### 5.4 建议的推进顺序

**阶段 0（半天-1 天，纯收益，无架构决策）**

1. 修 #12：`OnboardingOverlay.tsx:1150` 的 `applyLocale` 补 `settings.set("settings.locale")`。这是真 bug，且不修的话任何"安装期选语言"都会被打回。
2. 修 #14：统一 `update-manifest.json` 的 `notes` 形态（CI 生成对象 + 消费侧按 locale 取）。
3. 加 #9：`gui-release.yml` 里用现成的 `bun run ci:release:checksums` 覆盖 GUI 产物，发布 `SHA256SUMS.txt`。**校验脚本已存在，只是没接上 GUI。**

**阶段 1（1-3 天，工程契约）**

**阶段 2（需要决策，可后置）**

## 7. 附：三条可独立复用的判断

1. **"1.0 新增安装器"是伪命题。** 要吸收的是 0.2.x 就已定型的安装器架构 + 1.0 的三处加严（manifest 校验 / handoff / preview），不要重写整个安装器。
2. **构建期硬门禁 > 运行期校验 > CI 脚本自查。** 因为前者的正确性不依赖"记得跑哪个脚本"。
3. **把重工具塞进安装器是陷阱。** 官方两天内自我回退；可选的重能力应独立分发、独立签名、独立发版。
