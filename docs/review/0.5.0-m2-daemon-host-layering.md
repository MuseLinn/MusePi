## 1. 背景与目标

**为什么是现在**。dsh 0.1.7 官方发布了 Electron 桌面客户端（`apps/desktop`），"壳/宿主分离"从社区实践变成有官方背书的成熟形态；小袁总指示 daemon 改造参考 kimicode/dsh/zcode 最新源码。同时我们的单进程 daemon 已到临界点：`server.ts` 10,652 行，设置面板审计（M2-2.10）出现"受单进程 daemon 限制"的整档未接线项，插件化（M2 批次）要在巨石上加状态机/覆盖层/能力缝，继续堆叠的边际成本越来越高。

**目标**：

1. 在 **collab-proto 协议全程不动**、不中断 0.4.x 维护的前提下，给出 daemon 从"单进程巨石"演进为"宿主服务分层"的设计与迁移路径；
2. 与 cordis 试点（M2-2.9）**解耦**——设计中新增的中间层无论试点成败都成立，试点成功只是给这层换实现；
3. 让 M2 的 2.2/2.3/2.4 有明确落点，让 2.10 的"受限制档"能逐服务销项。

**三条追加纪律（小袁总 2026-09-25 批复 P1 时立下）**：

1. **会话改动接口契约检查**：凡触碰会话生命周期/journal/广播的抽取，必须逐条核对客户端 session tree 功能的相关接口（`session.branchAt`/撤回/leaf 移动/快照恢复等），保证 wire 事件与 RPC 行为零变化——相关测试（`test/daemon/session-branch-at-*`、`session-catchup-rpc` 等）是验收门槛；
2. **事件驱动，禁止轮询**：宿主层能力一律走事件/推送语义，不得以轮询图方便（dsh 的 Host 事件纪律同）；客户端已见的轮询式实现（如有）在服务化时改为事件驱动；
3. **TUI 插件化愿景**：TUI 未来与 desktop-app 平级——作为壳侧消费方（乃至壳插件）接宿主服务，最终形成 dsh 式"宿主可扩展 + 多壳稳定"的架构。0.5.0 不做，但 L2 服务接口禁止掺入任何"假设调用方是 GUI"的语义，为 TUI 插件化留路。

**非目标**（0.5.0 内不做）：不重写 agent 循环（L3 领域核心不动）；不换 WS 协议；不动 desktop-app 壳与液态玻璃 UI；不做多进程沙箱隔离（dsh `cordis-host-runner` 形态列为远期）。

## 2. 现状盘点（我们的）

### 2.1 daemon 侧（packages/coding-agent/src/daemon/）

| 件 | 规模 | 职责 |
|---|---|---|
| `server.ts` | 10,652 行 | `DaemonSessionHost`（L1102–3004，会话生命周期/复活/idle 快照）+ `DaemonServer`（L3044–10090，连接/静态资源/RPC 巨型 switch/凭据/更新）+ `startDaemon` |
| 20 个卫星模块 | — | approval-bridge / boards / browser-rpc / crons / event-batcher / extension-artifact-compiler / extension-lifecycle-tools / extension-runtime-tools / extension-sandbox / fs-ops / fx-rates / journal / pause-sidecar / pty-bridge / remote / static-web / terminal-provider / view-store / ws-transport 等 |

**判断**：分层已有雏形（卫星模块就是事实上的领域切面），缺的是一层**服务契约**——卫星模块被 server.ts 直接调用，无注册表、无生命周期、无能力缝声明，所以"插件化管理"和"设置接线"都无从挂接。

### 2.2 壳侧

- `desktop-app/electron/main.cjs` 3,724 行：窗口族/桌宠/气泡/托盘/更新/IPC——纯壳，无 agent 语义 ✅
- `client-core`（原 guest-client）+ desktop-app 渲染层、TUI、安卓远程：三个消费者经 collab-proto WS 接 daemon ✅

### 2.3 痛点 → 根因映射

| 痛点 | 根因 |
|---|---|
| 设置面板整档未接线（2.10） | daemon 能力散落在巨型 switch 私有方法，无服务边界可声明"谁提供什么" |
| 扩展热重载只能重启 | extension-* 模块无生命周期语义，随 server 一次性启动 |
| marketplace 无安装状态机（2.2） | 无 Marketplace 服务承载状态机，安装逻辑嵌在 RPC handler 里 |
| mode/preset 无会话组合执行面 | 无"会话作用域"概念可挂组合（cordis 试点 spike ② 的对症点） |

## 3. 对标：dsh 0.1.7 壳/宿主分离

### 3.1 它的形态

- **壳**（`apps/desktop/src`，核心四件共 1,776 行）：`main.ts` 1,293（窗口/托盘/更新/快捷键/退出确认）、`host-process.ts` 322（RunAsNode 子进程生命周期）、`backend-controller.ts` 157、`host-protocol.ts`。Electron 壳**零 agent 语义**。
- **宿主**：一个 RunAsNode 子进程跑完整 dsh Web 应用——`packages/host/` 插件族（webserver / apiproxy / frontend-static / plugin-inventory / directory-picker×4 / open-in-app / product-telemetry-otel），会话、技能、计划等能力族全部在宿主进程内以 cordis 插件组合。
- **壳↔宿主契约**：私有 IPC 控制面只有生命周期事件（ready/fatal/shutdown-complete/quit-inspection/update-tasks）；**数据面（HTTP/WS）由渲染端直连宿主**，壳只做转发与凭证隔离。退出前 `quit-inspection`（2s 超时按"有任务"处理）再弹确认。

### 3.2 对我们的启示（形态差异）

**dsh 是"壳 + 第二运行时（宿主子进程）"；我们是"壳 + 单进程 daemon 即宿主"**。我们不引入第二个运行时——daemon 进程保留，把它的**内部**切成层。dsh 值得逐条吸收的是三条纪律：

1. **壳零语义**：desktop-app main.cjs 保持纯壳（现状已符合，写死为纪律）；
2. **控制面/数据面分离**：壳↔daemon 的 IPC 只走生命周期；会话数据永远走 collab-proto（现状符合）；
3. **退出前问询**：daemon 提供 `quit-inspection` 语义（活动会话/定时任务两事实），desktop 关闭确认窗消费——对齐 dsh `quit-inspection`，也回应小袁总对托盘/关闭行为的既有要求。

## 4. 目标架构：四层

```
L0 壳    desktop-app(Electron) / TUI / guest web / 安卓远程   ← 不动
            │  collab-proto WS（数据面，唯一通道）  +  壳 IPC（仅生命周期）
L1 接入层  DaemonServer（瘦身）：连接/鉴权/通道绑定/静态/RPC 路由表
            │  路由表：method → (service, handler)
L2 宿主服务层 HostServices（新增，本设计核心）：
            SessionService / ExtensionService / MarketplaceService /
            ScheduleService / BoardService / BrowserService / FileService /
            TerminalService / RemoteService / ApprovalService /
            EventService / UsageService / ViewStoreService …
            每个服务：纯 TS 接口 + 能力缝声明 + 生命周期(start/stop/reload)
L3 领域核心 packages/agent · ai · wire · sdk · extensibility/hooks  ← 不动
```

**关键决策：注册表模式 = cordis 未定前的稳定中间层**。L2 服务接口按"将来就是一个 cordis Service"的形状设计（`ctx.<key>` 同名、inject 式依赖、effect 式注册可逆），但**零 cordis 依赖、纯手写注册表**。2.9 试点成功 → L2 服务逐个包成 cordis Service，注册表退化为兼容垫片；试点失败 → L2 就是终态，损失为零。这条决策让 M2 的 2.2/2.3/2.4 今天就能动工，不被试点阻塞。

## 8. 风险与评审决策点

**风险**：

1. P1 搬移回归面（巨型 switch 的行为依赖、事件序敏感）→ 路由表快照测试 + 分服务灰度合入；
2. cordis 4.0.4 相对 4.0.2 的 API 变化 → vendor 时锁定版本并附 API diff 笔记；
3. SessionService 抽取触碰复活/idle 快照/事件序，是全计划最险一刀 → 放最后、独立 PR、双跑验证。

**评审决策点（请小袁总批复）**：

1. **P1 纪律**：纯搬移、不改 RPC 命名/参数/事件序（建议：批准；任何协议微调另立 PR）；
2. **L2 服务粒度初表**（§5 顺序 + §4 清单）是否认可，有无遗漏服务（候选遗漏：PetService? daemon 侧无宠物语义，view-store 已覆盖——如不同意请指出）；
3. **P2 首个 cordis 化服务候选 SessionService**（建议）还是从更小的 UsageService 开始（更稳但验证力弱）。
