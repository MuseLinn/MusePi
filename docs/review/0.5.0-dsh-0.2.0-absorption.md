## ① composer 底部「性能与用量」条（StatsPills）——**推荐吸收，小-中**

### dsh 实现事实（`packages/client/ui-chat/src/client/chat/StatsPills.tsx` + `performance-usage.ts`）

- **挂载点**：`conversation.composer.dock` 插槽——跟着 composer 走，在会话滚动口内吸底，不占顶栏/侧栏空间。
- **两颗 pill**：时间丸（⚡ `N 轮 M 步 · 260 tok/s`）与用量丸（💾 `4.3M tok · 缓存命中 82%`）；点击出 popover 明细（模型用时/工具调用用时/TTFT/输出速度；精确 input/cacheRead/cacheWrite/output 分桶）。右缘再配上下文圆环（63%）。
- **数据契约**：全部数字优先读持久 projection（`sessionStats` / `tokenUsage`），**无 projection 时整体回退**到「可见窗口 fold」（`deriveStats`，字段名与 projection 故意同形，整体互换）；分页/compaction 永不改变已显示数字。
- **降级细节**：窗口里没有任何计时数据时，pill 退化为纯读数（不开放空 dialog）；两 pill 的 dialog 互斥（同时只开一个）；设置项「性能与用量：简洁/详细」控档（compact 档只显示速度 + 缓存命中两个纯读数）。
- **流式性能**：settled-node 身份做 memo，流式 delta 不重渲染该行。

### 我方对照

- **已有底子**：composer footerRight 已有 `ContextRing`（上下文圆环，点击开 `context-dialog.tsx`）；`contextUsage` 投影走 daemon；TUI 时期就有 `/context`、`/usage` 斜杠命令——但 GUI 里要看上下文详情/用量得离开输入区。
- **差距**：没有「跟随 composer 的常驻统计行」；轮次/步数/TPS/缓存命中率在 GUI 不可见（TUI 有）；`/usage`（账号额度）与上下文/用量信息分散。
- **拟立项（M1.10 批次 C 增补或独立小项「composer 统计条」）**：
  1. composer 底排下方新增 stats 行（与 ContextRing 同排或相邻），两颗 pill：轮次·步数·TPS、总 tok·缓存命中；popover 明细与 dsh 同构；数据读 daemon `sessionStats`/`tokenUsage` 类投影，无投影时按可见窗口 fold（字段同形回退，照抄 dsh 设计）。
  2. 设置项「性能与用量：简洁/详细」（compact 只留速度+缓存命中纯读数），与 dsh 的设置行同名同语义。
  3. ContextRing 保持原位的两种方案待评审：**A**（推荐，dsh parity）圆环留在胶囊排、pill 行在其下；**B** 圆环并入 pill 行右端，胶囊排减重。
- **验收**：分页/压缩后数字不变；无计时数据时 pill 退化为纯读数；流式中 stats 行不重渲染（memo 契约测试）；compact/detailed 两档设置即时生效；设计稿章节并入 `gui-design.md`（既有面板改动）。

## ② cordis 插件化完善与安全插拔——**推荐立项（M2 后续批次），中-大**

### dsh 0.2.0 事实

- **终端就是插件**：`packages/terminal/terminal` 是 cordis `Service`（`declare module '@deepseek-ai/cordis' { interface Context { terminals: TerminalSessionService } }`，backend 可插拔，错误码 DUPLICATE_BACKEND/NO_BACKEND/FOREIGN_SESSION）；`tool-terminal` 是六件模型-facing 工具的插件，`name`/`inject: ['terminals','tools','systemPrompt']`/schemastery `Config` 三件套声明式装配。
- **插件管理器**（截图「插件」页）：官方 8 插件（智能体团队/自动授权审查/自动化任务/语音输入/终端/Agent 循环/子智能体/网页搜索）逐行开关 + 一行能力描述 + 实验性徽记；「添加插件」支持 registry/git/路径安装，**安装需确认**（install-approve 测试族）。
- **回退保护**：兼容性拒绝（`incompatible-version` 结构化列出拒绝的包/runtime/peer 区间，带豁免 exemption 机制）；preset 声明的插件**加载失败只跳过该层**（`a load error means its layer was skipped`），不拖垮宿主；设置页 preset 卡片「查看配置」只读打开声明的插件列表 YAML，**加载失败的 preset 也能读**（诊断指向 YAML）；ManagementFailure 结构化错误码由调用方本地化渲染。
- 0.2.0 其他：webworker preview 内打开配置文件 + 加载插件管理器（插件在 preview 环境可运行）、plugin-manager 交互打磨一批、agent-preset 创作文档合并进 cordis-plugin-development。

### 我方对照与差距

- **已有**：扩展系统有 HMR 热拔插（入口变更 500ms 广播 + 忙会话挂起 `agent_end` 补做，AGENTS.md 有契约）；cordis 定案 v3（roadmap §4.3，收编约束解除）；M2 daemon 宿主分层设计稿（L2 HostServices 注册表，P2 才是 cordis 适配）。
- **差距**：① 内置能力（终端/浏览器/语音/STT-TTS）还是硬编码，未走 cordis 插件声明；② 扩展加载失败的面域隔离与「跳过该层」语义没有制度化；③ 无兼容性声明/拒绝/豁免机制；④ 插件管理页没有 dsh 式「逐行开关 + 能力一行话 + 实验性徽记」的呈现规范。
- **拟立项（挂 M2 后续或独立 M2.13「内置能力 cordis 化与安全插拔」）**：
  1. **声明式插件三件套对齐**：`name`/`inject`/`Config`(schemastery 或我们 settings schema) 作为内置能力改插件的统一装配契约（对齐 tool-terminal 先例）。
  2. **首批候选**：终端（pty 服务 + 工具）最适合第一个收编——我方 TerminalPanel 已是常驻挂载，`packages/terminal` 的 owner-scoped registry + backend 接口可参照。浏览器、语音随后。
  3. **回退保护三件套**：加载失败层隔离跳过（不拖垮宿主 + 面域 toast）、兼容性声明与拒绝（版本/peer 区间 + 豁免）、禁用插件时的内置能力兜底策略（终端禁用 → 会话内工具降级提示，不静默失效）。
  4. **插件管理页规范**：dsh 式行卡（图标+名称+一行能力描述+开关+实验性徽记）作为液态玻璃批次的管理页收敛目标。
- **验收**：禁用一个插件宿主无感（其余插件/核心不受影响）；终端插件卸载后会话工具给出结构化降级提示；兼容性拒绝带可读的包/版本清单；管理页行卡符合 §5s 玻璃层级。

## ②b 附录：dsh 单插件管理页解剖（语音输入为例）——**作为 #2 管理页规范的工程化基准**

`packages/experimental/voice-input-bundle` 是「插件套插件」的样板：bundle = `cordis.patch.yml` 声明插入 4 个子插件（speech-to-text 提供者抽象 / sensevoice-local 本地服务 / api-speech-to-text 云端兜底 / client-ui-voice-input 界面），首用自动下载运行时（"downloads its runtime on first use"）。其管理页（小袁总截图）的信息架构：

1. **头部**：名称 + 版本 + 稳定性徽记（实验性）+ 包名（@deepseek-ai/...）+ 一行能力描述 + 主开关。
2. **配置表单**：识别服务 / 识别语言等行——由插件声明的 schemastery `Config` **同一 schema 驱动**（配置界面与运行配置单一来源）。
3. **资源需求卡**：磁盘占用（~1GB）/ 运行内存（~1GB）/ 首次准备时长（1-10 分钟）——插件在 manifest 里声明资源要求，管理页照实渲染。
4. **首用引导流**：「首次使用需下载本地识别模型」展开器 + 模型下载源选择（自动选择(推荐)）+ 「下载并准备」按钮。
5. **包含的组件**：子插件清单，每个独立开关 + 运行中状态点——bundle 的子层可单独插拔。

**我方映射**（并入 #2 的验收）：扩展 manifest 增加资源要求字段（磁盘/内存/首次准备）→ 管理页资源卡；扩展 Config schema 驱动配置表单（我们 settings schema 已有，缺的是「按扩展声明生成表单」的渲染器）；bundle 子组件清单 = 我们扩展的 slot/contributions 列表 + 逐项启停。这张截图就是 #2「管理页行卡规范」的完整参照系。

## ③ creator 预设 vs dsh 创造模式——**部分对齐即可，小-中**

### dsh 事实

- 预设设置页**只读**：内置（标准/PTC/极简/创造）+ 自定义分组卡片、默认项高亮、每张卡片「查看配置」以只读 YAML 打开 preset 声明的插件列表（Loader 方言，加载失败的 preset 也可读）；**创建/修改一律引导至创造模式任务**（"让 Agent 帮我创建预设模式"），由创造模式以 bundle 形式创建或按行 id 覆盖内置 preset；0.2.0 起 agent-preset 与 creator mode 共享 agent experience skill，创作文档合并进 cordis-plugin-development。

### 我方对照

- creator 预设已存在（`presets/resolve.ts:316`，全量工具 + 创作 persona，提示遵循 musepi-extension-dev 技能与 modes 契约、`modes.validate` 自检）——**基础能力在**，能与 dsh 创造模式同路（自然语言创建/修改预设）。
- **真实差距**：① 没有「查看配置」只读视图——预设卡片/设置页看不到生效的继承展开结果（extends/prompt 区块/settings 覆盖），调试靠翻 `~/.musepi/modes/*.json`；② 创建产物没有 review 面（dsh 是 bundle + 行 id 覆盖的显式契约）；③ 创造质量依赖 persona 提示词，无 dsh 的「创作提示词两代演进 + userModified 编辑保护」体系（workdsh `WORKBUDDY-CREATION-*` 两文档此前已并入 M4.1 输入，预设创建流可共用）。
- **拟立项（小-中）**：预设设置页卡片化（内置/自定义分组、默认高亮、「查看配置」只读展开继承解析结果）。**creation-prompts 两代演进方法的吸收归 design 模式**（小袁总 2026-09-29 指正）——design 模式的创作工作流提示词吸收 workdsh `WORKBUDDY-CREATION-*` 两文档方法（从例子倒推资源 / 自检清单），creator 预设只保留查看配置入口，不再单独吸收。**不照搬** dsh 的「设置页零编辑全委托 agent」——我们的设置页编辑器已存在且用户可用，保留编辑能力，只补只读视图与创建引导入口。

## ④ 模式中文名与预设设置页——**确认 bug，小**

### 根因（两个叠加）

1. **词表没翻译**：`packages/coding-agent/src/i18n/zh-CN/commands.ts:759` 起 `"preset work name": "Work"`、`"preset chat name": "Chat"`、`"preset design/creator name"` 全是英文——zh 词表里就是英文，所以 daemon `modes.list` 本地化后返回的还是英文。
2. **GUI 绕过了取名链**：`WelcomeComposer.tsx:1634/1652` mode chip 直接用 `modes.list` 的裸 `m.label`；而 `mode-label.ts` 的 `resolveModeLabel`（GUI i18n `mode {id}` → catalog → 兜底）只被 ContextPanel/SessionHoverCard 用，chip 和它的选项菜单都没走。

### 拟修复（小）

1. zh 词表补翻译（建议：工作 / 聊天 / 设计 / 创造，或带「模式」后缀，随评审定）；en 保持。
2. WelcomeComposer 的 chip 与选项菜单改走 `resolveModeLabel(id, catalog)`，与 ContextPanel/SessionHoverCard 同名同链（mode-label.ts 头注释已有「两处必须永远显示同一个名字」的契约，扩成三处）。
3. 预设设置页（`settings-sections/modes.tsx`）参考 dsh 卡片化：内置/自定义分组、默认项高亮、卡片内一行描述——随 ③ 的卡片化一起做，不单独立项。
