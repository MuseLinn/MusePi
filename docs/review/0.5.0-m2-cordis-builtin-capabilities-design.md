## 0. TL;DR

## 1. 声明式三件套契约（`name` / `inject` / `Config`）

### 现状（文件:行号）

- 内置能力的注册是**散点硬编码**：内置工具表 `packages/coding-agent/src/tools/index.ts`（`BUILTIN_TOOLS`/`HIDDEN_TOOLS`/`isToolAllowed`，见 `docs/capability-seams.md:9` 锚点）；斜杠命令 `src/slash-commands/builtin-registry.ts`；终端 daemon 面 `src/daemon/services/terminal-service.ts:1-40`（L2 宿主服务 + 头注释缝声明）；provider 解析 `src/daemon/terminal-provider.ts:1-30`（bun-pty/node-pty/auto 三级 seam）；语音面 `packages/desktop-app/src/lib/voice.ts` + `src/components/settings-sections/voice.tsx` + `src/components/composer/voice-setup.tsx`（GUI 持有 STT/TTS 生命周期与设置面）。
- 扩展侧已有**命令式** register* 面：`src/extensibility/extensions/types.ts:1290`（`registerTool`）、`:1403`（`registerMode`）、`:1581`（`registerProvider`）、`:1392`（`registerToolView`）等——但没有「声明式 manifest + 统一装配」层，扩展入口是 JS 模块副作用，内置能力是宿主直挂，**两套装配语法**。
- dsh 参照（真码核实）：`packages/terminal/tool-terminal/src/index.ts:35-56`——`export const name = 'tool-terminal'` / `export const inject = ['terminals','tools','systemPrompt']` / `export const Config: z<Config> = z.object({...})`（schemastery，带 `.default()`/`.min()`/`.max()` 校验），Loader 据三件套完成装配，插件代码零 imperative 查找服务。

### 目标形态

统一装配契约三件套（builtin 插件与 user 插件**同语法**）：

```ts
// 插件入口（builtin 与 user 同形）
export const name = "tool-terminal";            // ① 身份：注册表键、错误码归因、管理页显示
export const inject = ["terminals", "tools"];   // ② 能力依赖：缺依赖 = 结构化拒绝（见 §3）
export const Config = { /* ③ 见下 */ };         // ③ 配置 schema：驱动设置表单 + 类型安全 parse
```

**③ Config 的 schema 选型（设计决策）**：用**自家 settings schema**（现有 settings 键值体系 + 管理页已有的键值渲染），**不引入 schemastery**。理由：
1. 我方已有 settings 覆盖链（mode settings 覆盖 → 会话有效 settings，`presets/resolve.ts`）与 `Config` 的 merge 语义天然同构，引入 schemastery 会多一套并行 schema 方言；
2. dsh 的 schemastery 价值在「schema 驱动表单渲染」，这个渲染器契约（见 §4）与 schema 方言解耦——渲染器吃「声明式字段描述」（type/default/min/max/step/description），我方用 TS interface + 装饰器式常量表即可产出同构描述；
3. 少一个 vendor 依赖，cordis 收编期内控制风险。

字段描述契约（渲染器的输入，§4 复用）：

```ts
interface ConfigFieldDesc {
  key: string;                       // "maxResultBytes"
  type: "boolean" | "number" | "string" | "select" | "path";
  default: unknown;                  // 缺省值（缺席 = 必填）
  min?: number; max?: number; step?: number;
  options?: readonly string[];       // select 用
  description?: string;              // 进管理页表单行 desc（i18n 键）
  restart?: "none" | "session" | "daemon";  // 变更生效域
}
```

### 迁移步骤

1. **M2-2.9 试点期不动**：spike ①（动态插件运行时）先用一个真实 user 扩展验证 Loader/隔离/生命周期/检视四能力，builtin 三件套化等试点报告。
2. **试点通过后第一批**：选「无 GUI 耦合、纯 daemon 面」的内置能力做三件套改写（终端工具集、schedule 等 L2 服务），宿主保留薄适配层（把现有 `DaemonService` 包装为 cordis Service 形状，roadmap §4.3「先包 daemon 服务为 cordis 服务」）。
3. **信任级差异落成数据**：builtin 插件 manifest 带 `trust: "builtin"`（随包分发、不可卸载、升级随版本），user 插件 `trust: "user"`；两者走同一 Loader，差异只在权限面（builtin 可声明宿主级 inject，user 插件不可 inject 宿主私有服务名）。

## 2. 终端首个收编试点

### 现状（文件:行号）

- **daemon 面**：`src/daemon/services/terminal-service.ts`（192 行，L2 宿主服务；桥接表 id → provider handle 为服务内内存态；`terminal.open/input/resize/close` 四个 RPC；terminal-output/terminal-exit 经调用方连接 envelope 推送）；`src/daemon/terminal-provider.ts`（242 行，provider seam：bun-pty 优先 / node-pty 兜底 / auto；manifest 显式声明时严格遵循、不静默回退）。
- **GUI 面**：`packages/desktop-app/src/components/TerminalPanel.tsx`（474 行；2026-09-28 已修为常驻挂载——切会话只折起不卸载，pty 不杀；xterm 主题/allowTransparency 构造器问题已修）。
- **归属判定**：终端是**跨宿主面**——pty 进程持有在 daemon，渲染持有在 GUI，工具面（模型调用）在 daemon。三者生命周期当前都由宿主直管，无任何插件边界。
- dsh 参照（真码核实）：`packages/terminal/terminal/src/index.ts:48-52`（`declare module ... interface Context { terminals: TerminalSessionService }`）、`:105-137`（`Service` 子类 + `registerBackend()`，`DUPLICATE_BACKEND` 结构化错误，effect scope 注册/反注册）；`types.ts` 错误码全集：`DUPLICATE_BACKEND / DUPLICATE_NAME / FOREIGN_SESSION / NO_BACKEND / NO_SESSION / OWNER_NOT_LIVE / SEND_ACTIVE / SERVICE_DISPOSING`。

### 目标形态（owner-scoped registry + backend 接口，不拷 dsh 代码）

```
┌─ builtin 插件 "terminal-core"（daemon 侧）────────────────┐
│  name: "terminal-core"                                     │
│  inject: ["rpc", "settings"]                               │
│  导出 TerminalRegistry（owner-scoped，对应 dsh terminals）  │
│    - registerBackend(type, backend): Disposable            │
│      （DUPLICATE_BACKEND 冲突 → TerminalError 结构化码）     │
│    - open(ownerRef, request) → sessionId                   │
│    - input/resize/signal/close（按 id + owner 鉴权）        │
│    - 输出推送：订阅制，按 owner 连接路由                     │
│  保留现有 envelope seq / 未知 id 语义（terminal-service      │
│  头注释缝声明即本插件的缝声明，原样迁移）                    │
└────────────────────────────────────────────────────────────┘
┌─ builtin 插件 "terminal-provider-bunpty" / "-nodepty" ─────┐
│  各自 registerBackend("bun-pty"|"node-pty", ...)           │
│  provider 三级解析（terminal-provider.ts）收进 provider 插件  │
└────────────────────────────────────────────────────────────┘
┌─ builtin 插件 "tool-terminal"（模型面，对应 dsh 同名插件）───┐
│  name/inject/Config 三件套；inject ["terminals","tools"]    │
│  提供 spawn/send/read/list/signal 工具集                    │
└────────────────────────────────────────────────────────────┘
```

**试点范围边界（哪些进插件、哪些留宿主）**：

| 面 | 归属 | 理由 |
|---|---|---|
| pty 进程持有、backend 注册表、owner 鉴权、输出路由 | **插件**（terminal-core） | dsh 已验证的 owner-scoped registry 形状；宿主只留 RPC 路由薄层 |
| bun-pty/node-pty 具体实现、provider 解析策略 | **插件**（两个 provider 插件） | 可插拔、可独立禁用（§3 禁用兜底场景） |
| 模型面终端工具集 | **插件**（tool-terminal） | 三件套首批受益者，Config（maxResultBytes 等）直接进管理页表单 |
| TerminalPanel xterm 渲染、常驻挂载/折起策略 | **宿主（desktop-app）不动** | GUI 渲染是 Electron 面，不受 daemon cordis 化影响；只消费 RPC 面，RPC 名不变 |
| envelope seq 计数、连接 emit | **宿主保留**（作 inject 能力注入插件） | 与 DaemonServer 共享编号空间是既有契约，不为试点改动 |

### 迁移步骤

1. daemon 服务→cordis 服务薄包装（roadmap §4.3 既定第一步），`TerminalService` 的 `nextSeq/emit/settings` 三个 deps 改由 cordis inject 提供（现有 `TerminalServiceDeps` 形状天然适配）。
2. 把 `terminal-provider.ts` 的 manifest seam 升级为 `registerBackend` 注册表，provider 解析策略不变。
3. 模型面终端工具从 `BUILTIN_TOOLS` 挪进 tool-terminal 插件；`isToolAllowed` 的调用点不变（工具注册表仍是权威，只是登记者从宿主变插件）。
4. 试点验收：加载/隔离/生命周期/检视四能力实测 + 禁用 provider 插件时的结构化降级提示（§3.③）实机走查。

## 3. 回退保护三件套

### ① 加载失败层隔离跳过（不拖垮宿主 + 面域 toast）

- **现状**：扩展加载失败已有面域隔离实践——`extension-artifact-compiler.ts`（collectExtensionSkills/validateExtensionComponents/invokeExtensionRpc，调用点 `services/extension-service.ts:206/427`、`services/marketplace-service.ts:229`、`server.ts:979/1102/1902`、`extensions-center/state-manager.ts:176`）；扩展中心有加载错误面。
- **dsh 参照**：preset 声明插件加载失败只跳过该层（不中断整树装配）；ManagementFailure 结构化错误码由调用方本地化渲染。
- **目标**：插件装配按「层」隔离——单插件 import/装配失败 = 该插件记 `failed`（结构化错误码 + 原因），宿主与其余插件不受影响；失败信息推送到**对应面域**（daemon 面 → 扩展中心错误行；会话内工具调用 → 工具结果内结构化提示），由调用方按错误码本地化，不散装 Error.message。

### ② 兼容性声明与结构化拒绝（版本/peer 区间 + 豁免）

- **dsh 参照（真码核实）**：`packages/boot/app-boot/src/plugin-compatibility.ts`——`evaluatePluginCompatibility()` 在**不 import 插件代码**的前提下读 package.json `peerDependencies`，对 `@deepseek-ai/dsh*` peer 做 semver 区间校验（workspace 协议按运行时版本解析），不兼容产出 `PluginCompatibility { name, version, peers, exempted }`；`exemptions` 数据结构 = `plugin 名@版本 → 可豁免的运行时版本列表`（精确配对，非通配）；`compatibility-preflight.ts` 在组合入口点（profile/include）预检，不污染 Loader。
- **目标形态**（数据结构）：

```ts
interface CompatibilityGate {
  /** 不 import 插件代码的预检结果 */
  status: "compatible" | "incompatible" | "exempted";
  plugin: { name: string; version: string };
  /** 未满足的 peer 区间（仅 MusePi 命名空间 peer 参与判定） */
  unmetPeers: Record<string, string>;
  /** 豁免：精确 "name@version" → 被豁免的运行时版本列表（人工登记，非通配） */
  exemptions: Record<string, readonly string[]>;
  /** 拒绝时的结构化码，调用方本地化渲染 */
  code: "incompatible-version" | "incompatible-peer" | "malformed-manifest";
}
```

- **落点**：预检挂在装配入口（扩展装载 / marketplace 安装 / builtin 插件随版本升级三个入口共用同一判定函数），**先于任何 import**。

### ③ 禁用/卸载插件时的内置能力兜底（不静默失效）

- **场景**：终端 provider 插件被禁用 → 会话内 `terminal.*` 工具调用不得静默消失或裸失败，必须给出**结构化降级提示**（「终端后端已停用，原因：插件 X 被禁用；恢复方式：扩展中心重新启用」）；语音插件禁用 → 输入框语音按钮置灰 + 首用引导改道。
- **目标形态**：工具/能力注册表登记时带 `providerPlugin: string` 归属；插件停用即能力从注册表摘除并广播 `capabilities.changed`，消费面（工具卡、composer 按钮、设置页）按「能力缺席 = 有归因的缺席」渲染，归因信息来自插件管理器的停用记录。
- **迁移步骤**：先做能力归属标注（纯登记字段，无行为变化）→ 再做缺席归因渲染 → 最后才允许禁用 builtin 插件（试点期 builtin 只读不可禁用，兜底主要保护 user 插件场景）。

### 回退保护总迁移序

①先行（现有面域隔离的结构化升级）→ ②随 marketplace 状态机（M2 已闭环）挂预检 → ③随三件套推广逐步生效。

**配置表单渲染器契约（新增组件，本设计稿定义、后续编码实现）**：

```ts
interface ConfigFormRendererProps {
  fields: ConfigFieldDesc[];              // §1 三件套之 Config 展开
  values: Record<string, unknown>;        // 当前生效值（settings 覆盖链结果）
```

## 5. 与既有契约的关系（兼容矩阵）

### 5.1 与能力缝声明（M2.4，`docs/capability-seams.md`）的衔接

**结论：builtin 插件也要缝声明；声明挂在插件入口头注释，capability-seams.md 索引页从「宿主文件锚点」扩展为「宿主文件 + 插件名双锚点」。**

- 现状：九个域的权威锚点都是宿主文件（tools/index.ts、builtin-registry.ts、services/types.ts 等，见 capability-seams.md:5-15）。
- 收编后：三件套化能力的缝声明随插件走（六字段：名称+ns / 输入 / 输出 / 生命周期 / 启停 / 冲突 + 检视入口，格式不变），宿主文件里只剩转发薄层的缝声明。
- 索引页改动：表格增「插件名」列；「触及时顺手补」纪律不变——三件套改写某能力时把它在索引页的锚点从宿主文件改到插件入口，禁止批量回填。

### 5.2 与 AGENTS.md 扩展 HMR 热拔插契约的关系

**结论：增强，不是替代。热拔插契约继续有效，cordis 化把它从「自定义实现」换成「cordis Loader 原生能力 + 我方补丁」。**

- 现有契约（AGENTS.md「Extension HMR」条）：入口文件变更 → daemon watcher 500ms 内广播 `extensions.changed` + 对活跃会话按入口 mtime 对比执行 `reloadExtension`（忙会话挂起、`agent_end` 补做）+ 会话内事件 `extensions.reloaded`；子模块改动不热生效（需 touch 入口）；内存态不迁移、在途副作用不回收、handler 重载 ~ms 双跑窗口。
- cordis Loader 原生提供依赖图级 HMR（子模块变更也能精确失效）与作用域 dispose——试点 spike ① 的实测数据决定吸收深度：
  - 若 Loader HMR 实测可靠 → 500ms 广播、mtime 对比、双跑窗口全部由 Loader 接管，**对外事件契约不变**（`extensions.changed` / `extensions.reloaded` 事件名与 payload 不变，GUI 无感），AGENTS.md 该条改写为「实现由 cordis Loader 提供，契约如旧」；
  - 若不可靠 → 保留现有 watcher 实现，cordis 只负责冷装配，热路径不动。
- 无论哪种，**忙会话挂起 / agent_end 补做**是 MusePi 会话语义，cordis 没有等价物，必须保留为我方补丁层。

### 5.3 与 roadmap §4.3 cordis v3、M2 宿主分层的先后关系

**结论：本批设计依赖试点，不阻塞试点；P2（cordis 适配进展）的先行项明确如下。**

- 先后序：M2-2.9 试点（vendor + 两 spike：①动态插件运行时对标 cordis-host-runner、②mode→每会话 Context fork 组合）→ 试点报告 → 收编决策（ADR）→ **本批三件套/终端试点/回退保护进入排期**。本设计稿全部内容以「试点通过」为前提，试点不通过则维持双轨、本稿归档。
