## 0.  TL;DR

- **ZCode**（2026-09-21 开源，Apache 2.0）的最大价值不在 UI 代码而在**会话消息的语义模型**：v4「行协议 + 只读投影 store + 轮渲染单元」三件套，直接对应我们"会话消息的显示和加载渲染"短板。吸收语义，不重写 wire 协议。

## 3. 参考仓库吸收分析

### 3.1 ZCode（zcode/）—— 会话消息语义

ZCode 是"AI 编程工作台"（Electron 桌面 + Web + CLI 一体，pnpm/Node 24）。与本仓关系：同为 agent 客户端，**消息渲染语义可直接吸收**；底座不同（它的协议是 zcode-protocol-v4，我们是 collab-proto），吸收**语义而非协议**。

**核心三件套**（`zcode/packages/ui/src/v4/`）：

1. **行协议 + 只读投影 store**（`conversationProjectionStore.ts`）
   - 会话 = `ConversationRow[]`（kind: `assistantText` / `reasoning` / `toolCall` / `subagent` / `userInput` / `turnHeader` / `timelineMarker` / `hookInvocation`），唯一写入方是订阅推送，UI 只读。
   - 三条纪律：snapshot 整体替换绝不 merge；delta 帧仅在 `frame.fromSeq === snapshot.seq` 衔接时 apply，**断档不猜不缓存**，携水位重订阅由服务端裁决 resume/snapshot；optimistic overlay 只用于 pending 命令展示，不产生会话事实。
   - 附带语义：runtime 回收（换代）时的有界退避重订（250/1000/3000ms）、ACK 后 2s 权威投影宽限期。
2. **轮渲染单元**（`conversationTurnRenderUnits.ts`）
   - `ConversationTurnRenderUnit`：turnId 聚合 —— header、可见 user inputs、assistant work rows、**workSegments**（原始输入与每条 accepted guide 各成一个独立视觉工作段）、flowItems（同轮内 user/assistant 可见交错顺序）、tail rows、hookInvocations（不进折叠）、latestAssistantTextRow（fork/retry/preview 只挂这段）。
   - 折叠边界读 workSegments 而非平铺行列表；browser 自动轮尾截图等"轮尾特殊行"有一等位置。
3. **加载可见性规则**（`chatLoadingVisibility.ts`）
   - 权限确认、AskUserQuestion 在等待用户时**禁止显示 loading**（弹窗/问答卡已是唯一进度反馈）；`compact` / `goalVerifier` 活跃时同样抑制。这是我们完全没有的集中语义。
   - 配套：`timelineScrollAnchor.ts` + `timelineRowHeightCache.ts`（滚动锚定/行高缓存）、`conversationTimelineLiveTail.ts`（live tail）、`SessionDataLayer`（租赁式会话数据层）。

**吸收策略（M1）**：把三件套语义映射到 guest-client Transcript 层——
- (a) 在 transcript 归一化层引入"轮渲染单元"中间表示（不改 wire 协议，entries → render units 的纯函数，可测）；
- (b) 抽出集中式 loading 可见性判定（对齐现有 ApprovalCard/AskCard/compact 事件）；
- (c) 滚动锚定 + 行高缓存补进 Transcript；
- (d) 长会话加载引入"窗口化渲染/水位重订阅"纪律（我们 daemon 已有 entries 分页，缺客户端断档纪律）。
- 代码可直接借鉴（Apache 2.0），注意保留许可证头。ZCode 其余吸收项走 `zcode-absorption-todos.md`。

### 3.2 deepseek-harness（deepseek-harness/）—— 插件化语义与 cordis 参照系

dsh 已全部 cordis 化：每个包是 cordis 插件，以 `ctx.*` 服务组合（`packages/` 下 63 包，1902 个文件 import cordis，vendor cordis 4.0.4）。注意 **dsh 不是"双核"——cordis 是它的唯一组合核**，dsh 的一切（含 agent 运行时）都是 cordis Context 上的插件。对我们，dsh 的价值是**"插件化该长什么样"的完整参照系**：对象模型、状态机、每会话组合都能对标；框架本身是否采用见 §4.3 定案。

**0.1.7 增量要点（2026-09-25 基线更新）**：

1. **官方桌面客户端发布**（`apps/desktop` + `apps/web` + `packages/client`/`host` 组）：Electron shell 内嵌完整 dsh Web 应用——RunAsNode 子进程拉起 profile runner，渲染端加载 `dsh-app://app/`，HTTP 请求转发给带鉴权的 Web Host，WS 流仅主窗口携带凭证；配套 single-instance、托盘（单击聚焦）、关闭隐藏不退出 + 退出前任务检查（问 Host"会中断什么"再弹确认）、强更/欢迎窗口、快捷键服务、嵌入式平台文档（WebContentsView 分区隔离）。⇒ 这是小袁总"daemon 改造参考 kimicode/dsh/zcode"的直接对标物：**壳与宿主分离**（Electron 只做壳/转发/生命周期，agent 运行在 Node host 子进程）比我们"单进程 daemon + WS"更接近可组合方向，M2 daemon/宿主分层设计时逐条对照。
2. **能力族成型**（`packages/` 按族分组，均带 `docs/subsystems/*.md` 子系统文档）：除已有的 preset/skill/hooks/subagent 外，新增 **goal**（会话级持久目标，跨重启/续跑）、**plan**（plan mode：先探索设计后执行）、**schedule**（Host 级定时提醒，跨重启存活）、**workflow**（模型编排脚本扇出 subagent）、**deliverables**（轮次交付物记录为会话事件）、**document**（Office→PDF 转换服务）、**interaction**（slash 命令/一次性审批/权限预设/问答缝）。⇒ 与我们 mode/preset 未接线、能力中心、todo 面板的对标面扩大，吸收分析按族逐个进 M2–M4。
3. **preset 语义升级**（`packages/preset/`）：`agent-preset` 直接在普通 Cordis YAML 配置里声明预设（`id` + `plugins` 子插件条目列表 + 元数据），`agent-preset-registry` 管选择/修订保留/profile 编辑（`ctx.agentPresets`），`agent-presets` 是内置预设集，`persona` 是可组合行。即**预设 = 声明式插件组合清单，不再是"目录 + agent.cordis.yml"的隐式约定**；会话选定修订后，该 agent 只见所选修订的 tools/prompts/skills。⇒ 我们 mode 的"会话组合"升级方向被进一步确认（见下 1）。

**值得吸收的对象与语义**：

1. **preset = 每会话 agent 组合**（`packages/preset/`，0.1.7 语义见上"增量要点 3"）：预设 = 声明式插件组合清单（Cordis YAML `id` + `plugins` 子插件条目），registry 管选择/修订保留/profile 编辑，persona 是可组合的行（换身份不只换工具）。核心技术手段是 **cordis 的 Context fork**——每个 agent 会话一个 fork 出的作用域，preset 的插件只挂进那个作用域。⇒ 我们的 mode 已有 extends/promptComplete/settings 覆盖（`resolve.ts`），**缺的正是"按会话组合 agent"的挂载执行面**——0.5.0 把 mode 从"prompt 覆盖"升级为"会话组合"（工具白名单、扩展集、persona、模型角色一并切换）。
2. **plugin-manager**（`packages/boot/plugin-manager/`）：profile bundles（`dsh.profile.bundles` 有序列表 = 配置优先级）、`cordis.patch.yml` 增量覆盖层（toggle 只写 disabled）、**安装状态机**（inspect → installing → cancelling → applying，requestId 可取消，失败恢复 package.json+lockfile，pnpm 11 构建脚本批准流）。⇒ 我们的 marketplace 安装是"clone+symlink+lock"（`docs/marketplace.md`），**缺安装状态机与失败恢复叙事**，M2 吸收。
3. **hmr**（`packages/boot/hmr/`）：插件源码与 profile 配置变更共享一个重载队列（模块替换 / Include 刷新 / 管理写操作），`ctx.hmr` 事件外露。⇒ 我们扩展的热重载目前是"手动重启生效"，M2 远期项对齐。
4. **extensions 组**（`packages/extensions/`）：`tool-cordis`（运行时发现工具）、`cordis-host-runner`/`cordis-client-runner`（host 半沙箱生命周期 + browser 半动态求值，`ctx.cordisInspect` 检视注册表）、`ui-cordis`（生命周期卡片）。⇒ "agent 自举地检视/装配插件"的元能力，M2-2.9 cordis 试点的直接对标物。
5. **agent-team**（`packages/experimental/agent-team/`，dsh 官方）：TeamMemberSnapshot（identity/mailbox/任务/共享检出）。workdsh 的"专家团"交互（§3.4）正是架在它上面。⇒ 我们已有 swarm/agent-hub（TUI），M4 对齐对象模型。

### 3.3 open-design（open-design/）—— design 模式的产品形态（六面全量吸收）

## 4. 关键决策

### 4.1 会话消息渲染：吸收 ZCode 语义，不改 wire 协议

guest-client 的 collab-proto 不动；在 transcript 归一化层与 Transcript 组件之间插入"轮渲染单元"中间表示 + 集中 loading 可见性 + 滚动锚定。理由：wire 协议改动牵动 daemon/TUI/mobile 三端，0.5.0 窗口不值得；语义层收益 80% 在客户端。

### 4.2 插件化：补登记与展示分层，吸收 dsh 插件语义，0.5.0 不换组合底座

- **登记补全**：把 bundled skills、tool-render 工具、magic keywords、内置 hooks、主题包等登记进 `BUILTIN_EXTENSIONS`（`builtin-registry.ts:30` 加行即可，机制已备），全部带"内置·只读·可禁用"徽章；native provider 进 provider tab（去掉 TUI/GUI 的 skip-native 特例）。
- **语义对齐**：marketplace 安装补 dsh 式状态机（inspect/installing/cancelling/applying + 失败恢复 + 构建脚本批准）；扩展 enable/disable 改"patch 覆盖层"语义（只写增量，不物理改插件）。
- **能力缝**：对齐 dsh capability seams 文档纪律——每个内置能力声明自己的接缝（输入/输出/生命周期），供 agent 检视。
- 以上各项**框架无关**：无论 §4.3 的 cordis 收编走到哪一步，登记/展示/状态机都是 UI 与注册表层语义，照做不浪费；收编后它们自然映射（注册表→bundle 清单、patch 层→cordis.patch.yml、状态机→plugin-manager 等价物）。

### 4.3 cordis：定案 v3（2026-09-21 三审）——长期主义"用"，渐进收编，**收编约束已解除**

**事实**：cordis（`vendor/cordis`，`@deepseek-ai/cordis` 4.0.4（0.1.7 基线），MIT，核心 src 仅 117KB/9 文件）是 Koishi 生态的 TS 插件/DI 框架（Context/Service/注入/作用域 fork/生命周期/配置驱动加载/HMR）。dsh 里 1902 个文件 import 它——**dsh 不是"双核"，cordis 是它的唯一组合核**，dsh 的一切（含 agent 运行时）都是 cordis Context 上的插件。小袁总指出的两点都成立：**cordis 与自有运行时不互斥**（它只是个库，局部共存没有障碍）；**"服务话语也是可以改的"**（一次性迁移成本，非长期约束）。

**关键背景修正（三审确认）**：MusePi 自 **2026-08-17 起已是独立上游**（`UPSTREAM.md` 归档：oh-my-pi 等一律视为参考吸收来源，无版本对齐义务；包名已改 `@musepi/pi-*`，版本线独立 0.4.x）。小袁总 2026-09-21 确认：master 分支可删、当前基本为自有设计。**这意味着 cordis 收编在 v2 中的决定性障碍（fork 同步约束）已不存在。**

**为什么长期判断是"用"**：

1. **0.5.0 路线图自己在逐项重新发明 cordis**：mode→每会话组合（dsh 用 Context fork 实现 preset 挂载）、patch 覆盖层、bundle、动态插件运行时（host 半沙箱+inspect）、安装状态机、HMR——这些加起来正是 cordis 的 Loader/patch/scope/HMR 能力集。逐项自研 = 长期维护一组比 cordis 更窄更弱的等价物。
2. **daemon 确实未必最优**：`server.ts` 已 10,336 行、巨型 RPC switch；单进程多会话 + 会话级组合（mode 挂载、连接器隔离、专家组合）天然是**作用域 DI** 的形状，正是 cordis Context fork 的强项。
3. **体量与许可成本可忽略**：MIT、117KB，dsh 已验证 vendor 路线可行。

**为什么仍然"渐进"而不是 0.5.0 直接换底座**（剩下的唯一理由）：

- **有状态 daemon 的大爆炸风险与上游无关**：`DaemonSessionHost` 是会话生命周期编排器（历史快照、再激活、WebSocket 协议），整体重写 = 高回归风险，strangler-fig 是唯一负责任的路径。
- **过渡期双话语成本**：需用收编边界框住（见下）。

**三阶段定案（v3：收编不再绑定 0.6.0 周期）**：

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| **0.5.0 试点**（M2-2.9） | vendor `@deepseek-ai/cordis` 到 `musepi-omp/vendor/cordis`；两个 spike：①动态插件运行时原型（对标 dsh `cordis-host-runner`：host 半沙箱 + inspect 注册表，挂载我们一种真实扩展）；②mode→每会话挂载（一个会话 fork Context、按 preset 组合工具/prompt/扩展的最小闭环） | 试点报告：加载/隔离/生命周期/检视四能力实测 + spike ②证明会话作用域组合可行 |
| **收编决策（试点成功后立即）** | 依试点报告决策：通过则立刻启动 strangler-fig，**不等到 0.6.0**；不通过则维持双轨（试点面保留 cordis，主干不变），损失仅 vendor 117KB | 决策记录（ADR） |
| **收编执行（若通过）** | daemon 宿主 cordis 化：先包 daemon 服务为 cordis 服务（session manager 第一个），再迁扩展装载为 Loader，WS 协议全程不动；每阶段可回滚 | 分阶段验收 |

**收编边界（代码卫生约束，不再是同步硬约束）**：cordis 依赖只进 daemon 宿主层与新增包，核心领域包（agent/ai/wire/sdk 等）保持零 cordis 依赖——这是清晰分层的纪律，便于回滚与测试，而非上游同步所迫。

### 4.4 design 模式：从 prompt 预设升级为创作面——六面全量吸收 open-design（已定案）

M3 给 design 模式接 open-design 式创作面，**六面全量对标：Prototype / Live Artifact / Deck / Template / Media(Image/Video/Audio) / Other**——直接吸收其 tab 结构、project metadata（kind/intent/fidelity/platform/design-system）、skill-mode 路由（daemon 侧解析归一）、design-templates 模板目录，再叠加我们的改动（中文工作流、`gui-design.md` token 视觉、与四预设的融合）。**不做"语义等价"的缩水重实现**；吸收中出现与我们底座冲突处（如它的 ACP 运行时），改的是适配层而非删减功能。

daemon 侧把 `artifact.manifest.json` 从 prompt 约定升级为校验+索引（FilePane/预览面板按 manifest 识别产物）。

### 4.5 专家团与连接器：按 workdsh 对象模型自建

专家 = 身份 + 技能修订引用 + 受控输入模板；连接器 = 每会话选择的 MCP 实例 + 凭据托管 + 可见 chip。架在我们现有 swarm/agent-hub 与 MCP runtime 上，不引入 dsh agent-team 的实现。

### 4.6 扩展隔离边界：API façade ≠ 进程隔离（2026-10-04 核查定案）

**上游现状（`dsh-v0.2.1-alpha.1` 核实）**：沙箱是三层，各管不同对象，只有一层是真隔离。

| 层 | 机制 | 管谁 | 真隔离 |
|---|---|---|---|
| `cordis-host-runner/sandbox.ts` | `node:vm` + API traps | 模型生成的插件 host 半体 | **否**——其文件头自述 "not containment: host-realm helper functions remain an escape route" |
| PTC runtime | 独立进程（host ↔ guest，JSON 回调） | 工作流脚本 | 是 |
| `packages/sandbox/` | **OS 级：Landlock / bubblewrap**，跨 Linux/macOS/Windows | **命令及其后代**（bash / terminal / fs 工具面），按会话 mode（`read-only` / `workspace-write` / `danger-full-access`） | 是 |

**我们的定案：扩展不做进程隔离。** 三条理由：

1. **信任模型不同。** 上游那层 vm 是为**模型现场生成的代码字符串**准备的；我们装载的是用户自己安装的扩展目录，信任级别等同于 agent 自身配置的 `extensions` 字段。上游自己也没隔离扩展——扩展同样在宿主进程内全权限运行，那层 vm 从来不是为它设的。
2. **`node:vm` 买不到隔离。** 上游已明写 VM 不是边界、真要 confine 靠进程。照抄 vm 只会拿到虚假安全感。
3. **代价与收益不成比例。** `ExtensionAPI` 是同步语义且持有宿主对象引用（session / eventBus / runtime），跨进程要整体改异步 + 序列化——这是重写扩展契约，不是加一层壳。

**与 M2-2.9 出口标准的对账**：§4.3 试点行写的"加载/**隔离**/生命周期/检视四能力实测"，其中"隔离"一项的实测结论是**不适用且刻意不做**。`cordis-dynamic-extensions.ts` 的能力缝声明与文件头已改为如实记录"API 面是 façade、进程面与 daemon 共享"。试点行的历史表述保留不改，以本节为准。

**真正的缺口在别处**：我们缺的是第三层（工具执行面的会话级 mode + OS 级 confinement），不是扩展隔离。前者是**产品功能决策**（要不要给用户一个模式开关），不是架构对齐；且跨平台 OS 级隔离在 Windows 上最难做对（上游只有 landlock / bwrap 两个 Linux 专属 e2e，Windows 路径未核实）。优先级低于扩展生态本身，不进 0.5.0。

## 9. 进度记录
- **2026-10-08 · profiling：唯一的形状超标项是 transcript-compose 的 depth-linear ratio，其余 bench 或健康或已腐化**：按「先 profiling 再动手」跑仓库已有的 4 个 bench。`streaming-throughput` 0.0923 ms/step（健康）；`session-tree-nav.bench.ts` **已损坏**（引用的 `buildSessionContext` 在 session-manager 里不存在，refactor 后 bench 没跟上，**待修**）；唯一超标的是 `transcript-compose`。
  - **实测**（width 100）：`ratio(N5000/N500) median = 2.975`，而该 bench 自己写的目标是 `ratio ≤ 1.3`——**超标 2.3 倍**。但另一条目标 `N5000 p95 < 10ms` 达标得很宽：**p95 = 1.97ms**。
  - **插桩归因**（把一个 tick 拆成 `updateContent` 与 `render` 分别计时）：`updateContent` **恒定**（N=500 时 0.0097ms，N=5000 时 0.0053ms，与历史深度无关）；`render` **线性增长**（0.2176ms → 0.6390ms，3 倍）。**成本全在 render**。
  - **根因定位到 `transcript-container.ts` 的三处每-tick 全量遍历**（与「已提交历史不再重组」的设计意图相悖）：① `:467` seal 扫描（依赖 `#committedRows` 才 break）；② `:483` live-block 扫描（要找尾部那个未 final 的块，**必须走过全部 5000 个已 final 的块**才 break）；③ `:519` 主组装循环——即使每块可完全复用，仍要构造 `BlockSegment` 对象 + 比较 6 个字段 + 算 contribution，**5000 × 每 tick ≈ 5 万次操作**。
