## 2. 重点条目详析（高相关性）

### 2.1 重复工具调用熔断阶梯（`a54e6f6a9`）——高，小工作量，建议尽快吸收

**机制**：A 的 `toolDedupeService`（`packages/agent-core-v2/src/agent/toolDedupe/toolDedupeService.ts`）对**连续相同的工具调用**维护 streak：≥ 阈值1 注入一层 system-reminder（r1，提醒改变方式）；随 streak 增长升到 r2（带重复次数）、r3（最后警告）；达到 FORCE_STOP 阈值后直接把工具结果替换为强制停止结果并终止本轮。**同一步内的重复调用去重恒开**（不提供开关）。环境开关 `KIMI_CODE_REPEAT_BREAKER=0` 只关闭"跨步的阶梯提醒+强制停止"，用于调试模型行为。

**与我方差异**：我们的 `ToolCallLoopGuard`（`session/stream-guards.ts:272-326`）是**跨 turn** 的循环防护且只有"超阈值注入 redirect prompt"一档；A 的阶梯在**单轮内逐步升级**且最终能强制止损，粒度细一档。吸收点：① 在 stream-guards 里给工具调用加同轮 streak 阶梯（reminder 文案走 `prompts/` 静态 md 纪律）；② 补同一步内去重；③ 加 `MUSEPI_REPEAT_BREAKER` 环境开关。架构上无需新依赖，挂现有 guard 管线即可。

### 2.2 compaction 三连（`775a6c35d` / `88a7d932f` / `f12d59e08`）——高，中工作量

- **重试上限可配**：A 把 `MAX_COMPACTION_RETRY_ATTEMPTS` 变成 `loop_control.compaction_max_attempts`（默认 5），覆盖可重试生成错误与空/截断响应收缩两条路径，并修了 shrink 次数无界与 retry delay 即时计算的 review 问题。我方 `compaction.ts:711-729` 是硬编码 10×3；加 settings 键即可。
- **预收缩**：A 在压缩请求前把 history **先收缩到 effective model window**，避免"压缩请求本身超窗→失败→再压缩"的死循环。我方只 trim summary 输入（`trimRemoteCompactionInputToContextWindow`），语义不同——input trim 保的是单次请求能发出去，history pre-shrink 保的是压缩链路能收敛。两者互补，都要。
- **恢复锚**：A 的压缩续跑以**最新用户消息**为锚（continuation anchor 随 compaction record 持久化、重放无条件带锚），保证压缩后恢复对话时上下文语义连贯。我方只有 token 计量锚与 summaryAnchorId。这对我方 auto-compact 后的续跑质量是直接可感的改进。

### 2.3 会话恢复/索引性能技术束（`5108cad9b`）——高，中工作量，直接喂 P2⑧/M1.11 后续

A 的手段清单与我方 M1.11 实测痛点（恢复 parse ~470ms、全量派生 ~200ms、371MB 常驻）逐条对应：单遍 wire restore（我方 journal catchup 已是流式，但历史快照构建仍是全量）、**延迟 immer freeze**（重放期间不做不可变封装，回放完一次性定稿）、并发任务文件读、窗口化 tail-read 重放折叠（先渲染尾部、历史折叠与引擎恢复重叠进行）、`session_index.jsonl` 增量压缩 + dir-mtime 新鲜度信号。落地顺序建议：先 tail 优先恢复（配合 M1.11 虚拟化已就位的渲染端），后索引压缩。

### 2.4 NotifyUser 工具 + 轮中更新面板（`f6a9c39e2`）——高产品价值，大工作量

**机制**：新增一个实验性工具 `notify_user`，**宿主在 bootstrap 时声明 `update_panel` UI 能力才下发**（能力协商，不是硬编码）；system prompt 里"主动汇报进展"的指引只在工具激活时注入。TUI 侧：本轮更新渲染在编辑器上方面板（堆叠、8 行窗口、Ctrl+N 回翻），下一轮清空；transcript 里保留单行卡片。配套 `0b6751129` 对长时间无输出的 agent 注入 nudge 提醒其发 NotifyUser。

**对我方**：桌面 GUI 已有 WorkStatusOrb、桌宠权威会话卡片（PetSessionCard），但**缺"agent 主动发中间进展"的一等通道**——现在进展只能从 toolName/流式文本推演。若吸收，wire 协议（collab-proto）要加一种 entry 类型或复用 custom_message，TUI/GUI/移动三端渲染；建议 M4 评估时与专家（受控输入模板的进度回报）合并设计，避免做两遍。

### 2.5 write-pr / review-pr 技能（`75d6767e0`）——高，立即可做

## 4. 一页结论

205 提交中约 50 条是 ci/chore/release 可跳过，约 60 条是 agent-core-v2 内部重构不需对齐。**真正值得动手的Top 5**：

1. **repeat breaker 阶梯**（小工作量，agent 运行时直接加固）；
2. **compaction 三连**（重试可配 + 预收缩 + 恢复锚，压缩质量硬提升）；
3. **会话恢复性能技术束**（直接喂 M1.11 后续/P2⑧）；
4. **write-pr/review-pr 技能**（半天工作量，M4 能力中心即有内容）；
5. **审计清单**（steering 7 例 + swarm 冷恢复 3 边界 + 存储健壮性簇，均为 A 侧真实故障换来的边界）。

**M6 前置决策**：pi-tui re-baseline（v0.85.1）是否执行，决定 TUI 交互特性（折叠点击/全屏布局/跳底指示器）是"移植"还是"重造"。
