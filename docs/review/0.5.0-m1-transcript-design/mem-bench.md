# M1.11 Transcript 虚拟化 mem-bench 基线报告

> 实测日期：2026-09-22 · 环境：Windows 11 + Bun 1.3.14 (x64)
> 脚本：`packages/client-core/bench/transcript-mem.bench.ts`（`bun run bench/transcript-mem.bench.ts` 可复现）
> 数据：可复现伪随机合成会话，每轮 = 1 用户消息 + 4~8 组 toolCall/toolResult（输出 0.3~20KB）+ 1 assistant 文本

## 背景

当前 `Transcript.tsx` 是**全量挂载、hidden=0、无窗口截断**（:80 注释明确记录 WINDOW_INITIAL 截断已移除）。
用户反馈（路线图 M1.11 动机）：轮次多时侧边时间轴显示不全、向上滚动加载慢、恢复会话慢。

## 实测数据

| 轮次 | 条目数 | wire 载荷 | 恢复(parse) | 派生-全量 | 派生-窗口 | 数据量-全量 | 数据量-窗口 |
|---|---|---|---|---|---|---|---|
| 300 | 4,214 | 19.44 MB | 50 ms | 28 ms | 0.6 ms | 37 MB | 2.9 MB |
| 1,000 | 14,054 | 65.30 MB | 149 ms | 35 ms | 0.1 ms | 125 MB | 2.6 MB |
| 3,000 | 41,820 | 194.51 MB | 473 ms | 198 ms | 0.1 ms | 371 MB | 2.6 MB |

- **派生-全量**：`buildRoundFolds + buildTurnRenderUnits + hasPendingAsk + lastUserMessageTs` 全量跑一遍的中位数——即 entries 每次变更时 React useMemo 链的重算成本。
- **派生-窗口**：仅对尾部 300 条窗口跑同一组派生。**不随历史深度增长**（0.1ms 平线）。
- **数据量**：entries 全字符串 UTF-16 字节总量（内存压力代理；JSC 的 rss 受 GC 页归还影响波动 ±400MB，不可用；派生结构 folds/units 实测堆增量≈0，只是索引投影）。
- 窗口条目数固定为尾部 300 条，故窗口列在 300/1000/3000 轮下基本持平——**这正是虚拟化的收益曲线**。

## 结论

1. **派生成本**：全量派生在 3,000 轮时约 200ms/次，且随历史线性增长；窗口派生恒定 ~0.1ms。**收益 ≈ 2000 倍**，且随会话变长继续扩大。
2. **恢复成本**：全量 wire 载荷 194MB → parse ~470ms（这还只是 JS 侧；真实链路还要算 daemon 读盘 + WebSocket 传输 + JSON 重序列化）。窗口形态下载荷可降到 ~2.6MB 级。
3. **常驻内存**：全量 entries 字符串数据 371MB vs 窗口 2.6MB，**~140 倍**差距。注意当前实现里 entries 全量常驻 + 全部行挂载 DOM，实际内存压力比本表的「数据量」列更大（DOM 节点成本未计入，需在浏览器侧另行测量）。
4. **判定：需要虚拟化**（窗口化 + 前缀分页按需加载 + 滚动回溯 backfill）。0.5.0 M1.11 成立。

## 实现要点（后续施工依据）

- 尾部窗口 W=300 条为派生与渲染基准；前缀以「分页 backfill」形式按需拉取（sentinel 已存在于 Transcript.tsx:1552，原窗口机制的遗址可复用）。
- 派生函数均已接受 `readonly SessionEntry[]`，窗口切片可直接喂入，无需改签名。
- 侧边时间轴/导航条应按**全量 entries 的元数据**（轮次边界索引）渲染，而非可见窗口——元数据索引体积小（每轮几个数字），可全量持有，解决「导航条显示不全」问题。
- 恢复链路优化：daemon 侧支持分页 wire 载荷（tail 优先），客户端首屏只解析窗口。
