# 0.5.0 会话轮渲染虚拟化 · zcode 对照稿

> 状态：评审稿（2026-09-22）· 依据：zcode 开源版（本地 `zcode/` @ 872ad96 "feat: open source" 2026-09-21）× musepi-omp 当前 main
> 动机（小袁总原话）：分页导致侧边导航条无法显示全量轮次、往上翻加载慢、恢复会话慢。
> 结论先行：**我们的痛点 zcode 全部没有**（它是只读调试侧栏，无流式、无历史分页、无滚动恢复），但**它的四层性能防线（调用级虚拟化 / 收起即卸载 / 高度裁剪 / 源头截断）正是我们所缺的**；直接照搬不适用，按 §8 规划分三期吸收。

---

## 1. 架构总览：两种完全不同的产品形态

| 维度 | zcode ModelTrajectory | MusePi Transcript |
|---|---|---|
| 产品定位 | **只读调试侧栏**：把 model-io JSONL 渲染成调用轨迹 | **活会话界面**：流式输出、分支编辑、轮次折叠、跟滚 |
| 数据形态 | 文件型、**快照式一次性拉取**（RPC 全量，手动 refresh） | 长连接、**增量推送**（daemon tail 200 + 游标分页 500/页） |
| 数据来源 | `~/.zcode/cli/*/model-io-<sid>.jsonl` 尾部 32MiB | daemon 物化视图（MaterializedView） |
| 虚拟化 | `@tanstack/react-virtual`，**调用卡级** | **无**——M1.11 尾部窗口（首 800 条）只增不减 |
| 收起语义 | **unmount**（Radix Collapsible 无 forceMount） | **保持挂载压高度**（fold-slot / useCollapseHeight） |
| 流式 | 不存在 | rAF 帧合并 + 增量 markdown 解析 + 异步高亮 |
| 历史回溯 | **不做**（源头截断 + "已截断"提示行） | 上翻分页（hasMore/beforeId 游标） |

**一句话**：zcode 是"把已经死了的调用记录优雅地展示出来"，我们是"让活着的会话长流畅地跑"。它防的是**静态长列表的内存**，我们防的还得加上**流式每帧成本**——后者 zcode 没有经验可抄，是我们自己的主战场（§5）。

## 2. 展开/卸载状态机对照

### 2.1 zcode

- 三级状态源：组件本地 `useState`（**默认展开**）→ `expansionRegistry.overrides`（用户手动覆盖）→ `expansionCommands`（按角色 system/user/reasoning/assistant/tool-call/tool-result 的全局展开/收起命令，带单调 version，`ModelTrajectoryExpansion.ts:11-24`）。
- **收起 = React 子树 unmount**（`collapsible.tsx:14-47` 是 Radix 薄封装、无 `forceMount`，Presence 语义），300ms 高度动画结束后释放 DOM；数据仍在内存。
- 展开状态**纯内存**，切会话/重启不保留；搜索命中会强制展开目标（`open = userOpen || searchRevealed`）。
- 无懒加载——数据首次 RPC 已全量在手，展开只是显示。

### 2.2 我们

- 轮次折叠 `roundFoldOpen: ReadonlySet<number>` 存"与默认的偏差"（`Transcript.tsx:1175` + `round-collapse.ts`）；思考块/工具卡各自本地 state + `useCollapseHeight`（`use-collapse.ts:29-82`）。
- **收起不卸载**：hidden-span 收进 `.tr-fold-slot`（高度 0，注释明确为双向动画保持挂载，`Transcript.tsx:1715-1731`）；思考块 body 保持挂载（`use-collapse.ts:63`）；工具卡 collapseWhenDone 同理。
- 这是我们**液态玻璃动效哲学**（一镜到底、双向动画）的直接代价：DOM 节点只增不减。

### 2.3 对照结论

| | zcode | 我们 | 取舍 |
|---|---|---|---|
| 卸载时机 | 收起即 unmount | 永不卸载 | **不照搬 zcode**（动效是产品基因）；改"动画完成后远端卸载"（§8-P0③） |
| 默认态 | 默认展开（防线靠外层虚拟化） | 轮次默认折叠 | 我们已更好 |
| 角色级批量展开/收起 | 有（expansionCommands） | 无 | **吸收**（P1，配合搜索很好用） |
| 状态持久化 | 无 | 无 | 保持（内存态合理） |

## 3. 虚拟化/窗口化对照（核心章）

### 3.1 zcode：真虚拟化，但单位是"调用卡"

```ts
// ModelTrajectoryTimeline.tsx:31-48
const virtualizer = useVirtualizer({
  count: items.length,
  getScrollElement: () => scrollContainerRef.current,
  getItemKey: (index) => items[index]?.key ?? index,
  estimateSize: () => 240,
  overscan: 3,
});
// 渲染 = 视口窗口 + 上下 spacer；行高 virtualizer.measureElement 动态实测
```

- 虚拟化单位 = **一次模型调用（CallCard）**，卡内消息行不做二次窗口化。
- 特意**不用 Radix ScrollArea**（display:table 内容层会让长轨迹参与异常宽度计算，`ModelTrajectoryPane.tsx:294-295`），用原生 `overflow-y-auto`。
- 搜索期间显式关闭滚动锚定修正（`shouldAdjustScrollPositionOnItemSizeChange = () => !searchQuery`，`:38-40`），命中定位走 Call 级 `scrollToIndex(center)` → `measure()` → 文本级 Range 滚动两阶段。

### 3.2 我们：窗口化挂载，三条硬伤

M1.11 渲染窗口（`Transcript.tsx:80-92`，42k 条全量 derive 实测 200ms/帧的教训）：

- `hidden = max(0, entries.length - renderWindow)`，只渲染尾部 slice；**窗口只增不减**——`setRenderWindow(w => w + 600)`（`:1352`）、jump 直接 `setRenderWindow(entries.length - idx)`（`:1406`），无向下回收。
- **未挂载行无占位 spacer**（顶部 sentinel 注释"paging trigger only, never a spacer — hidden history is not a thing any more"，`Transcript.tsx:1639-1641`）——滚动条高度不代表真实内容，虚拟滚动不可能，只能"翻到哪扩到哪"。
- 顶部 IntersectionObserver（rootMargin 1200px 前瞻，`Transcript.tsx:1331-1370`）同时触发数据分页 + 窗口扩展。

**硬伤**：上翻到底一次 ⇒ 全部已加载历史永久挂载；jump 到早期轮次一次扩窗上万行。这就是"往上翻加载慢"的第一因。

### 3.3 对照结论

| 机制 | zcode | 我们 | 吸收判定 |
|---|---|---|---|
| 虚拟化库 | tanstack virtual，调用卡级 | 无 | **吸收**：entry 级虚拟化（我们 entry ≈ zcode CallCard 内消息行，粒度天然更细） |
| 行高 | estimateSize 240 + measureElement 实测 | —（全量 DOM 不需要） | 沿用 zcode 实测方案，fold 开合走 measure 重测 |
| spacer | 上下 spacer，滚动条真实 | 无 spacer | **必须补**，这是虚拟化的前提 |
| 滚动条语义 | 真实总高 | 假高度（窗口） | 修复后 TurnRail 全量轮次定位可直接 scrollToIndex |
| 外部滚动容器 | 自带容器 | scroller 是 ChatView 的 `.gui-transcript`（`Transcript.tsx:1215-1223` 用 closest 解析） | tanstack 支持 getScrollElement 外挂，**架构兼容** |
| 跟滚状态机 | 无（静态） | M1.3 程序化/用户滚动意图机（`:1420-1499`） | 保留，与虚拟化正交 |
| 搜索定位 | scrollToIndex + 文本 Range | 无会话内搜索 | P1 再做 |

## 4. 数据流与分页对照

### 4.1 zcode：四层源头截断，放弃回溯

1. IO 层：文件尾 32MiB 上限（`modelTrajectoryFileTail.ts:6-7`，注释明说防 Host 事件循环阻塞与字符串内存峰值）；
2. 记录层：默认 200 条上限，超了丢旧的（`modelTrajectory.ts:19-20,110-111`）；
3. 语义层：`messagesKind:"tail"` 的 baseline **拒绝向上拼接更早历史**（`:291-295`，注释：防止把已裁剪的巨大上下文带回 UI 链路）；
4. 存储格式：model-io **delta 编码落盘**（request.messages 只存相对上条的增量，读出时还原 `:220-307`）——防的是同一 session 上下文梯度重复占盘。

UI 无订阅、无分页，截断就一行"已截断"文案。

### 4.2 我们：活会话全链路

- daemon `TAIL_ENTRIES = 200` 尾窗下发（`server.ts:703-727`）；上翻 `session.history {beforeId, maxMessages:500}`（`server.ts:6098-6121`）。
- store 侧 MaterializedView **全量投影、只加不驱逐**（`materialized-view.ts:389-403` "nothing is ever folded or evicted"）。
- **消息 delta 投影对我们不适用**——我们的架构不存在"每次调用重复携带全量 prompt"的问题（流式增量推送天然 delta）。这是形态差异，不是差距。
- zcode 的 delta 落盘思想对我们的 **journal 重放**有参考价值（恢复会话慢的根因：`server.ts:6122-6139` resume 重放 journal 秒级），但属存储层独立课题。

### 4.3 对照结论

- **截断换性能的思路不可照搬**：我们是会话产品，历史必须可回溯（用户明确要求导航条全量轮次）。zcode 的 200 条上限 + 放弃回溯 = 产品形态许可，我们没这个许可。
- **可吸收的 spirit**：源头限流（我们已有：daemon 尾窗 200/页 500）；store 侧驱逐（见 §8-P1）。
- zcode delta 落盘 ↔ 我们 daemon journal 重放慢：**另立项**（会话存储快照/增量压缩），不在本稿范围。

## 5. 流式每帧成本（我们独有，zcode 无经验）

调研确认我们已有相当好的防线，瓶颈在外壳层：

**已有（保持）**：
- rAF 帧合并 + message_update 折叠（`session-store.ts:200-205,421-459`）——per-frame 一次快照，非 per-token；
- 流式增量 markdown 解析按 "\n\n" 边界（`Markdown.tsx:686-699`，14KB 消息 11.5ms/帧 → sub-ms 实测）；
- tree-sitter 异步高亮 + FNV-1a hash 缓存 + 并发 3（`Markdown.tsx:856-916`）；
- EntryRow memo（`Transcript.tsx:625-658`）+ Transcript 内 folds/turnUnit 已窗口化（`:1283-1318`）。

**瓶颈（本稿要修）**：每次帧 emit 产生新 entries 数组引用 → ChatView 外壳 6+ 个 useMemo 每帧全量重算——`branchChildren`（`ChatView.tsx:1032`）、`leafWalk`（`:1063`）、`branched`（`:1133`）、`canvasRail`（`:1103`）、`visibleEntries`（`:1159`）、`buildTurnIndex`（`:1321`）。窗口化只救了 Transcript 内部 derive，外壳没救。长会话流式时这是 CPU 第一来源。

## 6. 长文本 / 大 payload 对照

| 机制 | zcode | 我们 | 判定 |
|---|---|---|---|
| 单条 payload 截断 | **无字符截断**，JSON.stringify 原样渲染（`trajectoryToolPayload.ts:42-54`） | 12k 字符截断（`Markdown.tsx:538,644-648`） | 我们更好 |
| 超长块显示 | max-h-64 + 渐隐 mask + "Show all"（`ExpandedContent.tsx:68-84,143-163`），收起再展开复位 | 10 行钳制 + 展开（`parts.tsx:111-137`）；思考块 80 句预算 | 等价，保持 |
| 语法高亮 | **无高亮**（裸 `<pre>`，零成本策略） | tree-sitter 异步高亮 | 保持（产品定位不同，我们是创作工具） |
| 折叠态预览成本 | preview 每次渲染全量 `replaceAll(/\s+/g," ")`（无 memo，`ExpandableMessage.tsx:273-324`） | fold 后回复行 textOnly 只渲染文本块 | 我们更好 |
| 大文件 | 32MiB 文件尾（IO 层） | artifact 预览 512KB 截断 | 等价 |

结论：**大 payload 防线我们已全面不劣于 zcode**，本节无吸收项。

## 8. 0.5.0 落地规划

> 总原则（小袁总定调）：站在巨人肩膀上改自己的——吸收策略层，不破坏液态玻璃动效与流式体验。改动全在 `client-core`（desktop/web/mobile 三端共享），ChatView 外壳随动。

### P0（本期目标，直接解决三痛点）

1. **entry 级虚拟化**：`Transcript` 引入 `@tanstack/react-virtual`，getScrollElement 挂 `.gui-transcript`；`estimateSize` + `measureElement` 实测（fold 开合触发重测）；上下 spacer 让滚动条代表真实总量——**"侧边导航条显示不全轮次"迎刃而解**（TurnRail jump 从"扩窗"改为 `scrollToIndex`）。删除 M1.11 只增不减窗口与"hidden history is not a thing"假设。
2. **ChatView 外壳 O(n) 派生降热**：`branchChildren/leafWalk/branched/visibleEntries/buildTurnIndex` 改挂 store 或按结构切片缓存；流式帧只重算受影响轮次。
3. **折叠远端卸载（zcode 收起即 unmount 的动效兼容版）**：fold 收起动画完成后，**视口外**的折叠轮次卸载正文只留占位（`content-visibility` 或 spacer 估算高）；视口附近保持挂载保动画。DOM 节点从"只增不减"变"有界"。
4. **历史分页保持**，spacer 高度按已加载段估算 + 上翻锚定沿用 scrollHeight 差值补偿。

### P1（吸收 zcode 交互层）

5. 角色级批量展开/收起（expansionCommands 对等物：思考/工具/正文分类折叠）+ 会话内文本搜索强制展开命中（`searchRevealed` 对等物）。
6. store 驱逐策略：MaterializedView 远端段冻结为紧凑快照（fold 态 + 摘要），回流时还原——长会话内存有界。
7. daemon `session.history` findIndex O(n) 换 offset 游标（`server.ts:6112`）。

### P2（独立立项，不在本稿动工）

8. 会话存储层：journal 增量压缩/定期快照（治"恢复会话慢"的源头，zcode delta 落盘思想的启发）。
9. 滚动位置持久化（会话切换回原位）。

### 验收

- 42k 条合成会话：首屏 TTI、上翻到底全程、jump 到首轮，三路径 60fps 无长任务（Profiler 实测对比基线）。
- TurnRail 全量轮次可见 + 点击 scrollToIndex 直达。
- 流式输出中上翻不跳变、不被拽回底部（M1.3 状态机回归）。
- 折叠/展开双向动画无损（视觉走查）。
- guest-client（web）/mobile 同组件回归。

### 风险与开放问题

- **fold 轮次高度估算**：折叠态高度稳定（textOnly 单行）好办；展开态虚拟化 + fold 动画同时跑需要 measure 时序小心（zcode 靠 animate 后 unmount 回避了这个问题，我们 P0③ 正面迎）。
- **tree-sitter 高亮与虚拟化卸载**：卸载行的高亮缓存保留（hash 缓存已是模块级单例），重挂不重算。
- **分支编辑**（branch bar）与虚拟化共存：编辑态 entry 强制 pin 在窗口内。
- tanstack virtual 版本对齐：zcode 用的版本与我们的 React/bun 工具链需核对（无锁文件冲突，独立依赖）。
