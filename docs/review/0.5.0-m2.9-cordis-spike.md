## 2. cordis 4.0.4 核心语义（源码审读摘要，供评审不读源码）

- **Context 是 Proxy**：属性读取即服务解析（`ctx.<key>`），未 inject 就读抛 `"cannot get property ... without inject"`。
- **Fiber 状态机**：`PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED`（外加 `FAILED`）。`ctx.plugin()` 返回 fiber（awaitable），`fiber.dispose()` 卸载并反向跑全部 disposer。
- **provide/inject**：插件 apply 内 `ctx.provide(name, value)` 把服务挂在自己 fiber 上；`inject: [...]` 声明依赖——不满足则 PENDING 挂起，服务出现/消失/换实现时**依赖方自动 unload/reload**（epoch 机制，`reflect.notify` → `fiber._refresh`）。
- **同名冲突**：同一 isolate scope 内第二个 `provide` 同名抛 `service "x" has been registered at <fiber名>`（`reflect.ts:290`），失败方 fiber 进 FAILED，先注册者无恙。
- **isolate 作用域**：`ctx.isolate(name)` 每次生成新 label = 独立 scope，同名服务并存；同 label 合并 scope。这是"每会话组合"的机制地基。
- **effect 账本**：插件 apply 返回的 disposer、`ctx.on`、`ctx.provide` 全部登记为 fiber effect（带 label 树），`fiber.getEffects()` 可检视；**卸载 = 框架保证全量反向回收，无需手写账本**。
- **活性门**：已 dispose 的上下文再注册 effect 抛 `cannot create effect on inactive context`（`CordisError('INACTIVE_EFFECT')`）。
- **检视面**：`ctx.registry`（Map 式遍历插件运行时）、`fiber.getEffects()`、`internal/status` / `internal/plugin` 事件。注意 `ctx.cordisInspect` **不是 cordis 原生物**，是 dsh `cordis-host-runner` 自建的检视注册表服务（见 §5）。

## 4. 关键判断题：DaemonService 契约与 cordis 的阻抗失配

对照物：`daemon/services/types.ts` 的 `DaemonService { key, routes?, start?, stop? }`（12 个 L2 服务，P1 收官）vs cordis plugin/fiber。

**同构面（占大头）**：
- `key` ≡ 未来 `ctx.<key>`（types.ts 头注释早已锁定命名纪律，spike 场景 0 逐字验证了 `provide(key, svc)` 后 `ctx.get(key)` 解析）；
- `start?()` ≡ apply 体（或 apply 内首行）；
- `stop?()` ≡ apply 返回的 disposer。

**`stop?()` 与 dispose 是否同构——基本同构，三处错位**：

1. **账本所有权**：cordis dispose 由框架保证全量反向回收（effect 账本），我们的 `stop?()` 目前只是注释约定"反向卸载全部副作用"，没有账本机制，靠自觉。cordis 化后 stop 语义从"手写纪律"变"框架保证"——这是收编的最大单点收益，对 ScheduleService 这类有状态服务尤其如此。
2. **routes 不进 ctx**：路由表是 L1 概念，cordis 无对应物。迁移后 `HostServices.routeTable()` 由注册表/Loader 生成，`routes` 字段留在服务声明层不进 Context——**失配但无需失配解决**，边界天然清晰。
3. **服务实例所有权翻转**：现在服务是 `new` 出来的无主单例再 `register()`；cordis 要求服务实例由 fiber 持有（provide 的 impl 记 `fiber` 所有）。12 个服务的迁移 = "构造注入 → `static inject` 声明 + 闭包内构造"的机械改写，逐服务独立提交，注册表垫片双跑（registry.ts 头注释已预留此路径）。

**两个次级失配**：
- **启动失败传播**：cordis apply 抛错默认被 logger 吞掉、fiber 进 FAILED；daemon 要求服务 start 失败 = 进程启动失败。host 侧须按序 `await fiber.await()`（spike 场景 0 演示了该形态），失败即中止 daemon 启动——需要一段 ~30 行的启动编排，属适配层职责。
- **无状态服务成本**：`start?/stop?` 缺省的服务在 cordis 里也必须是一个 fiber（一个对象 + 一个 provide），成本可忽略。

**适配层成本实测（代码层）**：`mountDaemonService()` 共 ~15 行（spike1.ts），把任意 DaemonService 包成 cordis 插件——阻抗可接受，无需改 cordis、无需改 DaemonService 接口。

## 5. 对照 dsh `cordis-host-runner` / `tool-cordis`：学什么、不搬什么

**学（按近期价值排序）**：
1. **group fiber 模式**（`requireGroup()`：`rootCtx.plugin({ name: 'cordis-dynamic', apply: () => {} })` 之下挂一切动态插件）：一个父 fiber 汇拢全部动态面，`await group.dispose()` 即整体回收。我们 daemon 的热重载（extensions.changed 已有）与 orderly shutdown 直接受益——建议收编时 daemon 根 Context 下设 `daemon-services` 与 `dynamic` 两个 group。
2. **启动失败不留挂**（`startHostHalf`：await 失败先 `fiber.dispose()` 再抛）：失败 fiber 绝不残留——写进我们的启动编排纪律。
3. **报错翻译**（`already registered` 冲突改写成"先停旧版再跑新版"的操作指引）：cordis 原生报错对用户不可读，收编时在适配层做一层错误改写。
4. **attempt/half/waitingFor 状态 vocabulary**（types.ts）：动态插件"版本/激活/等待依赖"的状态机词汇表，对 M4 专家/连接器对象模型有直接参考价值——现在不实现，设计时对标。

**不搬**：
- node:vm 半沙箱与 human-approval 流（`sandbox.ts` / `resolveRequestRun`）：0.5.0 扩展仍走 Bun 模块加载 + GUI 权限体系，P4 再议；
- `TypertRemoteService` 装饰器栈与 client-half（浏览器求值）：我们的 RPC 路由表（P1 路由覆盖快照）已定型，不引入第二套 RPC 声明方式；
- `cordisInspect` 检视注册表：cordis 原生 `registry` + `getEffects()` 已覆盖 daemon 内检视需求，跨端（host/client 双面）检视是 dsh 浏览器半沙箱特有的问题。

## 6. Spike ②：mode → 每会话挂载——闭环**跑通**（待复跑）

spike2.ts（16 条断言）直接 import 主干 `packages/coding-agent/src/presets/resolve.ts`（纯逻辑零依赖，可安全直连）：

1. 临时 modes 目录写入真实内置模板（`ensureModeTemplates`：work/chat/design/creator）+ 自定义子预设 `design-compact`（extends design，追加 prompt 区块 + settings 声明）；
2. `createModeResolver().resolve()` 展开三个预设；
3. 每会话 `root.isolate("prompt-sections").isolate("toolbelt").isolate("mode-settings").isolate("system-prompt")` fork 作用域，按展开结果 provide 资源；composer 子 fiber 以 `inject(["prompt-sections"])` 依赖驱动组装 system-prompt——**依赖注入式组合在会话粒度成立**；
4. 断言：design 五区块 persona、chat `promptComplete` 单区块生效、design-compact 继承 + 追加 + `compaction.enabled` 子声明生效；三会话互不污染；design 销毁后其余两会话完好、root 注册表剩 2 个会话运行时（含各自 composer 子 fiber，registry.size=4）。

**结论：会话作用域组合可行**——P3（会话组合）的机制风险解除。**复跑实测：16/16 全绿。**

**验收实录（主 agent 复跑时抓到并修复的 3 个 spike 缺陷，均为 spike 代码问题、非 cordis 问题）**：

1. **派生键不隔离会被跨会话污染**（重要发现）：初版只 isolate 了三个资源键，没 isolate composer 派生的 `system-prompt`——cordis 中子 fiber provide 的服务会向上冒泡，导致 chat 会话 `ctx.get("system-prompt")` 解析到 design 会话的 persona。修复：派生键同样进 isolate 清单。**对 P3 设计稿的教训：会话作用域的 isolate 键清单必须包含全部派生键，不能只隔离原始资源。**
2. **promptComplete 契约踩雷**：初版自定义子预设 extends chat（promptComplete: true），子预设追加的 prompt 区块被契约性丢弃（resolve.ts:198-200：complete 预设的 prompt 集 = 自身 sections，丢弃继承链其他 prompt）。属 spike fixture 误用契约，改 extends design（非 complete）后继承 + 追加均正常。
3. **registry 计数口径**：`root.registry` 把 inject 派生的 composer 子 fiber 也计为运行时（每会话 2 个 fiber），断言从"剩 2"修为"剩 4（2 会话 × 2 fiber）"——卸载 design 后其 composer 子 fiber 一并回收，恰好反向验证了 effect 账本完整性。

**挂载点建议：session-host 层（`daemon/session-host.ts`）**，不是 L1 也不是 L2 HostServices：

- L1（DaemonServer 路由/连接）无组合语义，且连接生命周期 ≠ 会话生命周期；
- L2 HostServices 是**宿主单例**服务（12 个），不应每会话实例化——会话组合消费 L2 服务，而非成为 L2；
- DaemonSessionHost 持有会话生命周期，`resolve.ts` 契约注释明确"v1 会话创建时消费"——fork 时机与销毁时机都在这里；preset 组合结果（工具白名单/prompt 区块/settings 覆盖）作为会话子 Context 的 provide 集，会话关闭即 `fiber.dispose()` 全量回收。
- 具体形态：P2 起根 Context 在 daemon 进程；会话创建时 `root.isolate(...)` fork + 按 `ResolvedMode` 装配；cordis 根与 isolate scope 的键名纪律（`prompt-sections`/`toolbelt`/`mode-settings`）建议进 P3 设计稿。

**spike ② 没测到的一个边界（写入决策点）**：isolate 只隔离**服务名**，不隔离**事件**——cordis 事件总线在 root 上共享，`ctx.on` 默认收全进程广播（仅 `internal/service` 等内部事件有 scope filter）。会话级事件隔离（如按会话广播工具事件）需要：事件名约定（`session:<id>/*`）、每会话子 Context 加事件过滤、或维持现有 EventService 会话级分发不动（L2 events 已按会话分发，可能是最省的——组合面走 cordis、事件面留 EventService）。

## 7. 收编边界建议 + ADR 草案（roadmap 待办 §"M2-2.9 试点启动时"）

> **ADR 草案：cordis 收编边界与分层纪律**（状态：草案，随试点验收定稿；正式归档建议 `docs/adr/0001-cordis-adoption-boundary.md` 或并入 roadmap §4.3 附录）
>
> **决定**：cordis（MIT，核心 9 文件）作为 daemon 宿主层的组合内核，strangler-fig 渐进收编。
>
> **边界（依赖方向纪律）**：
> 1. cordis 依赖只进 `packages/coding-agent/src/daemon/` 宿主层与未来新增的宿主侧包；核心领域包（`agent` / `ai` / `wire` / `sdk` / `catalog`）**零 cordis import**——它们消费的是 L2 服务接口（纯 TS 类型），永远不感知组合内核；
> 2. L2 服务接口文件（`daemon/services/types.ts`）保持零依赖，cordis 适配（mountDaemonService、启动编排、错误翻译）集中放 `daemon/host-context.ts`（新，~200 行量级）；
> 3. 测试用真 Context（纯内存、无 IO），不 mock cordis；
> 4. CI 门禁：依赖方向检查（grep/dep-cruise 级别即可——`packages/{agent,ai,wire,sdk,catalog}/` 不得出现 `cordis` 字样的 import），随 P2 首刀落地。
>
> **理由**：可回滚（注册表垫片双跑、Context 卸载即回 P1）、可测试（领域包测试面不变）、与 roadmap §4.3 收编边界一致。

## 8. Go / No-Go 建议

**建议 GO（启动 P2 strangler-fig）。前置已满足：主 agent 复跑 runbook 两个脚本，25+16 条断言全绿（2026-09-27）。**
