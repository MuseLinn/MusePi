# 0.5.0 评估：dsh 语音输入插件移植 + 插件管理交互吸收

> 评估日期：2026-09-26 · 基线：deepseek-harness `0.1.7-rc.2`（9/25 拉新）× musepi-omp main `b079c77e4`
> 性质：**评估文档，非实施承诺**。实施需小袁总批后按本文 §6 排期。

---

## 0. 结论（TL;DR）

1. **我们不需要移植 cordis，也不需要"整体移植插件"。** dsh 语音插件的价值 90% 在
   **引擎与流程层**（SenseVoice/sherpa-onnx-node、多源下载探测、首次使用引导），
   这些与 cordis 解耦，可平移；cordis 的 Service/Context 外壳在我们 daemon 里没有
   对应物，硬搬等于引进第二套运行时——与 P1 宿主分层方向冲突。
2. **我们语音"残废"的主因已定位：不是引擎坏了，是下载源被墙。**
   `stt/asr-worker.ts` 硬编码 `HF_RESOLVE_BASE = "https://huggingface.co"`，
   transformers.js/Kokoro 侧也没有任何镜像配置——大陆网络下模型永远下不来，
   首次使用即失败，功能等于残废。dsh 默认 `['https://huggingface.co',
   'https://hf-mirror.com']` + HEAD 探测选源，这正是小袁总截图里"配置更全面"的部分。
3. **快赢（建议 0.4.x 过渡版就做）**：多源下载回退 + 液态玻璃首次使用引导弹窗，
   预计 2–3 天即可让现有 Whisper/Kokoro 全链路真正可用。
4. **插件管理交互吸收点**（bundle 组件化详情、安装源镜像选择、官方/实验性分组、
   激活引导插槽）已有明确对位：我们的 ExtensionService/MarketplaceService +
   设置"扩展"tab，吸收的是交互与信息架构，不是代码。

## 1. dsh 语音插件架构解剖

### 1.1 五包结构（`packages/experimental/`，合计约 2,336 行）

| 包 | 角色 | 关键实现 |
|---|---|---|
| `voice-input-bundle` | 纯编排层 | 无代码，`cordis.patch.yml` 声明式 insert 4 个组件 |
| `speech-to-text` | Provider 注册表 | cordis `Service`，`register()/listProviders()/transcribe()/prepare()`，schemastery 配置 |
| `speech-to-text-sensevoice` | 本地引擎 | `sherpa-onnx-node@1.13.8`（npm 预编译二进制）+ SenseVoice ONNX INT8 + Silero VAD，受管子进程模型下载（HF 兼容源多源探测） |
| `api-speech-to-text` | 浏览器桥 | `@Remote` 装饰器暴露 `catalog/follow/configure/prepare/cancelPreparation/transcribe`（base64 WAV，字节/时长校验） |
| `client-ui-voice-input` | 客户端 UI | React 组件经 **slots 插槽**挂载：`conversation.input.activity`（Composer 麦克风）、`plugins.bundle.config`（插件详情准备卡）、`plugins.bundle.activation`（启用引导） |

### 1.2 值得吸收的设计决策

- **Provider 注册表模式**：STT 抽象为"可插拔 provider"（本地 SenseVoice / API），
  消费者只依赖注册表。我们的 `stt/models.ts` 目前是硬编码四档数组——同构但无注册机制。
- **readiness/准备状态机**：`follow()` 异步流推送 provider 准备进度（下载中/就绪/失败），
  UI 一次订阅全程跟随。我们是 `stt.downloadProgress/Done/Error` 三个离散事件，够用但没有
  "就绪总览"概念（dsh 详情页的"包含的组件 共4个·4已停用"即由此驱动）。
- **多源下载探测**（`model-sources.ts`）：对 HF 兼容镜像并发 HEAD 探测，首个成功的优先，
  其余保留作回退。约 60 行，与 cordis 零耦合，可直接借鉴。
- **受管模型进程**：sherpa-onnx 独立进程 + AbortController 生命周期 + 进度节流
  （4MB 一个进度事件）——我们 asr-worker 已有同构实现（进程模型、进度合并），对等。
- **首次使用引导**：启用插件 → 弹"使用前需要安装"（稍后/前往安装）→ 详情页准备卡
  显示空间/内存/时间说明 → 下载。这条链路我们完全缺失（下载失败就是裸错误）。

### 1.3 与 cordis 的耦合点（移植时必须剥离或替换的）

- `Service` 基类 + `Context`（fiber/entry/effect/生命周期事件）
- `cordis.patch.yml` 声明式装配（我们的对应物：daemon 内置登记 + ExtensionService）
- `@Remote` + `TypertRemoteContribution`（我们的对应物：daemon JSON-RPC + wire 事件）
- `slots` 客户端插槽系统（我们的对应物：guest-client/desktop-app 组件注册）

**判断**：四者在我们体系里都有对等物，只是名字不同。移植 = 把引擎/流程代码抽出来，
外套我们的 RPC/事件/插槽。不需要 cordis。

## 2. 我们现状与断点定位

### 2.1 已有资产（比想象中完整）

- **daemon RPC 全接线**：`stt.modelStatus` / `stt.modelDownload`（事件驱动进度）/
  `stt.transcribe` / `tts.synthesize`，在 server.ts 3711–3830 行，含幂等下载锁、
  wire 契约类型校验。
- **客户端 656 行 `voice.ts`**：16kHz PCM 录音 + VAD 判停 + barge-in + 设备枚举；
  Composer 的 `VoiceButton`/`VoiceStatusStrip`/`useDictation` 已接线；
  设置面板 `VoiceSection` 已注册进 nav。
- **引擎**：Whisper base/small/turbo（transformers.js）+ Parakeet（sherpa）四档；
  TTS Kokoro-82M；worker 均为受管子进程，与 TUI 共用。

### 2.2 断点清单（按致命度排序）

| # | 断点 | 位置 | 后果 |
|---|---|---|---|
| B1 | sherpa 文件下载硬编码 `huggingface.co`，无镜像 | `stt/asr-worker.ts:51` | 大陆网络 Parakeet 档永远下载失败 |
| B2 | transformers.js/Kokoro 未配置 `env.remoteHost`，无 hf-mirror 回退 | `stt/asr-worker.ts` / `tts/tts-worker.ts` | Whisper/Kokoro（默认档）同样下不来 |
| B3 | 无首次使用引导：下载失败 = 裸 RPC 错误 | 客户端 voice.tsx | 用户感知"功能残废" |
| B4 | 无 readiness 总览事件（只有离散 download 进度） | daemon stt 路由 | UI 无法做 dsh 式"组件×状态"矩阵 |
| B5 | Parakeet 不支持中文（已有注释警示，默认档已是 Whisper small） | `stt/models.ts` | 非断点，但中文用户选错档即"转写出空" |

**结论**：架构没坏，是"最后一公里"（下载源 + 引导流程）坏了。修复 B1–B3 后现有栈
即可用；B4 是体验增强。

## 3. 移植可行性逐项评估

| 项 | 评估 | 说明 |
|---|---|---|
| SenseVoice 引擎（sherpa-onnx-node） | ✅ 可移植，**但许可需核查** | npm 包 Apache-2.0 无问题；SenseVoiceSmall 模型权重在 ModelScope/HF 上为 **CC BY-NC 4.0（非商用）**——MusePi 若严格非商用可接受，否则应默认 Whisper 档、SenseVoice 作可选实验档 |
| 多源下载探测（`orderModelSources`） | ✅ 直接借鉴 | ~60 行纯函数，零依赖，改写成我们的 downloader 风格即可 |
| 准备状态机 + `follow` 流 | 🟡 部分吸收 | 事件模型对等（我们离散事件 vs dsh 快照流），建议保留离散事件，补一个 `stt.status` 聚合查询即可，不动传输 |
| `@Remote` API 桥 | ❌ 不搬 | 我们的 JSON-RPC 已对等且更薄 |
| cordis Service/slots/patch.yml | ❌ 不搬 | 与我们 P1 后的服务分层 + 客户端组件注册同构，引入即双运行时 |
| 客户端 UI（VoiceInput.tsx 等 437 行） | 🟡 参考不搬 | 交互逻辑（按住录音/波形/准备卡）可参考，视觉必须重做液态玻璃 |

## 4. 插件管理交互吸收点（对应小袁总截图 1/2）

dsh 插件面板（`ui-plugin-manager` 3,374 行 + `ui-settings-plugins`）的四个信息架构决策：

1. **bundle 组件化详情**：插件详情页列出"包含的组件 共N个"及每个组件的独立开关
   （语音输入 bundle = 4 组件）。我们的扩展详情页目前只有总开关——吸收此设计后，
   一个扩展可声明"服务组件 / UI 组件 / 命令组件"分组启用。
   *对位：ExtensionService 已拆出，扩展 manifest 需加 `components[]` 声明。*
2. **安装源选择**："添加插件"弹窗带安装源下拉（npm 官方源 / **中国大陆镜像源
   (npmmirror)** / 自定义地址）。我们的 MarketplaceService 已有 registry 概念，
   需补镜像预设 + UI 暴露。
3. **官方/实验性分组 + 徽标**：官方 7 插件分组列出，实验性插件带标签。
   我们的能力中心已有分类，需补"实验性"通道与徽标规范（gui-design.md 增补）。
4. **激活引导插槽**：`plugins.bundle.activation` 让插件在启用时注入一次性引导
   （语音输入的"使用前需要安装"弹窗即此）。对位我们的事件广播 +
   客户端首次启用向导。

**不吸收**：dsh 的 config-ledger（配置账本）层对我们过重，设置面板沿用现有
schema-driven 区段即可。

## 5. 建议方案（分阶段）

### A. 快赢包（0.4.x 过渡版，建议立即做，2–3 天）

1. 下载多源化：HF 主源 + `hf-mirror.com` 回退（sherpa 文件 + transformers.js
   `env.remoteHost` 都接上），探测逻辑借鉴 dsh `orderModelSources`。
2. 液态玻璃首次使用引导：启用语音/首次点 mic → "使用前需要安装"弹窗
   （空间/时间说明 + 稍后/前往安装），下载进度走现有事件流。
3. `stt.status` 聚合 RPC（cached/downloads/默认档）——支撑设置页"组件状态"行。

### B. 0.5.0 正篇

4. STT provider 注册表化（吸收 dsh 注册表模式，落在我们 daemon 插件体系内，
   作为"内置插件"范例——与 P1 分层后的服务注册同一条路）。
5. SenseVoice 中文档评估接入（许可核查先行；中文识别明显优于 Whisper small，
   值得作为第三选择）。
6. 插件管理交互四吸收点落地（组件化详情 / 镜像源 / 实验性徽标 / 激活引导）。

### C. 明确不做

- 不引入 cordis；不整体照搬 dsh 插件包；不重写已有 asr/tts worker 进程模型。

## 7. 风险与开放问题

- **SenseVoice 模型许可（CC BY-NC）**：MusePi 发布形态决定能否默认内置。
  建议：默认 Whisper（MIT），SenseVoice 标"实验性"并附许可说明——与吸收点 3 的
  实验性通道正好 synergy。
- **transformers.js 在 bun worker 下的实际表现**：代码路径存在但从未在大陆网络
  环境跑通过（B1/B2），快赢包落地后需真机验证 CPU 推理速度（Whisper small 15s
  窗格在低端机可能 >10s，必要时引导用户选 Fast 档）。
- **TTS 朗读质量**：Kokoro 中文支持一般；若小袁总对 TTS 期望高，后续可评估
  接 Edge-TTS 类在线源作备选 provider（注册表模式正好留了这个口子）。
