## i18n contract (guest-client/src/i18n)

- **Named parameters**: `t("… {count} …", { count: n })` — no `{0}` positional parameters (openchamber/opencode/bitfun/kimi-code all use named parameters, which read well translated; positional parameters were musepi's old approach, fully migrated 2026-08-06).
- **Word lists split by domain** (2026-08-16): `zh-CN/` + `en-US/`, 12 domain modules each (shell/composer/sessions/context/collab/transcript/settings/agents/tools/pet/guest), merged by barrel into a flat map — edit copy by finding the corresponding domain file; duplicate keys across domains throw at barrel module load (replacing silent spread overrides). The TUI word list (`coding-agent/src/i18n/zh-CN/`, 13 domains) uses the same split and guard but keeps `{0}` positional parameters. Architecture overview in `docs/i18n.md`.
- **Typed keys**: `TranslationKey = keyof typeof zhCN` (zh-CN barrel merged `as const`) — both key and params of `t()` checked at compile time: misspelled key, wrong placeholder name, missing param → tsgo error. Dynamic keys (schema-driven labels, runtime error strings, `tag.${…}` concatenation) take an explicit `as TranslationKey` assertion — at runtime they still fall back to the raw key via `?? key`.
- **Placeholder types**: `ParamsOf<K>` uses template literal types to extract `{name}` from zh-CN values and map them to `{ [name]: string | number }` — parameter names strongly bound to translation templates.
- **Compile-level en parity** (2026-08-16): every en domain file is `as const satisfies Record<ZhKey, string>` — en missing/extra key is a compile error (negative check TS2353); new zh keys must add en in sync.
- **Plugin seam** (2026-08-16): `registerTranslations(locale, map)` registers/overrides copy at runtime and `emit()`s an immediate re-render (fully new locales supported); plugin-owned keys go through `tLoose(key, params)` (core `t` accepts only `TranslationKey`). Neither persists.
- **en passthrough**: keys are the English source text; replacement applies to the final string (dict hit or key fallback alike) — English UI shows `context · 42%` rather than `context · {pct}`.
- **Tests**: packages/client-core/src/i18n/i18n.test.ts (key-set parity, cross-domain duplicate guard, registration override/isolation) + test/i18n.test.ts (lookup/replacement/fallback/English passthrough/no-positional-residue assertions); tests calling setLocale must restore the initial locale in afterAll (bun test runs files sequentially in one process; leakage pollutes other tests asserting English copy).
- **Typed side effects**: typing forces every UI string to have a zh translation — migration backfilled previously passthrough keys (open sidebar/connected/unknown/jump to bottom, etc.); `as const` scenarios (PREFERENCE_LABEL, KIND_TRANSITION, SCALAR_ARGS, TIP_KEYS, SOUND_USAGE_KEYS) use `as const satisfies Record<…, TranslationKey>` or explicit `Partial<Record<…, TranslationKey>>` so dynamic indexing keeps literal types.
- **Call during render**: `t()` is called at render time only (module-load calls capture the old locale — already constrained by comments).

## 1. Layout system

- **Primary task and hierarchy**: identify the user's primary task and dominant action before adding copy or decoration. Establish structure first through layout, spacing, alignment, typography, and grouping; do not use badges, dividers, nested cards, or explanatory text to compensate for an unclear composition.
- **Text earns its place**: avoid unnecessary secondary labels and descriptions. Do not repeat a section title inside every card, restate the same state in a badge and a sentence, or keep guidance permanently visible when a tooltip, details view, or other on-demand surface is enough. Let the layout do the explaining.
- **Restraint preserves essentials**: keep input purposes, unfamiliar actions, consequential settings, errors, and accessible names clear. Progressive disclosure is for advanced options, diagnostics, and secondary metadata, not for hiding the primary action or information needed to make a safe decision.
- **Polish is an acceptance criterion**: inspect the composed interface at representative widths with long and localized content, and cover empty, loading, error, disabled, and keyboard-focus states where applicable. Correct behavior and passing tests do not excuse repeated headings, unintended wrapping, alignment collisions, nested card faces, crowded controls, or other avoidable visual noise.

- **Three-column shell** (openchamber-consensus layout): left SessionSidebar (sessions/groups/projects) + middle ChatView (message stream + rounded composer) + right ContextPanel (always visible). `gui-shell` is flex ROW — every full-width pane (SettingsView etc.) must carry `flex:1; min-width:0`, otherwise it collapses to content width.
- **Side session tab** (2026-11-11): a normal session can open beside the active chat from the session list's context menu. The right panel owns one `session` tab per target (identity = session id); the target keeps its own live transcript, composer, approvals and asks, so it is steerable rather than a read-only preview. Opening the active session is a no-op; the tab offers "open in main area" instead of duplicating the main chat. Advisor transcripts keep their read-only note and use the "Advisor session" title.
- **App rail (two-tier left column, 2026-11-07)**: a persistent 52px destination column (`.gui-rail`, `components/AppRail.tsx`) precedes the panel slot, so collapsing the panel to zero width cannot strand the user — the way back never lives inside the thing being collapsed, and the settings round-trip still replaces only the sidebar slot while the rail stays mounted. A 48px draggable top band (`.gui-rail-top`, level with `GuiHeader`'s `h-12`) is deliberately EMPTY: the rail avoids the titlebar instead of moving it — the window's one fold/unfold control stays at its original `left:16px` on frameless windows. Destinations start BELOW the band, never in the window titlebar row (regression 2026-11-07: the first icon overlapped the top bar; 2026-11-08: a second fold button in the rail duplicated the titlebar one). Buttons are icon-only with a tooltip and an accessible name, `aria-current="page"` marks the one destination the panel is showing, and the unread dot is decorative (`aria-hidden`) rather than a badge count. Destinations are 首页 / 任务中心 / 看板 / 问题与拉取请求 / 能力中心 (plugin-gated) / 设置; 新建 and 搜索 stay in the panel because they are actions, not destinations — the menu rows that duplicated the destinations in `SessionSidebar` are gone. Each destination owns its left column: 首页 shows the session list, 设置 the settings nav, and 看板 / 问题与拉取请求 fold the session sidebar (display:none, still mounted) so their surface owns the width. 任务中心 and 能力中心 keep the slot and swap in their OWN second-tier panels (`ScheduledTasksPanel` / `CapabilitySidePanel`), so the fold control, side resize handle and rail remain usable there (see the panel rules below). `computeSettingsShellState({pageDestinationActive, scheduledPanelActive, capabilityPanelActive})` is the single decision point, and the rail's 首页 restores the session list. On a destination without a left panel no toggle is rendered and the background double-click is inert rather than doing something invisible. The rail is a real flex child, not an overlay: the side-resize handle and every pane offset derive from `RAIL_WIDTH`.
- **Rail footer (2026-11-08)**: the instance menu, keyboard shortcuts and remote control used to live only in the collapsible sidebar footer, so folding the panel or opening a page destination removed them. They now sit in the rail's bottom group (ChatGPT's account/more footer parity): `InstanceButton` gets a `compact` variant that keeps the full portal menu but shows only the connection dot in a 36px rail button; shortcuts and remote control are icon buttons beside it; Settings stays last. `SessionSidebar.showFooter` (default true) disables the duplicate footer for the two-tier shell while other hosts and the sidebar contract tests keep it. Compact geometry is verified equal to the other rail buttons (36×36, `--radius-md`).
- **Card geometry contract (2026-11-08)**: every destination's floating card — chat, welcome, right pane, terminal dock, board, scheduled, PR, capability — shares ONE geometry. `.gui-chat-surface` carries the window gutter (`margin: var(--gui-card-gutter)` = 8px) and the card inside carries the same gutter again, so every card sits 16px from its column edge. Radius is `var(--radius-2xl)` (16px), shadow is `var(--gui-card-shadow)`, surface is `var(--color-surface)`. `.gui-float-card` covers the chat/welcome/right-pane cards; `.gui-page-card` covers page destinations rendered through `ChatSurfaceShell`. Tailwind `m-2`, `rounded-2xl` and the old single-card `0 4px 24px rgba(0,0,0,.25)` shadow are forbidden here: they made page cards sit 8px closer to every edge and cast a heavier shadow once the two-tier rail changed the column width. REA parity: ChatGPT's `PageSurface` owns one `inset`/radius for all destinations. Verified with headless Chrome computed styles — the chat card and the page card report identical left/top/right/bottom/width/height/radius/shadow/background (diff `[]`).
- **Titlebar coexistence & hover peek (2026-11-08)**: `--gui-rail-w` (52px) is a single CSS width that the collapsed `.gui-header-spacer` subtracts — reserving only the part of the fixed titlebar cluster that overlaps the chat column, so a collapsed panel no longer gains a phantom 52px gutter before the session title/tabs. A destination without a left panel (board / PR) hides the fold button entirely but keeps the collapsed-value spacer — its geometry equals a closed panel, so dropping the spacer would slide the title under the titlebar cluster (`GuiHeader.panelAvailable`). With the docked panel closed, hovering ONE rail button that declares `panelId` floats the SAME mounted pane its destination owns (`data-panel` = hovered id, 2026-11-08). The rail's empty band and destinations without a panel float nothing, so 任务中心 peeks its task list and 能力中心 peeks its capability navigation instead of the 首页 session list. `data-panel` therefore accepts `home` / `scheduled` / `capability` / absent. The floating pane is `fixed`, `top:48px`, `left:calc(--gui-rail-w + 8px)`, `z-index:42`, rounded elevated surface, 8px slide-in, dismissed 140ms after pointer leave — ChatGPT's `app-shell-floating-left-panel` parity (fixed, no layout width, no second instance). Hover only PREVIEWS; a click commits: clicking a panel-bearing destination (or any row inside the peeked pane) opens that destination WITH the panel it owns, and the row's nav action is replayed once its page mounts. Peek alone never re-docks the panel. `lib/rail-peek.ts` owns the pure gate and the `data-panel` decision. REA evidence: `Layout[data-app-shell-docking-peek]` clears the sidebar divider while the floating panel owns the surface; the titlebar's `tracksAppShellHover` sets the hover store, and the panel motion is `initial{x:-8}→animate{x:0}`.
- **Scheduled Tasks owns the rail's sidebar slot (2026-11-08)**: the task list is a real second-tier panel (`ScheduledTasksPanel`) mounted in `.gui-side-keeper` next to the session sidebar — not a 260px grid column inside `ScheduledTasksPage`, which disappears on the empty state and sits to the right of the slot. `computeSettingsShellState` keeps the keeper visible for this destination; the `.gui-side-keeper--scheduled` modifier swaps which mounted pane is displayed, so expanded session groups and the task panel's search/filter/selection both survive a destination change, and Settings still takes the slot back. The page publishes one `cron.list` projection through `lib/scheduled-task-nav.ts` and consumes the panel's select/new actions — no second request, no duplicated selection state. The panel carries a title + count, new-task action, search, and a status filter (All / Enabled / Paused / Failed recently — REA: ChatGPT's `automations.scheduled.filter.option` uses `active|paused|completed`; MusePi maps to real `CronTask.enabled` / `state.lastStatus` fields rather than inventing a "completed" state). The detail pane is the page's only column. The panel is the Cordis contribution `sidebar.panel.scheduled` (`plugins/scheduled-panel/`); the host mounts the same built-in component only when the registry is unavailable or the plugin is disabled / fails to compile, and `task-nav` is bound through the shared host-module table so the compiled panel reads the page's one snapshot.
- **Capability Center owns the rail's sidebar slot (2026-11-08)**: the three 技能 / 插件 / 插件市场 switches used to be `WorkspacePageHeader.tabs` buttons INSIDE the page — one container with three tabs and no second-tier navigation column (ChatGPT's 自定义 left panel is the reference). They now live in `CapabilitySidePanel`, a THIRD mounted pane in `.gui-side-keeper`, following the same `gui-side-panel.css` rhythm: one full-width primary action (添加能力 → marketplace), one compact search row, one flat 浏览 section with three full-width rows (icon + label + installed/plugin count badge), a single accent for selection, and a one-line no-match hint. The page header keeps only title / description / back; the content column renders exactly one pane, and the 技能 discover/installed sub-segment stays in that column. `computeSettingsShellState` keeps the keeper visible, `resolveSidebarPanel` returns `capability`, and the rail's capability button declares `panelId: "capability"` so hover-peek floats THIS panel. `lib/capability-nav.ts` is the one-way bridge: the `app.capability` page publishes `tab` + `skillsCount`/`pluginsCount` and consumes `select`/`add` actions; both compiled subtrees bind `capability-nav` through the host-module table. The panel is the Cordis contribution `sidebar.panel.capability` (`plugins/capability-panel/`), with the same built-in component as the offline / disabled fallback. Contract: `test/capability-panel.test.tsx`, `test/capability-panel-plugin.test.tsx`.
- **Second-tier panel spec (2026-11-08)**: `gui-side-panel.css` is the single surface language for every destination and plugin-contributed panel (home / scheduled / capability) — 8px drag band, one full-width primary action, one compact search/filter row, flat named sections (no nested card faces, no row hairlines), full-width hover rows with one accent for selection, and a compact one-line empty hint. The panel repeats neither the destination heading nor the content column's illustrated empty state. Every pane carries its own slot class (`.gui-scheduled-slot` / `.gui-capability-slot`) so the `home` selector excludes the others; `data-panel` is the single authority and never switches `display`.
- **Equal-height rounded cards (2026-11-08)**: the sidebar pane is the SAME card as `.gui-chat-column` / `.gui-page-card`: it starts below the 48px rail/header band, mirrors the content column's two-layer gutter (48px + 16px at the top, 16px at the bottom), and carries `border-radius: var(--radius-2xl)`, `box-shadow: var(--gui-card-shadow)` and `background: var(--color-surface)`. Both columns therefore report the same top/bottom/height. `data-panel` only changes which mounted pane is active — it NEVER switches `display`, or the 220ms width fold would be lost.
- **Sidebar motion (2026-11-08)**: folding animates `width` over 220ms `--spring` with a 160ms opacity fade and delayed visibility; hover-peek keeps both panes fixed at the card geometry and animates `opacity` + `translateX(-8px)` over 140ms. `data-peek-open` is deliberately separate from `data-panel`: leaving a rail button drops `peekHovered` immediately (fade-out) while the panel id survives 140ms so the pane stays mounted through the exit. Reduced-motion drops every transition.
- **Getting-started card (REA reference, 2026-11-08)**: observed in the reference capture — a compact card at the BOTTOM of the home sidebar with a title, overflow menu, collapse chevron, a thin completion bar and a short checklist (hollow circle pending / check done, optional trailing glyph); clicking a row opens its entry point and advances the bar. Inference for MusePi: four rows map to real destinations (settings / providers / session import / task center), completion means "visited" and is stored renderer-locally. Unknown: the reference app's persistence key and whether its completion comes from server state. `GettingStartedCard` owns collapse, dismiss, reset and progress; `SessionSidebar.gettingStarted` is only a layout slot, so the card folds and peeks with the panel.
- **Global liquid-glass spec (2026-11-08)**: `tokens.css` owns one three-layer ladder — L1 cards (chat / sidebar / page / right panel / dock / session info / getting-started), L2 floating layers (menus / popovers), L3 interaction states — each with a fill, hairline, rim pair and shadow, derived from the ACTIVE theme's `--bg-*` / `--fg` (so every preset and both schemes share one ladder). `gui-glass.css` loads last as the single authority. Hairlines are neutral per scheme because a black outline on a dark card and a white outline on a light card are both invisible: dark uses 18–30% white, light uses 18–30% neutral dark. Hover no longer uses `--color-surface-raised` (the card's own color, which made the highlighted menu row identical to its parent): it lifts with `--glass-hover-strong` plus an inset hairline, active rows use `--glass-active`, and `:focus-visible` adds an accent ring. Cards gain a specular top rim, a bottom echo, a diagonal sheen and a lifted shadow. L1 cards themselves add no `backdrop-filter`: on win32/linux the OS window supplies no material to sample, so tint + hairline + rim carry the glass. The EDGE BANDS are different — they blur in-window transcript rows, which exist on every platform (see the progressive-blur bullet). `prefers-contrast: more` promotes every hairline to the strong value.
- **Theme-native accent & one palette per screen (2026-11-08)**: a color theme is no longer surfaces-only. Every `UiThemeId` supplies a `--theme-hue` in tokens.css, and `data-accent="theme"` (the fresh-install default) resolves the whole `--accent` family from that hue plus the scheme's lightness/ink; brand / mono / ocean / jade / a custom hex remain explicit overrides. The L1 fills, hairlines, rim and hover states, and the transcript fade bands (`--gui-card-surface`, `--gui-card-surface-fade`) are derived from the active theme's `--bg-*` / `--fg` instead of a literal hue-60 fill. That was the exact cause of 「品牌黄 + 午夜蓝」 mixing: the sidebar / ChatView / right rail kept the DEFAULT warm-brown card while the session-info card and the top/bottom fades followed the midnight-blue surface. `.gui-session-info` joins L1 so it shares the same surface, and the pre-rebrand `#7aa2ff` / `rgba(122,162,255,…)` literals in cron/calendar controls became `--color-accent` mixes. Contract: `test/theme-palette.test.ts`.
- **Progressive-blur edge bands & a seamless chat head (2026-11-08)**: the top/bottom transcript fades used to paint an OPAQUE slab of `--gui-card-surface-fade`, which read as a hard color step against the 对话/地图/信息 head (that head shows the card's glass composite + sheen + rim) and hid 24–32px of content. Both bands now stack THREE sibling backdrop layers — 2px across the full band, 6px over the inner 62%, 14px over the inner 34% (`--gui-blur-progressive-1/2/3`), each masked to a shorter ramp, so blur STRENGTH grows toward the edge and rows dissolve progressively. The band carries only a low-alpha tint of the SAME derived card surface, and `.gui-chat-head` starts from `--gui-card-surface-veil`: head + band are one continuous glass surface with no seam. The 对话/地图 switch and the info toggle dropped `--color-bg`'s darker inset slab for `--glass-hover` + `--glass-hairline` + a specular rim, so the controls share the card's palette. Head padding drops 8px → 6px and, because the band is bounded (28px / composer-inset ramp) instead of a scroller mask, scrolling never recomposites the whole transcript. `@supports not (backdrop-filter)` restores the opaque ramp. Contract: `test/progressive-blur-dock.test.ts`.
- **Collapsed terminal dock leaves no hairline (2026-11-08)**: the dock stays mounted at inline `height: 0` so open/close can animate. `gui-glass.css`'s L1 shorthand re-armed all four 1px borders; the older fix zeroed only `border-top-width`, so a 1px bottom edge survived at the window bottom. A last-sheet, higher-specificity `:not(.gui-terminal-dock--open)` rule now zeroes every border width, the glass fill and the shadow; the open state still gets the full L1 glass. Contract: `test/progressive-blur-dock.test.ts`.
- **Narrow desktop shell**: at ≤640px the session sidebar becomes an overlay drawer. Its closed state is hidden and inert, and opening it does not compress the chat column. Session tabs expose keyboard selection and navigation, settings collapse controls have accessible names, and an empty board provides a direct new-tab action.
- **Mobile remote-control dialog**: the wide dialog keeps scan sharing and Bot channels in two columns and stacks them below 800px. Sharing scope, its safety implications, and the primary action form one flow; a missing cloudflared executable produces a localized recovery card with an installation guide, retry, and on-demand technical details rather than a raw error block. Bot rows suppress redundant off copy, preserve meaningful live/detail states, disambiguate channel actions for assistive technology, and keep credential labels visible. Loading, empty, and failed channel lists remain distinct, and the secondary plugin inventory is collapsed by default.
- **Remote connection disclaimer**: the first attempt to open mobile remote control or instance management presents one shared, versioned disclaimer before the target opens. Decline, close, and Escape cancel the pending action; only Accept grants the current version and continues. Once accepted, the disclaimer remains available from the instance menu and both dialogs without re-prompting. The text distinguishes full-control from view-only links, content encryption from relay metadata, third-party Bot policies, and the localStorage risk of instance tokens.
- **Settings panel** (slot replacement since 2026-09-24, retired the chat-column overlay): the settings shell REUSES the main layout — the settings nav fills the app sidebar's slot (`.gui-settings-nav-slot`, same position + width language; SettingsView portals its nav column into it) and the content fills the chat column, topped by the 48px window-drag strip (`gui-settings-content` fixed-height scroll container, centered column via `width:100% + max-width + margin-inline:auto`; the ceiling is `--gui-settings-content-max` = `clamp(840px, 78%, 1080px)` — 840px is openchamber's flat value and stays the floor so normal windows keep the reference geometry, rising to 1080px on wide panes so a maximized high-resolution window doesn't strand the column in whitespace). The real sidebar and the chat header + surface stay mounted underneath (`.gui-side-keeper` / `.gui-chat-col-keeper`, display:none), so closing settings restores the workspace — expanded groups, transcript, virtual list — without a re-mount (slot decision table: `lib/settings-shell.ts`).
- **Shell minimization transparency**: Settings → Shell presents measured command count, saved bytes, weighted reduction, and per-filter totals beside the advanced minimizer controls. A minimized Bash result shows its filter and per-command percentage; when the host supports it, View raw output opens a wide read-only `DialogFrame` in the owning session. The preview uses the existing modal focus stack, a visible close action, and scroll-edge feathering; large content is explicitly truncated rather than silently clipped.
- **First-class workspace headers**: task center, boards, issues & pull requests, and capability center use `WorkspacePageHeader` for one leading back action, `h1`, optional description/meta/actions, and an optional tab row (capability center no longer uses the tab row — its three destinations moved to the rail's second-tier panel, 2026-11-08). Board home returns to the workspace; an open board returns to the collection. Pages do not reimplement title geometry or place a second back action on the trailing edge.
- **Issue/PR workspace**: the list and selected detail are independent scroll regions in a two-column master-detail grid. The first visible item opens automatically; filtering repairs an invalid selection, and a stale detail response never replaces a newer selection. Bodies and comments use the shared Markdown renderer, with a comment composer in the detail column. Open, non-draft PRs also offer approve and request-changes actions; request-changes requires a body. Comment and review drafts survive failed submissions, and Ctrl/Cmd+Enter submits a comment without treating IME composition as a shortcut. PR rows include their comment count. Refocusing the window refreshes a list only when its last request is at least 60 seconds old. Below 960px the detail keeps the full width and the list opens in a glass `MenuPopup` from the item button; selecting an item closes the popup. Surfaces use the shared glass background, border, sheen, and shadow tokens rather than duplicate section labels.
- **Collapsed settings search**: at ≤900px the icon rail keeps its full navigation while the search popup filters results independently. Search uses the shared `MenuPopup` portal, so the 64px rail cannot clip it; result selection, outside dismissal, and Escape clear transient query state, and Escape restores focus to the search button.
- **Task-calendar selection**: a date with scheduled tasks opens a per-day task list, including days with multiple tasks. Choosing a task from that list or a status-board card opens the visible task-detail view rather than only changing an internal selected id.
- **Extensions control center** (settings "Extensions" tab): the section fills the settings viewport (`gui-skills-section` = `height:100%` flex column, `gui-ext-center` `flex:1; min-height:0`) — the left list (`gui-ext-list-scroll`) and right detail (`gui-ext-detail`) scroll **independently** inside their own rounded containers while the settings page as a whole does not scroll (TUI /extensions panel parity); both columns share the thin scrollbar recipe (8px, thumb `text-faint 30%`, hover 50%, same formula as xterm); instruction content is not height-capped (pre has no max-height), scrolling wholesale with the detail area to avoid nested scrolling.
- **Plugin state and composition**: a component shows its effective green/on state only when its parent is active and the component itself is not denied. A disabled parent keeps the component selection visible with an off, disabled control. The Cordis-owned capability center mounts through `app.capability` and has Skills, Plugins, and Marketplace panes; its destination navigation is the separate `sidebar.panel.capability` second-tier panel. Component availability is the only source of truth for its sidebar entry, sidebar tab menu, command-palette action, and external navigation; disabling the last component while the page is open returns to chat. The Plugins management list shows Installed before Official, classifies native scoped modules as Official regardless of their source directory, and does not repeat preset groups. Official modules use the same enablement lifecycle as their slot registrations, not a second package switch. Package and module cards share one horizontal geometry: a fixed leading icon, a flexible center column for title, description, and tags, and trailing actions. Cards retain the same dimensions in list and grid variants; `experimental: true` adds a warning-tinted Experimental badge instead of overloading the description. The package/bundle card model remains: package switches use the runtime lock, bundle switches update the profile selection, and unreadable selected bundles stay visible without a separate Composition tab. Settings → Presets remains the session-scoped Agent preset surface; declarations mount real fibers in each session and the first turn locks the active session's preset.
- **Complete marketplace details**: catalog detail opens the wide `DialogFrame` rather than a metadata confirmation card. A single hierarchy keeps brand and enablement in the header, full introduction and skills in the scrolling body, and version/repository actions in the footer; it does not add tabs or secondary labels merely to look dense. Installed scope and enabled state are real registry values, not presentation-only flags. Search text, category, installed/catalog/sources segment, and the open detail id survive renderer reloads; source clones persist in the daemon cache, not duplicated renderer storage.

## 2. Design tokens & theme

- **Three orthogonal axes** (the DOM layer always carries resolved values, no "system"): `data-theme` (resolved light/dark) + `data-accent` (accent preset) + `data-ui-theme` (independent light/dark UI preset).
- **Density**: `--gui-density` is a **unitless factor** (e.g. `1`/`0.85`); CSS uses `calc(32px * var(--gui-density, 1))`.
- **Shared geometry and semantics**: spacing, control sizes and the `--z-dropdown` through `--z-tooltip` layer ladder live in `tokens.css`. Semantic text aliases resolve to the foreground hierarchy, and touch controls keep a 44px minimum target. Component-local stacking and decorative art colors may remain local when they do not escape their container. `scripts/check-css-tokens.ts` checks that semantic color references are defined; it does not certify contrast for every ported theme.
- **Radii — 6-step ladder (2026-09-17)**: `--radius-xs 2` / `sm 4` / `md 6` / `lg 8` / `xl 12` / `2xl 16` (+ pill `999px`, circle `50%`; `--radius-full` = 9999px serves both, since `border-radius` clamps to half the box). Concentric rule: child radius = parent radius − parent padding (16−4→12−4→8−2→6) — "outer round, inner square" means the chain is broken. Literal px radii are banned in authored CSS (`scripts/check-radius-tokens.ts` runs inside `check:tools`; generated `tailwind.out.css` is exempt), and every referenced `--radius-*` must resolve to a `tokens.css` definition (an undefined custom property renders the corner square with no console error) — cards/panels sit at `lg`, dialogs/drawers/popovers at `xl`, fullscreen sheets at `2xl`. Cards uniformly keep `border: 1px solid var(--border)` + `background: var(--color-surface-raised|sunken)`.
- **Fonts**: UI defaults to serif plus bundled Maple Mono NF CN (monospace); variable fonts Inter/JetBrains Mono under `@fontsource-variable/*`. Code block font size follows `--gui-code-size`.
- **Glass**: `gui-vibrancy` IPC + CSS `--gui-glass-overlay` opacity; transparency toggle off = 100% overlay covers all semi-transparent rules. **Liquid glass (2026-09-17)**: on top of the vibrancy window, elevated glass surfaces (dialogs, shell rail/header, lightbox primaries) render as liquid glass — tokens.css `--glass-*` ladder (translucent fill, specular inner top rim `--glass-edge-hi` + dim bottom echo, diagonal `--glass-sheen` via unclaimed ::before, lifted `--glass-shadow`) and `--spring-liquid` (overshoot cubic-bezier(.34,1.56,.64,1)) for entrances/menus/presses. `.gui-dialog` is the reference implementation (translucent 72% surface + blur(3xl) saturate(170%); ::before is the sheen layer — keep content z-index above it). Accent-color changes do NOT affect the glass ladder; the semantic greens (success/pet) stay green.

## 3. Motion standard (core standard, finalized 2026-08-06)

| Scenario | Component | Mechanism |
|---|---|---|
| Conditional block (visibility follows another option) | `<Reveal open>` (`components/Reveal.tsx`) | useCollapse px-height 240ms `cubic-bezier(0.22,1,0.36,1)` + outer 160ms fade-in; closed state `aria-hidden`+`inert`; node stays mounted |
| Stays mounted but changes height (tab switches/list growth) | `<HeightMorph morphKey>` (`components/HeightMorph.tsx`) | Capture old height at render → commit new content → height transition → settle `auto`; same outer 160ms fade-in restarts per key; **during the morph the container clips content with `overflow:hidden`, otherwise new content instantly fills (overflow pins the short box) and you only see box edges moving = "no animation"; restored after settle**; when height is unchanged (`|target-prev|<1`, e.g. the fixed-height scroll container of settings section switches) skip pinning/clipping and keep only the fade — otherwise the scrollbar vanishes 300ms and scrolling gets disabled; **duration adapts to height delta 240→480ms (`delta/6` capped) — the ease-out curve is extremely front-loaded, so even a fixed 240ms large expansion (e.g. the 2200px provider grid) still reads as a quick pop** |

- **HeightMorph iron rules**: children render directly into the ref-carrying outer element, **never wrap an intermediate div** — callers pass their own layout classes (`.gui-provider-grid` is a CSS grid); a wrapper becomes the grid's only child and stacks everything single-column (lesson from 70 cards at 4234px pseudo-smooth). `display:contents` is an alternative fix but the fade won't render. **Morphs must clip** (see table above) — the provider "show all" expansion reveals cards progressively (8→40→56→…→70), not cards popping in at once.
- **Forbidden** to collapse via `grid-template-rows: 0fr↔1fr` (Chromium one-way animation issue documented in useCollapse).
- Settings-section switching is a fixed-height scroll container; HeightMorph contributes only the fade.
- Timing conventions: height/morph 240ms + `cubic-bezier(0.22,1,0.36,1)`; fades 160ms ease; KITT sweep 1.7s same easing alternate.
- Application sites: SettingsView conditional items (theme branch/glass slider/sweep color), model inner tabs, provider-grid "show all", settings section switching, SessionSidebar group/project blocks, CustomGroups.

## 3a. Status transition standard (2026-11-07)

State copy is a **fixed slot**, not a block that appears and disappears. `StatusText` (`packages/client-core/src/components/shell/StatusText.tsx`, shared CSS in `shell.css`) is the single implementation: outgoing and incoming strings share one grid cell and cross-fade via `gui-status-out` / `gui-status-in` at `--gui-motion-fade-out` / `--gui-motion-fade-in` (160ms) with `--gui-motion-slide-y` (6px); `gui-motion-off` and `prefers-reduced-motion` swap instantly with no leaving layer. The wrapper owns `role="status"` + `aria-live="polite"`, the leaving copy is `aria-hidden`, and `text: null` clears the line. No remount of the surrounding layout, no height jump, no blink.

- **One timer per state, never one cumulative timer.** Entering a new state restarts its window; time spent in earlier states is not charged to the new one. Declare the budget next to the state so a costly step is not judged by a cheap step's threshold. A phase-independent backstop may exist, but it must be far longer than any single budget.
- **Three levels, one escalation path**: `normal` → `slow` → `stalled`. `slow` is informational ("still working") and never names a failure, guesses a cause, or shows recovery controls. Only `stalled` may say the daemon is stuck and offer Export diagnostics / Restart. A normal wait must never read as an error.
- **Copy describes the current state, not the user's patience.** Status lines report what is running; exception lines report what stopped. A cumulative clock must not turn a progressing operation into a diagnosis.

**Startup splash** (`StartupSplash.tsx` / `useBootStatus`) is the reference application: `probe` / `spawn` / `gate` / `connect` each own a budget (`BOOT_TIMINGS.budgets`: 8s / 20s / 15s / 8s), both thresholds reset on every phase change, and a phase stalled past `budget + 15s` — or a boot past 60s — escalates to `stalled`. Phase and notice are two `StatusText` slots in a fixed-width centered column, so a normal multi-second version gate shows only its phase and, later, the informational note, never "the local daemon may be stuck".

- **Default companion: the builtin spherical brand pet (2026-11-05)**: `DEFAULT_COMPANION_ART_ID = BUILTIN_VECTOR_ART_ID` (`musepi-note-bot`) is the hand-drawn sphere in the builtin branch of `CompanionArt.tsx` — `.gui-pet-svg__shell` plus the `lib/companion-face.ts` layers (eye tracking, blink, the 31-state moods), the `lib/companion-decor.ts` `headphones` accessory, and the `pet-gesture` press/drag rig; the `happy` rings of that face are also the expression of the app/site logo mark. That rig composes with the session's authored motion, interaction expression and gaze.
- **Explicit-state atlases**: an imported `format:"atlas"` package declares its frame geometry and named rows instead of being forced into the legacy 8×9 grid. The standard rows are `idle`, `running_left`, `running_right`, `working`, `waiting`, `failed`, `idle_random_1` and `idle_random_2`; additional named rows are one-shot actions played by a desktop double-click without replacing a standard state. Dragging selects the authored direction rather than mirroring it again, idle actions return to the live session row on completion, and pointer/sleep/session states retain priority. A package may also supply a muted bubble palette; it is used only with three six-digit hex colors and at least 4.5:1 foreground/background contrast, while error/question semantics and the default glass geometry remain application-owned.
- **Size normalization & scaling** (2026-08-06): all Petdex companions render normalized to **rest-row content height** (`PET_CONTENT_TARGET_H = 100`, k = 100/contentH) — imported packs vary in frame size (Doraemon 192×208 vs built-in 96×104); without normalization everything doubles in size and shadows overflow the canvas. contentH sources: built-ins use the measured-hardcoded `BUILTIN_SPRITE_PRESETS.contentH`; imported packs measure at import via `measurePetdex()`; legacy packs are backfilled automatically by `migratePetdexContent()` (at useCompanionArt mount). **Companion size slider** (Settings → Companion, `musepi-gui-pet-scale` 60–150%, default 100) multiplies on top of normalization; the desktop pet window receives scale via the main-window bridge `pet-activity {scale}` (cross-window localStorage unreliable), the in-composer pet reads the pref directly.
- **Window & shadow bounds**: the pet window is a fixed 320×290 box (`PET_WINDOW_SIZE`), with the companion anchored `bottom: 52px` and enough room for its drop shadows. It contains the sprite and the single bubble mode/count control. Conversation cards live in a separate, content-sized `bubbles.html` window whose bottom sits 8px above the sprite, clamped to the current work area and moved with the pet. An empty stack hides that window. There is no single-click interaction panel.
- **Bubble stack**: transient notifications are capped at 5 (`MAX_VISIBLE_BUBBLES`); non-question notifications auto-dismiss after 8s. Cards have a 20px radius, self-drawn glass faces and a width+height stack morph. The three modes are `stacked` (the priority card plus an "N more" chip), `expanded` (the full list) and `hidden` (only the pet-side count control). Clicking a stacked card body expands it; clicking an expanded card body opens its session and keeps the list expanded, while a notification opens the main window. The separate ↗ action opens the session or main window. Reply, open, approve, deny, stop, dismiss and clear actions do not activate the card body. The pet-side control is the only mode switch and steps `expanded → stacked → hidden → stacked`.
- **Bubble notification lifecycle**: a genuinely new done/error activity or actionable request moves to the front once; repeated snapshots retain the current priority and never reopen count mode. Dismissal is remembered per session activity revision or request id, so an unchanged activity stays dismissed while a later turn may appear again. The ✓ action on a finished session card marks that conversation read in the main window, synchronizing reminders, the sidebar and the pet badge. Dismissing one card with × or clearing the list affects only local bubbles: it does not mark conversations read and never approves or denies a request. Every approval requires an explicit decision.
- **Bubble material and motion**: cards, decorative backs, the clear capsule, quick actions, reply field and count surfaces reuse the shared `--glass-*` material. The collapsed stack renders inert near/far backs with the same layout size as the 320px priority card. The 344px outer stack leaves 12px of shadow clearance on each side, keeping the fixed-width window and controls unclipped. Width/height morphs and entrances use `--spring-liquid`; short control reactions use `--spring-snappy`. Reduced motion shows complete text immediately and skips entrance and size-morph animation.
- **Primary-session visibility**: pet bubbles, tray session entries and welcome reminders list primary sessions only; advisor and subagent sessions stay hidden. Skipping an auxiliary tree node does not hide its primary descendants, and approval collection still covers auxiliary sessions.
- **Onboarding personalization uses live companion previews**: the vector orb is the first option, followed by built-in Petdex presets and imported packages. Each option renders its real `CompanionArt`; gloss and accessory controls apply only to the vector orb. The right-hand preview follows the selected companion and decoration. Input mode shows the docked composer companion; desktop mode shows the independent companion with a glass bubble.
- **Bubble quick actions**: hovering or keyboard-focusing a card reveals its actions in one horizontal row. The row sizes to its actual button count, including the persistent actions on unread cards, without changing the bubble window's fixed width.
- **Bubble kind differentiation**: `bubble.kind` (`completed`/`error`/`question`/`subtask`, `lib/companion.ts`) sets the `--pet-kind` color for the uppercase kind tag (`.pet-bubble__kind`, zh/en i18n `pet bubble kind *`). Cards have no left accent stripe or padding reserved for one. `error` and `question` additionally tint their borders (55% mix), and an unknown kind yields no tag rather than a misleading one.
- **Pet stays above normal windows, and gets out of the way of fullscreen (2026-09-19)**: the pet is a desktop companion, so it lives in the always-on-top band — but three behaviors define "well-behaved" here, and all three are user-visible. ① **It must not sink.** The z-order assertion is re-applied every 5s while the pet is visible, because Windows demotes the band on edge snaps and across sleep/wake and never restores it; the level is `pop-up-menu` (above taskbar-level UI), not `floating`. ② **It must not fight fullscreen.** When another app owns the screen — a game, a video, a presentation — the pet withdraws from the topmost band for the duration, and comes back when the app exits. This is the difference between a companion and an annoyance, and it must work for **other people's** apps, not just our own windows. The desktop itself is never "fullscreen": clicking the wallpaper, or Alt-Tabbing, must not banish the pet. ③ **It must come back.** A display unplugged, a DPI change, or a laptop waking from sleep must not strand the pet off-screen, invisibly cloaked, or at a wrong size (a maximized-looking pet that keeps growing on every sleep cycle is the failure users report as "it's broken"). After any of these, the pet returns to a sensible position **without** being moved if the user had deliberately parked it somewhere reachable — a DPI event is not permission to recenter a pet the user placed by hand.
- **Pet gestures and sleep**: a single click plays a greeting and raises the main window; a double-click plays a random interaction without repeating the previous pick. Session cards carry reply, stop, acknowledge and open actions; approval cards carry approve/deny actions and retain the global `Ctrl/Cmd+Shift+Y/N` hotkeys while pending. After 60s without a gesture or task activity, the sprite dims and floats "z z z" (`.pet-window__pet--sleeping`); any gesture or mood change wakes it.

## 5b. Animation & library choices (evaluated 2026-08-07)

- **Principle: CSS first + hand-rolled hooks**. The entire existing motion system is handwritten CSS/JS (Reveal/HeightMorph/useCollapse, BorderBeam, DotMatrixMark, ThinkingOrbs, the KITT sweep, two-phase float layers, companion frame animation) — desktop GUI motion needs are "refined, restrained UI feedback"; CSS transition/keyframes suffice at zero runtime cost and natively respect `prefers-reduced-motion` (the `gui-motion-off` preference).
- **Third-party in use**: `cuelume` (sound), `lucide-react`/`lucide` (icons), `morphicons` (composer send/stop icon morph), `beautiful-mermaid` (guest-client Mermaid rendering), `@xterm/xterm` (terminal), `EmbedPDF` (PDF). **motion (formerly Framer Motion) was a dependency with zero references — removed** (2026-08-07).
- **GSAP evaluation (not adopted)**: GSAP 3 (now entirely free, all plugins included) is the industry standard for imperative timelines/ScrollTrigger/SplitText/MotionPath — but its strengths (marketing-page scroll scenes, per-character text effects, complex multi-step orchestration) aren't on the desktop GUI core path; adopting it would establish a new animation paradigm (timelines/interpolation) running parallel to the existing CSS track. **Kept as a candidate**: re-evaluate if we later do welcome-page brand-text per-character animation (SplitText-class) or complex transition orchestration.
- **Icon transitions = morphicons, hand-drawn crossfades forbidden (lesson 2026-08-14)**: any "icon A → icon B" transition (theme/accent full-screen masks, button state swaps, status cards) uses **`morphicons`** exclusively (`morphicons/react`'s `MorphIcon`, or in pure-DOM contexts `morphicons/element`'s `<morph-icon>` + `set()`/`morphTo(target, "snappy")`) — **shape morphing via Procrustes optimal rotation + polar interpolation + spring physics**. **Forbidden**: stacking two SVGs and faking a morph with opacity/rotate crossfade (misused on the 2026-08-14 theme mask; the user explicitly demanded the morphicons look; Composer/Transcript/onboarding steps are already all morphicons — the mask must match).
- **Store change notifications must emit inside the swap callback (lesson 2026-08-14)**: `setThemePreference`/`setAccentPreference` execute the switch delayed (340ms) via `withColorTransition` — **`emit()`/`emitAccent()` must live inside `withColorTransition(fn)`'s `fn`** (after preference/accent have been updated), not after the call: emitting synchronously outside broadcasts the **old value**, so `useSyncExternalStore` subscribers (settings segmented/palette buttons) read the old preference — button state **lags one click** (you clicked light, the theme switched, the button still says "follow system"; the next click displays the previous choice).
- **React Bits evaluation (source reference, no package installs)**: 140+ open-source animation components (MIT family, github.com/DavidHDev/react-bits). Consistent with our existing "borrow patterns from reference repos" workflow — candidates (copy on demand): `BlurText`/`ShinyText` (welcome brand text), `CountUp` (rolling numbers: status-bar tokens/stats), `SpotlightCard` (settings-card hover glow), `Aurora`/`Particles` (welcome-background alternatives; the existing DotMatrixMark takes priority). BorderBeam we already have self-built (referencing opencode); reactbits' version works for parameter comparison.

## 5f. Design asset extension points (pluggable, finalized 2026-08-16)

Built-in design assets are organized around **tokens + an override mechanism**; third-party/theme/motion packs extend by overriding tokens, never by forking components.

### Motion parameter table (gui.css `:root`)

| Token | Default | Purpose | How to override |
|---|---|---|---|
| `--spring` / `--spring-snappy` / `--spring-bouncy` | spring(300,30)/(400,34)/(320,16) linear() | All UI morph easings | Inject CSS overriding the `:root` variables |
| `--gui-motion-menu-in/out` | 130ms | Float-layer menu enter/exit | Same |
| `--gui-motion-chip` | 180ms | Chips/small elements | Same |
| `--gui-motion-fade-in/out` | 160ms | Fades | Same |
| `--gui-motion-height` / `-max` | 240ms / 480ms | Height morphs (HeightMorph, delta/6 capped) | Same |
| `--gui-motion-blur` | 280ms | Blur-type effects (BlurText) | Same |
| `--gui-motion-roll` | 240ms | Roll/page-flip type | Same |
| `--gui-motion-slide-y` / `-lg` | 6px / 10px | Translation distances | Same |
| `--gui-motion-blur-amt` / `-lg` | 8px / 24px | Blur amounts | Same |
| `--gui-ease-out` | cubic-bezier(0.22,1,0.36,1) | Height/morph easing alias | Same |

**Override mechanism**: keyframes and transitions always read tokens (`var(--gui-motion-*)`); a motion pack/theme injects a stylesheet (later-loaded wins) overriding the variables for a whole-skin swap — no keyframe edits needed. `gui-motion-off` (prefers-reduced-motion) disables globally.

### Component parameterization (customizable without forking)

- `BlurText` (`stepMs`/className), `ShinyText` (`speed`/`spread`/`shineColor`), `CountUp` (`duration`/`format`), `SlidingNumber` (`padStart`/`decimals`), `TextMorph` (`stepMs`/`durationMs`), `GuiSelect` (options/className), `SpotlightCard` (`spotlightColor`)
- Glass layers: `--gui-glass-alpha` (transparency slider) + derived `--gui-glass-overlay`; `.gui-main`/floating-card blur reads platform classes (`[data-platform="win32"]` disables the underlying blur, see the performance section)

### Intake contract for new motion components

1. Durations/offsets/blur amounts **must read tokens**; bare values forbidden (bare values = uncapturable by theme/motion packs).
2. Enter animations go two-phase (`useTwoPhaseEnter`, or `opacity:0` + next-frame `--entered`) to prevent Chromium skipping backdrop sampling.
3. Respect `gui-motion-off` (disabled state appears directly, no animation).
4. Reuse the `gui-menu-in/out` / `gui-fade-in/out` keyframes or build same-parameter ones (named `gui-<name>-in/out`).

## 5e. Dialogs, keyboard & selectors (finalized 2026-08-14)

### Dialog animation & keyboard priority

- **DialogFrame contract**: hosts render **unconditionally** + driven by `open` (`{x && <DialogFrame/>}` conditional mounting loses the exit animation — the 180ms closing phase); prompt/confirm (`lib/prompt-dialog.tsx`) use the same two-phase enter + closing; `finish()` resolves the promise only after the exit animation completes.
- **Modals hold the keyboard**: while a DialogFrame is open, Esc is listened for on `document` in the **capture phase** → onClose (wins over handlers beneath; the composer stops swallowing Enter-to-send); focus moves into the dialog's first focusable element and restores on close; confirm boxes: Enter = confirm (focus lands on the confirm button); onboarding panels: Enter = next step (a focused input keeps its own Enter), Esc = previous step/close from the first step, panel focuses itself on open; announcement panels: Esc = close.
- **Compact dialogs**: small-content confirmation boxes use `gui-dialog--confirm` (auto size + max-width 380 + 22×24 padding) — the base `.gui-dialog` is a 600×420 settings box; desc + two buttons inside reads broken (board delete / new project / scheduled delete all tripped on this).
- **Hooks iron rule**: all hook declarations must precede **any early return** (hooks after `if (!open) return null` crash with "Rendered more hooks than during the previous render" when open toggles — AnnouncementOverlay regression, observed live).

### Floating positioning standard (finalized 2026-08-25, benchmarked against openchamber v1.20.0)

**Single-entry iron rule**: all popup float layers (menus/dropdowns/context menus/color pickers/attachment menus) must route through `components/Pop.tsx` → `lib/use-floating-menu.tsx` (the only implementation: portal to React root + global exclusivity + `gui-menu-in/out` animation). **Hand-written `position: fixed/absolute` popup floats are forbidden** — openchamber uses @base-ui/react (floating-ui popper engine internally); we hand-write the same semantics without the dependency:

- **Collision semantics (flip + shift)**: vertical = flip upward when it doesn't fit below the anchor (or more room above) (flip); horizontal = shift wholly into the viewport on left/right overflow (clamped to `[8, innerWidth − menuW − 8]`, shift never flips) — right-aligned menus pin their right edge to the anchor's right edge and nudge right to survive tight spaces instead of being truncated by window edges.
- **Two-phase measurement**: at first open the menu isn't mounted yet → estimate position at 260×300 → re-measure `offsetWidth/Height` once on the mount frame for exact repositioning (`measuredRef` guards loops); right-aligned menus therefore still land precisely on the anchor.
- **Vertical flip accounts for height**: `flipUpForBottomOverflow = r.bottom + 6 + menuH > innerHeight − 8` — tall menus hanging under low anchors flip up too; bottom overflow is never allowed.
- **Persistent floating cards (non-popups)**: fixed corner cards like the btw ask-card/badge cards must clamp themselves to the viewport (`maxWidth: calc(100vw − 48px)` + `max-height: min(60vh,520px)` + body scrolling); bare boundary-less fixed is forbidden.
- **Keyboard**: floating cards/menus must wire their Esc promises (e.g. the btw card's "Esc closes" hint ↔ onKeyDown Escape); hints and behavior must not diverge.
- **Three requirements (finalized 2026-10-18)** — every floating layer must satisfy all three before merge:
  1. **Dismissable**: outside click and Escape both close it, and Escape must `preventDefault` to claim the key (an unclaimed Escape leaks into the window-level bare-Esc binding and interrupts the running turn).
  2. **Viewport-fitting**: flip/shift/max-height clamp — never off-window, always internal scroll rather than truncation.
  3. **Unclipped**: it escapes every `overflow` / `transform` / `backdrop-filter` ancestor (i.e. it portals) and is never covered by a neighbouring element.
- **"Clipped" is this component family's dominant failure, and it is not a styling mistake**: `.gui-right-rail` is a 44px card with `overflow: hidden` (a rounded card must clip, or children spill past its corners); any `position: absolute` layer drawn inside it is clipped away whole. The cause is not one component's "wrong property" but the **clipping container + absolutely-positioned child** combination, which must not exist at all. Two hard rules:
  - **The floating shell (`.gui-menu-popup`) owns position (`position/top/right/z-index/animation`); the content class owns internal layout only** (`display/gap/min-width/padding`). The shell's inline `position: fixed` is what lifts the layer out of the clipping tree. Precedent in the same family: `.gui-context-menu` / `.gui-select-menu`.
  - **A trigger docked to the window edge must open toward the space it has.** The right-edge rail's layer must use `side: "left"` (`useFloatingMenu`) and fly out leftward. Opening downward gets clamped to a sliver by the viewport shift — a second, independent defect from the clip: fixing the portal alone still leaves it unusable.
- **How dsh / openchamber handle it (surveyed 2026-10-18)**: dsh's `Menu`/`Tooltip` are **in-place `absolute` by default** and rely on each call site passing an explicit `portal` to escape a clipping tree — so every call site that forgets is a latent clip bug (its `TabMenu.tsx` comment exists to record exactly this). openchamber uses Base UI, where `Portal` is structural and a call site cannot get it wrong. **We align with openchamber**: `useFloatingMenu` portals unconditionally, so a call site neither needs nor can forget a `portal` flag. Neither repo has a mechanical gate that catches an in-place layer being clipped (dsh only has an AST test requiring `role=menu/listbox` to sit inside `MenuSurface`).

> **Scope clarification (2026-09-14)**: the "hand-write the same semantics, no dependency" rule applies **only to float-layer positioning** — floating-ui's flip/shift/clamp semantics are small enough to reproduce exactly with CSS + measurement, and are deeply coupled to the `gui-menu-in/out` two-phase entry. **Drag-and-drop sorting is NOT covered by that rule**: choose **pragmatically** — `@dnd-kit`'s sensor arbitration (pointer/keyboard activation thresholds), collision detection, accessibility (screen-reader reorder announcements) and nested containers are a genuine state machine; when a dependency solves that well, use it (openchamber aligns all 14 of its drag sites on it, section below); hand-write **only** when the interaction is so simple that a dependency would be dead weight (no ordering semantics, a one-off placement, pure one-axis pointer motion). Rule of thumb: the drag encodes an **order** that must persist → `@dnd-kit`; it just moves **this thing over there** → hand-written pointer capture.

### Drag-reorder spec (2026-09-14, openchamber parity)

Every openchamber drag (14 sites: model favorites/providers, context-rail surfaces, session tabs, draft-starter chips, queued-message chips, session folders/projects, TodosSection, mobile project/session sheets) uses `@dnd-kit`. Our order-encoding drags align on the same library:

- **Dependencies**: `@dnd-kit/core@6` + `@dnd-kit/sortable@10` + `@dnd-kit/utilities@3` (`@dnd-kit/modifiers@9` as needed), installed in `packages/desktop-app`.
- **Sensor conventions**: visible reorder uses `PointerSensor` with `activationConstraint: { distance: 8 }` (drag starts only after ≥8px of motion, so clicks never trigger it); whole-header drag uses `MouseSensor` distance 8; when keyboard sorting matters add `KeyboardSensor` + `sortableKeyboardCoordinates`.
- **Structure**: `DndContext` (sensors + `closestCenter` + `onDragEnd`) wrapping a `SortableContext` (`verticalListSortingStrategy` / `rectSortingStrategy`); rows via `useSortable` + `CSS.Transform.toString(transform)`; the drag handle is its own `<button>` carrying `attributes`/`listeners`, never the whole row — whole-row drag hijacks clicks when the row contains buttons/inputs. **Exception**: a bare icon button (the right-rail icon) holds no nested controls and may be the activator itself — the 8px threshold keeps a click a click.
- **Completion**: onDragEnd applies `arrayMove` and writes the **whole array** back to storage (localStorage or RPC); visual-only reorder that diverges from the backing store is forbidden.
- **Disabling**: when there is ≤1 item, set `draggable={false}` / skip rendering the handle; while a search filter is active, resolve by id against the **full array** (never splice the filtered subset — hidden items would be dropped).

### Right-rail interactions (openchamber ContextPanelRail parity, 2026-09-14)

- **Drag reorder**: full `@dnd-kit` stack (PointerSensor distance 8 + TouchSensor delay 200/tolerance 6); `arrayMove` resolves against the **full order** and writes it back to localStorage (`writeSurfaceOrder`). Extension-slot tabs (`ext:`) stay outside the SortableContext.
- **⌘/Ctrl hold reveals order numbers**: hold the modifier 500ms → the rail icons paint 1..N (matching the ⌘1..8 jump); releasing, losing focus, or actually pressing a digit consumes and dismisses them until the next hold. app.tsx owns the jump itself; the rail only visualizes the mapping.
- **Badges**: a live count (currently git changed-files, capped at 99+) takes precedence over the order number, which only appears during the modifier hold. The count is read into `aria-label` so screen readers announce it.
- **Rich tooltip**: every registry entry may carry a `description` (i18n key); hover and keyboard focus share a 150ms delay, while a stationary touch opens after 500ms and release dismisses it. One portal, owned by the rail (`RailTooltip`), prefers the icon's left but flips/shifts to remain inside the viewport and follows its anchor on scroll, wheel, and resize. It uses the shared tooltip layer, above the managed-browser page host. Window blur or a disconnected anchor closes it. Escape dismisses without moving focus; dragging suppresses it. Entry/exit is opacity-only and becomes immediate under reduced motion. Standard and rich tips share the L2 glass material without changing their established overlay levels.
- **No skin scrollbar on the rail**: the nav rail's scroller sets `data-gui-scrollbar="off"`, keeps `overflow-x: clip`, and relies on its own overflow fold/edge feather. The global snake/gummy rail must never paint over the icons or invent a horizontal thumb there. Snake/gummy built-in sizes are 10px/12px so the skin recedes behind content.
- **Not done**: the surface show/hide configuration dialog (openchamber's equalizer entry) — musepi's has-content auto-hide covers it and nobody asked.
- **Surface hide via rail (2026-10-15, openchamber absorption A2)**: right-click a rail icon → "Hide surface" (`ContextMenu`, no nested controls so the icon button stays the drag activator); hidden ids persist (`musepi-gui-right-hidden`) and are filtered from the rail, the ⌘1..8 jump (`app.tsx`), and stale-order backfill; an already-open panel is NOT yanked. Restore from the "…" overflow menu's "Show hidden surfaces" section (per-surface buttons; the overflow renders while hidden exist even with nothing folded). No equalizer dialog — right-click + overflow covers it.
- **One panel width (2026-11-04)**: the right panel is one workspace, so every tab shares `musepi-gui-right-width` (200–1200 clamp); switching tabs never resizes it. The first valid legacy value in `musepi-gui-right-widths` migrates into the shared key, and drag-end writes only the shared key. `ContextPanel` is the sole width owner.
- **Selected-session reveal (2026-11-04)**: selecting or creating a session expands its project and the ancestor-session chain that hides it (one reveal per selected id). Unrelated manually collapsed projects and subtrees stay collapsed, so navigation never behaves like “expand all”.
- **has-content fallback rule (2026-10-15, absorption A1, mechanism only)**: `surfaceVisible` without an explicit predicate falls back to open tabs (`openSurfaces` plumbed ChatView → RightRail → ctx); no built-in flipped yet — flips are one-line product decisions.
- **Rail and panel are shell-level (2026-11-08)**: the workspace row holds the scene stack (welcome or chat), the panel shell and the rail as siblings, so the rail survives the scene swap and the welcome screen keeps it (OpenChamber layout parity). The panel opens there onto its zero-tab page. Registry descriptors may set `requiresSession`; without a session the rail hides those surfaces, while the empty-state page and the "+" menu list them disabled with a `general.sessionRequired` hint. The pre-session tab set is keyed by the selected project, and creating a session starts a session-keyed set (workspace tabs do not migrate).

### Model selector (provider compound key)

- **Model identity = `provider/id`**, never the bare id — two providers can expose the same bare id (opencode-go / opencode-zen both ship `deepseek-v4-flash`): favorites (`musepi-gui-fav-models`), the DEFAULT pin (`modelRoles.default`), selection state, and role-row assignment are all keyed by `provider/id` (legacy bare-id entries match compatibly and are cleaned up on toggle); `session.setModel` carries `provider` so the daemon resolves precisely (daemon-side provider-scoped lookup added).

### Fetch available models (custom provider form)

- **Config surface shape**: adding a custom provider is a **properly designed dialog** (DialogFrame, `gui-dialog--settings`), opened from "Add custom provider" inside the "Custom Providers" tab — **not a standalone tab** (user feedback: adding a custom provider belongs in a designed dialog; the old add-tab was removed). Once Base URL and API protocol (openai-completions / openai-responses) are set, press "Fetch available models" — **only OpenAI-compatible protocols can be queried**: anthropic-messages / google-generative-ai expose no readable model list; the error guides manual entry (same philosophy as DSH discover-models: a one-time query against the draft during configuration, writes nothing anywhere). **The onboarding (OnboardingOverlay ProviderSetup) custom form offers the same "Fetch available models"** — no hand-typing model ids.
- **Query-is-draft**: RPC params = the form's current values (baseUrl/api/apiKey/provider name); **the apiKey serves this one query only — the daemon never persists it**; without a baseUrl the button is disabled with the hover hint "Fill in Base URL first".
- **Candidates dialog** (DialogFrame, permanently mounted, driven by `candidates !== null`, nested inside the config dialog): checkbox list (id + name, endpoint order) + select-all/deselect-all ("Deselect all" while all selected) + "Add selected"; adopted candidates merge into the form's model list (`adopted`), each row deletable; errors (protocol unsupported/401/404/endpoint has no models) display inline beneath the button, never a dialog.
- **Submit semantics**: the `models.add` models array = adopted list merged with the manually entered single entry (modelId/modelName/compactionModel); validation changed to "provider name, Base URL, and at least one model required" — the single entry and the adopted list must satisfy at least one.
- **Success feedback**: saving closes the dialog and returns to the "Custom Providers" tab, briefly showing "Provider added" at the add button's original spot (dismisses after 2.5s); onboarding shows the added card.

### Board canvas & group glow

- **Canvas adaptation**: `.gui-board-surface` layout width is fixed at BASE_W (1092), fitted to the window via `transform: scale(containerWidth/1092)`; the effect depends on `activeId` (home-view ref null at mount → deps `[]` left the scale stuck at 1 forever, the 1092 layout overflowing clipped — fixed); `overflow-x: hidden` + `overflow-y: auto` (transforms don't change layout; narrow windows would otherwise show horizontal-scrollbar artifacts).

- **OTA update UI**: "Check for updates" (§4) upgraded from "Go to download" (openExternal) to **download → progress → restart** via electron-updater (v0.4.4) — `docs/archive/ota-update-design.md`; the toast now shows percent + "Restart now". Notes channels unchanged: toast reads `update-manifest.json.notes`, "What's new" reads `CHANGELOG.musepi.md`.
- **Bilingual docs convention** (`docs/i18n/README.md`): every in-scope `docs/**` markdown pairs `foo.md` + `foo.zh-CN.md` + `foo.i18n.yaml` (blob-hash consistency record); language switcher after the heading (`English | [中文](foo.zh-CN.md)` / `[English](foo.md) | 中文`); enforced by `bun run verify-translation-pairing` (`--write` records hashes; strict for named pairs); the two languages hold equal authority and structure mirrors across the pair.
- **SketchPad Codex parity** (2026-09-19): the board gained a **text tool** (a real `<textarea>` overlay positioned in canvas pixels — IME/paste/selection behave natively; the label lands as a Konva `Text` on blur or on arming another tool, so a pending caret is never lost), a **shape flyout** replacing the two flat line/arrow buttons (line/arrow/rect/ellipse/diamond/triangle/star/heart in a 4-column glass popover; the rail button shows the *armed* shape's glyph so rect vs diamond stays legible), a **12-swatch palette**, and a **continuous thickness slider** (1–24) that replaced the four-step 2/4/8/14 ladder. **All geometry moved to `lib/sketch-geometry.ts`** — drag normalization, star/heart point generation, text metrics, hit extents — because Konva cannot be asserted against without a canvas; `test/sketch-geometry.test.ts` (42 tests) covers it. Board chrome joined the **liquid-glass + spring standard**: translucent 78% surface + `blur(3xl) saturate(170%)`, `--glass-sheen` on an unclaimed `::before`, `--glass-shadow`, and a 240ms `--spring-liquid` entrance (the 180ms `--spring` scale-out on close is unchanged, so the board still reads as falling back into the composer). Every visual `position`/`transform` here is one-owner (board entrance owns the keyframe; the veil only fades).
- **A board-drawn chip reopens A0, never a copy of A1** (2026-09-20): the interaction rule is *continuity of the drawing*, not *an image you can draw on*. 完成 emits the PNG that goes into the message **and** the board's stroke list (a `scene`, `lib/sketch-scene.ts`); the chip keeps both, so clicking it restores the objects — each still selectable, movable, scalable and erasable — and a re-edit fixes the specific stroke the user means. The old behaviour (mount the exported PNG as the base layer) made the board's own output immutable in one step: every later edit could only stack paint on a raster, which is why it read as "just a pasted picture". The scene is also what keeps the round trip closed — 完成 swaps pixels *and* scene, so the tenth re-edit is as editable as the first. Degradation is one-way and invisible: a chip that lost its scene (restored draft, pre-change data) opens as the old flat base layer rather than refusing to open.
- **A text label behaves like a shape, not like a caption** (2026-09-20): the rule is *one object model*, so text gets no privileges and no exemptions. It wraps and grows taller as you type (the label owns a real box; its height follows the wrapped line count), it resizes from the same four corner handles as a rect or an image, and a single click selects and drags it exactly like anything else — editing is the **double-click**, because "click a label to place the caret" made text the one object on the board you could not move. The invariant worth keeping: the text you see and the box that selection draws are measured by one shared line-height, so a widening selection frame can never disagree with the glyphs inside it.
- **Measure text, never estimate it — and respect the width the user chose** (2026-09-20): two rules that together make a text box feel like an object rather than a guess. (1) A label's box is sized from **real canvas metrics**, because any fixed per-character factor is a statement about one script: an estimate tuned for Latin under-measures CJK by ~1.6× and silently clips Chinese labels down to their first few glyphs. (2) When the user drags a box to a width, that width is kept — text wraps inside it and the box does not spring back to fit its own content, because a size the user set by hand must never be quietly overruled. The only exception is a line that cannot fit at all, where the box widens rather than hiding glyphs.
- **System screenshot editor** (2026-11-13): both composers' captures open as a full-bleed annotator rather than a dialog. A transparent header carries the original pixel size, preview zoom, HEX/RGBA and select-all; the shot owns the stage; one floating glass pill holds crop, pen, arrow, rectangle, ellipse, text, mosaic, eraser and eyedropper, with undo/redo/clear and a contextual palette plus stroke slider. 1. **model prop 接线（已落地）**：`<Transcript model={snap.state.model ? provider/id : undefined}>`（`ChatView.tsx`），与 DetailsPanel 同一 compound key 约定；render-units 语义取 turn 内最后一个 model_change，轮内切换仍显示实际产出回复的模型。缺省（无 snap）时 header 不显示模型段。
2. **审批等待反馈——等价物映射，不照搬**：guest-client 用 ApprovalCard 底部 accent 进度线；desktop 的 ApprovalCard 已有 pulse border beam（`BorderBeam`）+ 提示音，且 ChatView 有 "paused for you" wave 语义（审批 pin waiting）。设计裁决：**desktop 保持 beam/wave 现状**，进度线不跨面照搬——两个面各自已有"卡片承担进度反馈"的实现，语义同构即可，视觉允许面差。
3. **loading 收敛**：desktop Composer 无 guest 式聊天 loading pill，工作态指示走 `snap.working` 既有链路；M1.2 的抑制矩阵（审批/ask/compact 期间抑制聊天 loading）在 desktop 无对应物可抑制，记为无需移植，仅保留语义对照（`docs/archive/0.5.0-m1-transcript-design.md` §B 判定表）。

**M1.3 滚动锚定**：将落在共享 `Transcript` 组件内（现有 followKey/lockRef 机制上补 timelineScrollAnchor 语义），一处落地 guest + desktop 两面同时生效，不设 desktop 单独验收。

**液态玻璃统一（roadmap M1.10 前置说明）**：turn header/折叠段 CSS（`.tr-turn-head`/`.tr-seg` 系列）已在 guest-client transcript.css 内以液态玻璃 token（`--glass-*`）实现，desktop 随包继承同一套样式；M1.10 的全产品统一设计稿将以 guest-client tokens.css 暗色段 + desktop gui.css 液态玻璃段为双基准做映射，不动本章节组件语义。

**验收**：desktop-app `tsgo --noEmit` + biome 全绿（已达成）；人工走查：折叠态/展开态/审批等待三视图（desktop 真机 daemon 会话）。

## 5r. 轮渲染视觉语言（M1，评审稿 2026-09-21 转正，源 `docs/archive/0.5.0-m1-transcript-design.md`）

参照 ZCode v4 轮渲染单元语义（`zcode/packages/ui/src/v4/conversationTurnRenderUnits.ts`）。**设计基线**：全部视觉值取自 `packages/client-core/src/styles/tokens.css` 暗色段，禁止发明新 token；品牌 accent #d9a441 金禁止改。

**轮结构（`ConversationTurnRenderUnit` 对齐）**：

```
turn
├── turn header        轻边界：turn 序号 · 模型 · 时间 · 聚合状态(✓/进行中 + 耗时)
├── user bubble        现有 tr-user 语言
├── workSegments[]     语义折叠单元（核心新增）
│    折叠态(默认历史)  单行：chevron + 段摘要 + 工具数 + 段状态 + 段耗时
│    展开态            工具行全序列表（各自状态+耗时）
├── latestAssistantTextRow  轮尾最终正文（复制/重试/分支操作栏）
├── tail rows          重试失败 / 异步结果 / token 用量 —— 永不进折叠
└── hookInvocations    hook 行（mono 细条 + 左边线）—— 永不进折叠
```

**折叠边界规则**：① 段划分 = 原始输入 + 每条 accepted guide 各一段（ZCode `workSegments` 语义），段内保持 CLI row 全序；② 历史轮一律折叠，当前轮工作段默认展开随流式追加；③ 聚合状态取段内最差（任一 err → err；否则 running；否则 ✓），耗时为段内工具耗时之和；④ 折叠的是"工作过程"不是"信息"——latestAssistantTextRow / tail rows / hook 行 / 用户气泡一律不参与折叠；⑤ 展开/收起 `--spring-liquid` 0.25s，chevron 旋转同步。与既有 pre-compaction 折叠（`collapseCompacted`，按时间切）独立共存。

**IRC 流量行（`irc:*`）**：每条消息一行，不并入工作段折叠。路由（`from → to`）由 `details` 组成，`content` 里的 `[IRC …]` 头与 incoming 的 `<irc>` 模板都不渲染；三种 kind 只差视觉权重——`relay`（旁观的双方流量）最轻，`incoming` 读作发给当前会话，`autoreply` 带 `auto` / `reply` 标签。同一对 agent 的连续消息共享一次路由头，正文超过 3 行截断并提供显式展开——一段往返问答不再逐条重复发言人。展开/收起复用共享 collapse morph：clamp 在开始展开时摘下、收起结束后再挂回，高度按 220ms `--spring` 过渡，不会瞬跳。

**后台任务结算卡（`async-job-result`）**：L1 卡片（复用 `.tr-async-result` 外壳），头行是状态字形（✓ / ✕ / ⊘，按 completed / failed / cancelled 取色）+ agent 名 + `[type]` + 时长 + 状态文字 + 行数/体积；`<output>` 是 JSON 对象时按字段渲染（字符串值解码换行），其余按等宽正文；超过 8 行截断并淡出，展开/收起走同一 collapse morph；尾部 idle / `history://` 提示降为一行 faint 文本。卡片只表达"这个 job 结算了"，运行中的实时状态仍由右侧子代理面板承担，不在这里重复。

**过程行的折叠锚点**：思考块、活动/运行汇总与工具卡片共用左侧折叠字形（`.tr-round-fold-icon` / 前置 `.tv-chev`）；思考块流式输出显示「思考中」，结束后显示「思考过程 · 时长」或「思考完成」。后台完成卡改为用户侧锚定（右对齐、与用户气泡同右缘），卡片头即折叠锚点，输出/payload 可整体收起。

**运行中后台任务 HUD（`AsyncJobBar`）**：会话有运行中的 job 时，输入框上方出现一张卡片，逐行列出命令、状态点、实时时长、取消与详情入口；收起后只留「后台 Bash · N」chip。桌面端点详情打开右侧「后台任务」surface（`JobsPane`：运行/全部过滤、实时输出尾部、取消）；web / Android / 鸿蒙没有右侧面板宿主时，同一卡片就地展开详情 sheet。读数只来自 `session.jobs` / `session.jobOutput` / `session.jobsCancel`，1s 轮询且仅在文档可见时进行；没有运行中的 job 时组件不渲染，也不轮询。

**设置开关（2026-09-26 补齐，Kimi Code 桌面端 parity，入口：外观 → 聊天设置）**：

- **消息自动折叠**（默认开）：回合完成（非流式 in-flight）时该轮工作段自动收为折叠态、仅展示总结——这是 §5r 折叠的默认行为，开关控制渲染默认态（`defaultRoundFoldExpanded` 取反，纯渲染偏好，不改折叠内核）。**流式中当前轮永不收**（in-flight 轮豁免，`working` 边界同 `buildRoundFolds`）。关闭 = 已完成轮的活动摘要默认展开、逐条呈现工具过程。存储键沿用 `musepi-gui-chat-roundfold` 的反义映射（键语义仍是"默认展开"），原「活动默认展开」开关由此替换，旧设置值无缝迁移、无需新存储通道。
- **工具调用汇总**（默认开，键 `musepi-gui-chat-toolsummary`）：回合内 ≥2 次连续工具动作（toolResult / bashExecution 行，按 `classifyTranscriptRow` 的 work 口径）聚合为**一行摘要**——`读取了 N 个文件 · 编辑了 N 个文件 · 运行了 N 个命令`（按工具类别聚合计数，i18n 双档；纯函数 `round-collapse.buildToolRuns`，摘要行 `.tr-run-summary` 复用 `.tr-round-fold` 的 token 语言）。单次工具调用不汇总（自有卡片已足够）；摘要行点击展开该段的完整行序、再点收回（折叠的是过程不是信息，展开态必须可回）；流式中延伸到条目末尾的 run 保持逐条（spinner 即进度，§D），已完结的 run 照常汇总；关闭 = 现状逐条渲染工具卡。与消息自动折叠正交：折叠关闭态由 活动 头承担摘要，汇总行只在展开态/当前轮生效。

**loading 可见性（判定表）**：权限确认 pending → 聊天 loading 隐藏，由 ApprovalCard 进度线承担（2px，`--glass-border` 轨道 + accent 40% 滑块，`plslide 1.6s var(--spring-liquid)` 无限，文案"等待用户决定"）；AskUserQuestion pending → 提问卡自身承担；compact 进行中 → compaction divider 承担；goalVerifier 活跃 → verifier 卡片承担（挂接点待确认）；正常流式 → 显示；pending resolve 后恢复。

**tail/hook 行**：tail rows 保持 CLI 全序原位渲染，chip 用 `--glass-bg-strong` + inset rim；hook 行 turn-local，mono 细条 + 2px 左边线（`--glass-border`），`hook 名 · 事件 · 耗时`，hover 出详情——永不并入工作段折叠（hook 是轮的"事后审计信息"）。

**流式进行态（D）**：turn header 圆点 accent + 旋转 spinner + "进行中"，耗时 `…`；当前轮工作段 `.tr-seg--open.tr-seg--live`（`--glass-bg-strong` 底，与历史段 `--glass-bg` 区分）；进行中工具行 spinner + `…`，完成立即转 ✓ + 实际耗时；滚动锚定视口钉在 `latestAssistantTextRow` 末行；流式 caret 8px×1.1em accent 块 0.9s steps(2)。

**遗留决策点**（随实现推进裁定，未裁定前按现状执行）：① turn header 是否保留模型名段（多模型场景有用，单模型是噪声——现状：接线后缺省不显示）；② 段摘要的 i18n 模板句 vs 规则拼接；③ token 用量行 settings 开关；④ hook 行是否默认聚合 "N 个 hook · 展开"。

## 5s. 液态玻璃材质与动效语言——全产品视觉总纲（M1.10，评审稿 2026-09-21 转正，源 `docs/archive/0.5.0-m1.10-liquid-glass.md`）

> 总纲：**整个产品统一液态玻璃视觉与交互效果，动效丰富流畅，一镜到底。** 双基准：client-core `tokens.css`（web/安卓/desktop 共享渲染层，`--glass-*`/`--spring-liquid`）+ desktop-app `gui.css`（桌面壳，`--gui-motion-*`）。收敛方式是**单向映射层**而非合并词汇：desktop 壳保留 `--gui-motion-*`（motion-pack 皮肤机制是产品特性），取值与曲线锚定 client-core 玻璃语言；client-core 不引入 `--gui-motion-*`。

### 玻璃 = 四层配方（缺一不可，blur 缺席时后三层独立成立）

1. **底** `--glass-bg` / `--glass-bg-strong`（卡面 7% / 浮层 11%；亮色 55%/72%）
2. **缘** `--glass-border` + 内 rim（edge-hi 上缘高光 30% / edge-lo 下缘收 7%）——"液态"读感主要来自 rim 的 1px 高光，不是 blur
3. **泽** `--glass-sheen` 线性渐变（对角 45°，仅浮层/活动卡）
4. **影** `--glass-shadow` 双层（近环 + 远落地）

**层级表（新增组件必须按级取值，禁止跳级发明）**：L0 pane（滚动面板底/输入条：全无）/ L1 card（折叠段、消息卡、工具卡：底+缘）/ L2 float（ApprovalCard、TurnRail hover、回到底部钮、lightbox：强底+缘+rim+泽+近环）/ L3 overlay（对话框、GlobalPause、导览：双层全量）。

**活态**（玻璃随会话状态呼吸）：streaming/进行中 → rim 高光换 accent、底升 strong；审批等待 → 进度线（guest）/pulse beam（desktop）+ 底升 strong；冻结态回落 L1。

### 动效语言

- **曲线统一锚点**：常规变形 `--spring`（linear()）；entrance"弹入" `--spring-liquid = cubic-bezier(0.34,1.56,0.64,1)`（两面对齐到此，写进规范防漂移）；退出 `--spring-snappy`（无 overshoot）；俏皮（宠物/彩蛋）`--spring-bouncy`。
- **时长阶梯**（desktop `--gui-motion-*` 保留，取值成规范）：130ms 菜单浮层 → 160ms 淡入淡出 → 180ms chip/小件 → 240ms 高度形变/滚动 → 280ms 模糊 → 480ms 大高度形变上限；高度形变一律 delta/6 capped；位移 6px（小）/10px（大）；模糊量 8px/24px。
- **一镜到底（核心交互原则）**：场景切换不许黑场/闪白/整屏淡入淡出——共享元素持稳定 identity（data-morph-id）从原位置连续变形（desktop `morphFrame` 先例收编：单 rAF 链 translate+scale 插值）；非共享元素就地收缩/滑出（高度形变到 0 + 8px 下滑），整屏 opacity 动画禁用（系统级 overlay 除外）；会话切换（welcome→chat、chat→chat）按此执行，聊天内发送视为同场景增量；场景 morph 总长 300-420ms。
- **降级**：`gui-motion-off`/`prefers-reduced-motion` → morph 与浮层 entrance/exit 都即时完成（玻璃材质保留，材质不是动效）；`prefers-reduced-transparency`、不支持 `backdrop-filter` 与 `[data-platform="win32"]` → 浮层 blur 归零，切换不透明可读底色并保留 border/sheen/rim/shadow。

### Token 映射表（落地契约）

| 统一语义 | client-core | desktop-app |
|---|---|---|
| 玻璃底/强底 | `--glass-bg(-strong)` | `--gui-glass-alpha` 派生 overlay（对齐 7%/11% 两档） |
| 玻璃缘 | `--glass-border` | 同名对齐，否则 gui.css 引 client-core 值 |
| entrance 曲线 | `--spring-liquid` | 同名（已天然一致） |
| 淡入淡出 | 160ms ease（不新建变量） | `--gui-motion-fade-in/out` 时长语义 |
| 高度形变 | delta/6 capped | `--gui-motion-height(-max)` 同一规则 |

**纪律**：新组件先查本表与层级表；两表没有才提案新增，新增必须双面上报（更新本章）。

### 批次计划（随里程碑推进）

A（顺手带）：M2-2.10 设置面板审计对齐玻璃层级；回到底部按钮（L2 规格，已落地）。B（guest/安卓壳）：ConnectScreen→会话 morph、移动端列表↔会话 morph、composer 浮层升 L2。C（desktop 壳）：面板浮层（ContextPanel/DetailsPanel）层级审计到 L2/L3；会话切换 morph 推广到 chat→chat。D（收口）：映射表 CI lint（check-radius-tokens 先例）、双平台截图对比报告。

**验收**：映射表与层级表即本章（已合入）；逐面板收敛 biome+tsgo 全绿、无"表外" token、motion-off 无中间帧；Windows blur 缺席下与 macOS 并排截图对比可读性；动效抽查（无黑场、entrance 全走 `--spring-liquid`、时长落阶梯）。

## 5t. 顶栏（titlebar）架构定稿：避让三件套与"无 tab"原则（2026-09-22，替代 §3.1 A2 的内联 tabs strip）

> 背景：A2 批次曾在顶栏内联加入会话 tabs strip（与会话标题 pill 并排），评审认定"四不像"——tab 与标题挤在顶栏同一层级、折叠侧栏时标题 pill 与浮动控制簇重叠。本章为顶栏的最终设计约束，后续顶栏改动以本章为准。

### 设计依据（来自参考实现的实测结论）

- **openchamber**（`packages/ui/src/components/layout/TitlebarLeftControls.tsx` + `Header.tsx` renderDesktop）：浮动控制簇（侧栏开关 + ProjectActions）是 drag header 的 fixed 子节点；簇用 ResizeObserver 实测自身宽度，发布为 CSS 变量 `--oc-titlebar-controls-width`；头部内容区左侧放两个 spacer——① 红绿灯 drag inset、② no-drag carve spacer（宽 = controls-width，220ms 宽度过渡）。侧栏顶部另有 `SidebarTopBar` 预留条（drag inset + no-drag carve + drag 剩余）。
- **openchamber `sessionTabsEnabled` 默认 false**：会话 tab 是实验功能；开启时由 SessionTabsStrip **承载标题**（活动 tab 内嵌标题列，是"替换"而非"与标题并排"）。
- **zcode（zai-org/ZCode）桌面端 GUI 存在于 `packages/desktop` + `packages/ui`**（本地 `zcode/` 克隆即含，初始开源提交即有；2026-09-22 实证）：顶栏模型 = `WorkspaceHeader`（TitleSection + ActionSection 两段，**无 tab 条**；`DesktopWindowFrame` 的 `tabBar` 插槽语义是"渲染在 header 内标题**后面**"，不与标题并排）；Win/Linux 用**内联自绘窗口控制按钮**（`DesktopWindowControls`，min/max/close 在 ActionSection 最右，`[app-region:no-drag]`，最大化态经 platform 事件同步换 restore 图标）而非原生 `titleBarOverlay`；mac 避让 = 状态感知 padding 类（pl-38/48/58/66，按全屏 × 更新就绪角标取值，更新角标占红绿灯区），过渡显式限定 `transition-[padding]`（注释说明：限定 transition-property 避免非合成动画拖慢大会话 resize）；Linux 外壳 16px 圆角 + `clip-path` 合成裁切防圆角丢失 + win/linux 不透明根底（mac 才有 vibrancy 透明底）。
- 结论：**tab 若未来要做，走 openchamber 模式（tab 承载标题）或内容容器内的 tab 条（zcode tabBar 插槽同属此类），必须先出设计稿评审；顶栏本身永远不放与标题并排的 tab。** 窗口控制：维持我们的原生 `titleBarOverlay` + 150px 右避让（零维护、白得系统 snap/贴边布局）；zcode 内联自绘按钮列为已评估替代方案——若未来要主题化窗口按钮或在标题栏塞更新角标再切换。

### 我们的窗口 frame 配置（`packages/desktop-app/electron/main.cjs`）

主窗 `titleBarStyle: "hidden"`；macOS `trafficLightPosition: {x:16, y:17}`；Windows/Linux 用原生 `titleBarOverlay {height: 48}`（右上原生最小化/最大化/关闭，命中区约 138–150px，内容右避让取 150px）。

### 避让三件套（落地契约）

1. **左浮动簇** `.gui-float-controls--overlay`：fixed，`left: 84px`（mac，红绿灯避让）/ `16px`（win/linux），`top: 11px`，z 50，header 子节点保证 no-drag 生效。簇内容 = 侧栏开关 + openin 胶囊（自动发现/停止 + 预览 + 项目动作），对应 openchamber toggle + ProjectActionsButton。
2. **折叠 spacer** `.gui-header-spacer`：仅 `data-collapsed="true"` 时渲染宽度——win/linux `calc(var(--gui-float-controls-width, 86px) + 8px)`；mac `calc(68px + var(--gui-float-controls-width, 86px) + 8px)`（84 − 16 基础 padding + 簇宽 + 8 间隙），220ms 宽度过渡。**禁止**再用内联 `paddingLeft` 凑数（已删除的 mac 172 / win 16 hack 即为反面教材——win 折叠态 16px 让标题 pill 被浮动簇压住）。

## 5u. Dialog motion & style spec (finalized 2026-09-26, source `docs/archive/0.5.0-installer-update-dialogs-design.md` §4, review decisions ①-⑧ approved as-is)

> Normative for every modal dialog / full-screen overlay in the desktop GUI. **Every value below is a codified existing value** — the §5s M1.10 ladder plus current component values; inventing new tokens, curves, or scrim recipes for dialogs is prohibited. Verified against the component inventory in `.workbuddy/tasks/2026-09-26-installer-update-dialogs.report.md` §3.3.

### Overlay selection: six surface types

| Type | Use and examples | Material | Keyboard and focus | Scrim |
|---|---|---|---|---|
| Tooltip | Shared `gui-tooltip`, `RailTooltip` | **L2 float**: strong glass fill, border, complete top/bottom rim, sheen and shadow | Never moves focus; the anchor owns `aria-describedby`; tooltip content is not an action surface | None |
| Toast | `ActionToast`, `UpdateToast`, client-core `Toasts` | **L2 float**, neutral fill with status carried by icon/accent | Non-modal; actions and close buttons are keyboard reachable; hover or focus pauses expiry, errors persist until dismissed | None |
| Alert / approval | `ApprovalCard`, blocking tool decisions | **L2 float**, semantic status colors over the shared glass | `alertdialog` semantics without a page-wide focus trap; approve/deny controls own their activation keys | None |
| Drawer / sheet | `AgentDrawer`, `SessionsSheet`, capability drawer | **L2 float** on the container only; content rows stay paper-like | Shared modal stack: only the top layer handles Tab and Escape; closing restores a connected opener | Standard |
| Modal / palette | `DialogFrame`, `TaskModal`, board/media overlays, `CommandPalette` | **L3 overlay** with the complete glass recipe | Shared modals trap focus only at the stack top; palette focuses its input, supports arrow navigation and closes on Escape | Standard; heavy glass only for full-screen tour/system surfaces |
| Confirmation | Promise confirm, client-core `ConfirmDialog` | **L3 overlay**, compact size; `ss-card--confirm` distinguishes it from an L2 sheet | Ordinary Enter confirms; destructive Enter never confirms and starts on Cancel; Escape cancels only at the stack top | Standard |

`gui-motion-off` and `prefers-reduced-motion` remove both entrance and exit animation. `prefers-reduced-transparency`, lack of `backdrop-filter`, and Windows without blur retain border, rim, sheen and shadow over an opaque readable surface; the persistent transcript and composer never acquire overlay blur.

### Enter/exit motion ladder

| Surface | Curve | Duration | Notes |
|---|---|---|---|
| Dialog/overlay **backdrop enter** | ease (pure opacity) | **160ms** (`--gui-motion-fade-in` tier) | DialogFrame / onboarding / TaskModal / palette backdrops all 160ms |
| Dialog **card enter** | `--spring-liquid` | **240ms** (height/offset tier) | DialogFrame and TaskModal (`gui-focus-zoom 240ms`); palette keeps 130ms `gui-menu-in` — menu-floater semantics, codified exception; UpdateToast keeps its 260ms spring (non-modal floater, not a dialog card) |

Judgment rule: heavy glass when the user must keep perceiving the covered content (tour, freeze); standard scrim for pure attention blocking. **A third recipe is prohibited.**

### Keyboard contract

1. **Only the top shared modal owns the keyboard**: Escape is claimed on `document` in the **capture phase**; lower nested modals stay open but do not handle Tab or Escape.
2. **Focus in/out**: opening moves focus to the first focusable element (prompt dialogs focus the input, destructive confirms focus Cancel); closing the top layer restores a still-connected opener, while closing a lower layer never steals focus.
3. **Ordinary confirm: Enter = confirm, Escape = cancel**; prompt inputs: Enter submits. **Destructive confirmations never confirm on Enter** — Cancel has initial focus and an explicit confirm-button activation is required; Escape still cancels at the stack top.
4. **Forced/system-level overlays swallow Escape**: GlobalPause's Escape = resume (semantically a close); a future forced-update layer ignores Escape and must swallow held Enter/Space.
5. **DialogFrame stays mounted and is driven by `open`**; prompt/confirm close defers its promise resolution until the 180ms exit finishes — restated verbatim from the AGENTS.md GUI rules as rule 5 of this spec.

### Material & degradation

- Dialog, TaskModal, palette and confirmation cards are **L3 overlay** (§5s tier table): `--glass-bg-strong` + border + complete top/bottom rim + `--glass-sheen` + `--glass-shadow`. Glass belongs to the container; card content stays paper-like.
- `gui-motion-off` / `prefers-reduced-motion` disable both entrance and exit with no intermediate frames. `prefers-reduced-transparency`, unsupported `backdrop-filter`, and Windows without blur use an opaque readable fill while retaining border, rim, sheen and shadow; scrims become opaque.

## 5v. Right-panel tab strip: tab-primary completion (M1.12, approved 2026-09-29; source `docs/archive/0.5.0-promo-gap-analysis.md` v3 + interactive prototype `docs/review/tab-primary-prototype.html` v2)

> Background: the tab-primary model (`lib/panel-tabs.ts`, openchamber ContextPanel parity — ONE tab strip hosts every open view regardless of surface; the rail is a launcher) has been in place since 2026-09-15, but the interaction layer never arrived: rail clicks open a target-less placeholder tab (`surface::`), so each surface hosts exactly one rail-opened tab and the strip degenerates into a 1:1 mirror of the rail. M1.12 completes the interaction layer; the model layer is untouched. **A center-pane multi-surface container was evaluated and rejected** (2026-09-29, 小袁总): the product keeps the codex-style layout — the main conversation owns the center pane exclusively; every auxiliary surface (terminal/code/board/previews) is carried by right-panel tabs.

### Layout contract (unchanged)

Panel content on the left, 44px `RightRail` flush against the client surface's right edge (`ChatView.tsx` ~2507, sibling of the panel). No structural change; this chapter only adds interaction and removes one visual state.

### Rail semantics — pure launcher

- **No persistent active highlight.** The rail never stays lit to mirror the active tab (hover highlight only). The current active-state styling on the rail item is removed; "which tab is active" is communicated exclusively by the tab strip. Rationale (小袁总, prototype review): a lit rail item reads as an instance tab, which it is not.
- Click = open-or-focus: focus the surface's most-recent tab if one exists; otherwise open its placeholder tab. Clicking the rail item of the already-active surface while the panel is open collapses the panel (existing RightRail parity — Chrome side-panel semantics) and is unchanged.
- **Middle-click or ⌘/Ctrl+click = new instance** (never focus): opens a new tab of that surface with a freshly chosen target (files → directory picker, notes → new note, browser → address entry, others → surface default). The modifier variant must not toggle/collapse the panel.
- Keyboard `Mod+1..N` keeps its existing jump semantics (focus-or-open); no new-instance shortcut is added in this batch.

### Tab strip contract

- Identity stays `surface::target` (`panelTabId`, `lib/panel-tabs.ts:64`): `target` is the instance address (file path / note id), or the managed tab id for Browser. `surface::` (empty target) remains the placeholder for surfaces that support one — a rail click with no open tab opens the placeholder, and the first real open replaces it. Browser tabs always resolve a managed tab id instead of opening a placeholder.
- **"+" button at the strip head** opens the new-instance menu, grouped by surface: each entry carries the surface favicon + "new instance" affordance with its target picker (files → directory, notes → new note, browser → a new blank managed tab). Position: first child of the strip, before all tabs, always visible, never scrolled out (the strip scrolls tabs under it).
- The default per-surface budget stays `PANEL_TABS_MAX_PER_SURFACE = 12` (openchamber parity): evicting spends the oldest non-active tab of that surface. "+" on a surface at budget focuses the oldest tab with a toast instead of silently evicting. Browser projections are unlimited because closing a projected tab also closes its managed guest; a presentation-only budget must not silently destroy browser sessions.
- Strip overflow scrolls horizontally with the existing left/right feathering (`--gui-fade-x`, gui-chat.css horizontal section); the strip never wraps.

### Tab interactions

- **Context menu** (right-click / long-press): browser tabs expose a state-aware action list — new tab to the right, reload, duplicate, rename, copy URL, open externally, mute/unmute, close, close others, and close tabs to the right. Page actions disable on blank tabs; external open additionally requires HTTP(S); close-right disables when the source is last in its column. Duplication creates a new managed tab at the source URL instead of copying the panel identity, and a user rename wins over later page titles for the runtime. Other surfaces keep duplicate, close, close others, and close all. Menu motion and materials follow §5u (L2 float recipe, `--spring-liquid`).
- **Per-session panel state (2026-11-05)**: the right-panel tab layout is keyed by chat session, and managed-browser tabs carry an owner session. Switching sessions restores that session's split, tab order, and browser tabs; tabs and webviews owned by other sessions stay mounted but invisible, so no session ever sees another's page. Agent reveal only applies when the activity target belongs to the current session.
- **Tab drag shield (2026-11-05)**: a panel-tab drag mounts the same fixed gesture shield used by pane-width resize, above the page host. Pointer moves that cross the browser guest keep reaching dnd-kit, so same-column reorder and the right-half split drop zone work for browser tabs too.
- **One header row for both layouts (2026-11-06)**: the single column and each split column render their strip through the same header row (`PanelHead`), which owns the row's height, padding, rule, and bottom gap; the chips box is its only shrinking part, while the add control and window chrome keep their width. The strip no longer re-declares that geometry, so turning split on or off no longer changes the tab row's height. The new column slides in from the divider, the right-half split target fades in while a tab drags, and the dragged chip reads as lifted; `gui-motion-off` and `prefers-reduced-motion` disable all three.
- **Drop resolution (2026-11-06)**: `lib/panel-tab-dnd.ts` resolves one verdict per pointer position instead of letting `closestCenter` flip between a chip and the column-sized zone. Containment wins, smallest box first, so a chip beats the column that contains it; a release inside the dragged tab's own column but off any chip reorders to that column's nearest other chip; the right-half split target never falls back to a chip because it means "new column"; and a release just outside the strip lands on the nearest chip within 48px. Cross-column verdicts stay zone-authoritative.
- **Split divider (2026-11-06)**: the two columns are separated by a 7px hit band with a 1px hairline down its centre (VS Code sash / dsh divider semantics). A drag maps the pointer to column 0's share of the track and keeps at least 160px on each side; when the panel is too narrow for two such columns the floor degrades to an even split, on top of a 15% structural floor. Double-click recentres, and a focused divider steps 2% per arrow key (10% with Shift). The share persists with that session's panel layout, and layouts written before the divider existed restore to an even split. The drag mounts the same full-screen gesture shield as pane-width resize, so crossing the browser guest never stalls it.
- Drag-to-reorder uses the existing dnd-kit strip implementation; drop reorders only, never reparents surfaces.
- Close button (×) per tab: hover-revealed, follows the existing strip close affordance; closing the active tab activates its right neighbor (existing behavior). Closing a Browser projection also closes its managed guest, and host-originated closure removes the projection.

### Managed-browser projection and controls

- The managed-browser host remains the runtime and restart-persistence authority. Each managed tab has exactly one right-panel tab, keyed by its managed id in both `target` and `dedupeKey`; the browser pane has no internal tab strip. Add/open, activate, close, duplicate, split-column placement, and Agent reveal reconcile through that id in both directions without remounting the stable webview host. Persisted `browser` and legacy `settings.browser` panel entries are filtered during restoration; host restoration recreates valid projections.
- Every built-in panel tab shows its registry icon. Browser tabs use the page favicon with the browser icon as fallback, and these visuals are decorative. A tab whose managed id is busy or has a dispatched Agent operation shows the Agent badge even in the background, with accessible running-state text.
- The browser menu derives availability from the active managed tab. With no tab or on `about:blank`, find, print, zoom, device-toolbar visibility, page focus, screenshot, copy URL, and hard reload are disabled; opening in the system browser additionally requires HTTP(S). Downloads, history, data clearing, and browser settings remain available globally. Print, screenshot, download-folder, and data-clearing failures produce visible feedback.
- **Managed and external extensions**: the managed toolbar's Extensions popup lists only extensions actually loaded into `persist:musepi-managed-browser`, with a real empty state. Installing an unpacked extension requires an explicit directory choice and a second permission confirmation; removing unloads it without deleting source files. Records persist only id/name/version/path/permissions and reload on restart, while startup failures stay visible. Settings → External browser integrations separately owns Relay status/actions and shared-Chromium extension inventory; those external entries never appear in the managed popup. Full-URL display uses the shared browser-preference store. At ≤480px, annotation, developer tools, and new-tab move into More actions so the address field keeps a usable width.
- **External profile data**: Settings → Browser is divided into General, External browser integrations, and Data through the shared `Segmented`. Import copies cookies and localStorage from the default Chrome profile into the shared automation Chromium; it does not include passwords, the managed Electron partition, profile selection, or synchronization.
- **Structured Agent browser results**: `status`, `read`, and `screenshot` have dedicated cards backed by the same structured results the Agent receives. State distinguishes controlled and visible tabs and shows navigation facts; text shows scope, block counts, truncation, continuation, and capture time; screenshots show dimensions, byte size, path, and capture time beside the image. Raw JSON stays behind a disclosure, and the existing run timeline remains the interaction view.
- **Turn sources**: one deduplicated Sources card per turn groups pages read from pages passed through. Successful structured reads and legacy `observe` steps count as reads; `open`/`goto` counts visits. Repeated URLs preserve first-seen order and open counts, while screenshots, clicks, and status calls never invent a visited page.
- **Snapshot actions**: element and visual snapshots carry ids, capture time, bounded pages, and a 60-second tab-scoped lifetime. Ref actions and coordinate actions show their own element/visual cards plus success or failure receipts; stale refs never produce a blind click. The prompt teaches fresh snapshots after navigation or re-render.
- **Original crops, paths and device configuration**: visual crops read the original capture and show source snapshot, region and capture time without creating a new clickable snapshot. Continuous drag paths return the ordinary action receipt. Device catalog/configuration cards distinguish CSS viewport and mobile/touch identity from display scale; the Agent re-observes after device changes.
- **Retained history and downloads**: history and download cards read the same profile records returned to the Agent, newest first and independent of currently open tabs. History shows title, URL and visit time; downloads show filename, status, byte progress and optional save path. A save path is evidence, not a file-existence claim.
- **Navigation and observable waiting**: navigation cards show the action and actual current URL/title after navigate, search, history movement, reload, stop, or load-state waits. Condition waits show match/timeout and lastObserved so an unsuccessful wait is inspectable rather than a generic failure.
- **Dialogs and tab control**: pending and handled JavaScript dialogs have compact cards showing type, message, prompt text, outcome, and whether the Agent, user, or auto-policy answered. `activate` selects a control target without revealing it, `switch` reveals the real target, and `release` detaches Agent control while explicitly showing that the page remains open.
- Device presets, dimensions, display scale, and page background use the shared disabled semantics on blank pages: native/ARIA disabled state, no pointer or keyboard activation, no hover preview, and visible focus treatment when enabled. Collapse/reveal stays available, and the menu can show or hide the toolbar on nonblank pages.
- Generic tooltips snapshot the current `title` on each hover/focus interaction and restore it only when no newer external title has appeared. The maximize control's icon, tooltip, and accessible name are store-driven and update in the same click that commits the geometry; the imperative controller never writes labels separately.

### Motion

All additions ride the §5s ladder: tab open = shared-element grow from the invoking affordance (rail icon / "+" / menu item) with `--spring-liquid`; focus-or-open flash = 700ms accent-muted fade (prototype `flash` keyframes precedent); new-instance menu = §5u enter/exit. No new tokens, curves, or scrims.

### Acceptance

- Rail shows zero persistent highlight in any state; hover-only. Click/middle-click/⌘-click semantics per above.

### Implementation anchors

- `ChatView.tsx:796-808` — `setActiveView` is the single choke point that drops `target` today; new-instance flows thread a target through it (or call `panelTabs.open` directly with the descriptor, keeping `setActiveView` for focus-only paths).

### Android emulator tab

## 5w. Composer stats row: the「性能与用量」pill line (M1.10 batch C addendum, approved 2026-09-29; source `.workbuddy/tasks/2026-09-29-m1.10c-composer-stats-pills.md`, dsh-v0.2.0-rc.1 StatsPills parity)

> Scope: a persistent statistics line docked with the composer — two pills (time / usage) that surface session performance and token accounting next to the input, absorbing dsh 0.2.0's composer-dock stats without adding any statistics RPC.

### Layout & placement (decision ① — plan A)

- The `ContextRing` stays in the existing capsule row (`footerRight`), untouched. The stats row is a **new independent line directly below the composer footer row**, rendered outside the input card's frosted surface via a `belowRow` slot on `ComposerFrame` (mirroring `aboveRow`). Right-aligned to the same grid as `footerRight`; initial, empty and pill-less states keep the same 32px minimum row height and show `—`.
- Mounting follows the composer (not the chat transcript), so the figures stay visible while the transcript scrolls — dsh `conversation.composer.dock` parity.

### Glass & motion (§5s tiers, zero new tokens)

- Pills at rest: **L1 card** — base + edge from the footer-pill family recipe (`.gui-stats-pill` joins the pill family group in gui-composer.css; colour carries state, same discipline as 批次 C1).
- Popovers: **L2 float** through the single `.gui-menu-popup` recipe (`useFloatingMenu`, two-phase transform-only enter) — the same convergence contract as 批次 C2; no pill may declare its own background/backdrop-filter/box-shadow.
- Motion: pill entrance 180ms `var(--spring)` (the chip step of the §5s duration ladder). Popover positioning and motion use separate layers: the outer anchor keeps `translate(-50%, -100%)` while the inner layer runs matching enter/exit morphs.

### The two pills (decision ②)

- **Time pill** — `N 轮 M 步 · tok/s` (turns · steps · decode speed). Popover detail rows: 模型用时 (Σ request wall time) / 工具用时 (Σ tool-call→tool-result wall time) / TTFT (average) / 输出速度 — each row only when its data exists; when the window carries **no timing data at all**, the pill degrades to a plain reading with no popover (dsh contract).
- **Usage pill** — `总 tok · 缓存命中 %`. Popover: exact buckets input / cacheRead / cacheWrite / output (cacheWrite row drops when zero, dsh parity).

### Data contract (decision ③ — zero new RPC)

- **Token figures ride the daemon's durable projection**: `session.contextUsage` already returns `usage { input, output, cacheRead, cacheWrite, totalTokens, cost, cacheHitRate }` (TUI `cache_hit` parity, computed daemon-side). Composer already polls this RPC for the ContextRing — the stats row consumes the same state. Total = input + cacheRead + cacheWrite + output (billed input buckets + output). Paging/compaction never rewrites these numbers. A null response or RPC failure keeps the last valid readings for that session; switching sessions clears them before the new session responds.
- **Time/turn/step figures ride a visible-window fold** (`deriveWindowStats` in `packages/desktop-app/src/lib/derive-window-stats.ts`): daemon has no per-turn timing projection, so the fold answers "what is on screen" from `SessionEntry[]`, with field names deliberately mirroring dsh's `WindowStats` for a wholesale future swap.
- **Fold 口径 (the contract tested in `packages/desktop-app/test/derive-window-stats.test.ts`)**:
  - `turns` = non-synthetic user messages in window; `steps` = *settled* assistant messages (`stopReason` present — a streaming entry is not a step yet).
  - `llmMs` = Σ `AssistantMessage.duration` over settled steps; `ttftMs`/`ttftSteps` = Σ/count of `ttft` where recorded.
  - `decodeMs` = Σ `max(0, duration − ttft)` over steps carrying both; `decodeTokens` = Σ `usage.output` over those steps; displayed speed = `decodeTokens / (decodeMs / 1000)`.
  - `toolMs` = Σ `max(0, toolResult.timestamp − hostAssistant.timestamp)` for `toolCallId` pairs where **both** sides are in-window; unpaired calls/results contribute nothing.
- **Performance boundary**: the fold is O(n) over the visible tail (≤ ~200 entries). It may re-run per render (cheap field reads), but the row component is `memo()`-gated on the derived numbers + usage identity — a streaming delta changes no settled figure, so the comparator returns equal and the row does not re-render (contract test guards this).

### Compact / detailed (decision ④)

- Setting「性能与用量」(settings → 外观 → 聊天 section, `ChatSection`): Segmented **简洁 / 详细**, renderer-local `localStorage` key `musepi-gui-stats-mode` (`detailed` default) + a `musepi-stats-mode-changed` window event — the same pref pattern as `musepi-gui-chat-*` (GUI-only pref, zero daemon change).
- **Detailed** (default): both pills with popovers, per above.
- **Compact**: only two plain readings — decode speed and cache-hit — and only when each has data; no popovers, no counts. Both empty → the stable row shows `—`.

### Interaction contracts

- The two popovers share one open slot — opening one closes the other (the `useFloatingMenu` module mutex already enforces this app-wide).
- Both empty (no steps, no tokens) → the stable row shows `—`; a window of pure user messages shows the counts pill as a plain reading.
- Figures never move because of paging or compaction: token figures are projection-backed; window figures only change when the window's settled content changes.

## 5ab. Session list rendering stability: field-level meta merge + memoized pipelines (2026-10-21)

The sidebar's session list re-sorted and re-grouped every session on **every** render of `SessionSidebar` — search keystrokes, context menus, hover state, and the 5s status poll each triggered a full `sortSessionTree` (recursive node rebuild + per-sibling-group sort), collapse-prune, flatten, child-count map and fork-parent lookup **per date group**. Fixes, in three layers:

- **Poll merge (app.tsx)**: `pollRowEquals` compares the poll-lane fields (working/live/messageCount/paused/title/timestamp/updatedAt/cwd/modeId/agentCount) against the existing row; unchanged rows keep their object identity, and when nothing changed the `sessionMeta` **map keeps its identity** so React bails out of the whole subtree. - **List pipeline (SessionList.tsx)**: the sort/flatten/prune/child-count chain is memoized on `[nodes, sort]` / `[ordered, effectiveCollapsed]`, and the component is wrapped in `memo` — unrelated sidebar re-renders no longer re-sort any group. - **Grouping (GroupedSessionList.tsx)**: date bucketing memoized on `[nodes, locale]` (`useLocale()` subscribes for the non-reactive `t()`), component memoized like SessionList.

Non-goals (deliberate): no list virtualization (memoized rows + memoized pipelines keep per-render cost linear in visible rows; revisit only if hundreds-of-sessions profiles still hurt), no daemon-side pagination of `session.list` (the payload is small metadata; the cost was client-side re-derivation, not the RPC).

## 5ad.2. User-message attachment cards (2026-11-08)

## 5ag. Liquid-glass edge refraction recipe (2026-10-21)

Frosted glass blurs the backdrop; liquid glass also bends it at the rim. Applied to the composer card and the work-status card via the `.gui-liquid-glass` utility (gui-base.css) + `lib/liquid-glass.ts`.

- **Warp layer**: the utility relocates the pane's `backdrop-filter` onto a dedicated `::before` (z-index −1 under `isolation: isolate`); the element keeps only its translucent tint, so text and controls stay sharp while the backdrop sample bends.
- **Displacement filter**: `ensureLiquidGlass()` injects a 0×0 SVG with `feImage` → `feDisplacementMap` (R/B channels, scale 24, 20% overscan). The map is generated at runtime on a 256×256 canvas — neutral grey (#808080 = no displacement) across the interior, bending outward along the radial only inside the rim ramp (t² eased, 14 px at the corner). No bundled image asset; `slice` keeps the rim circular on non-square panes.
- **Rim highlight**: `::after` draws a 1.5 px gradient ring via `mask-composite: exclude`.
- **Safety gate**: the warp `filter: url(#…)` only applies under `html.gui-liquid-glass-ready`, armed by the module after the SVG is in the DOM — Chromium hides an element whose filter references a missing id, so a failed injection degrades to plain frosted glass instead of blanking the pane. Non-Chromium engines skip the effect and render the same frosted fallback.

## 7. Icon morph & color pipeline (finalized 2026-09-18)

### Icon morph rules (StateIcon, spec board「图标 morph 规范与缺口清零」)

- **Shape swap → `<StateIcon on pair>`** (`components/StateIcon.tsx`): any icon that flips with runtime state (play/pause, eye/eye-off, expand/collapse, saved/download, panel direction, fullscreen toggle) morphs between its two shapes instead of hard-swapping. Both shapes stay mounted in an inline grid; the outgoing icon collapses (scale .4 / −90° / fade 120ms) while the incoming one grows in from the opposite side, timed by `--spring`. Pure CSS on purpose: `.gui-motion-off` / `prefers-reduced-motion` degrade it globally with no per-component wiring. 29 sites migrated (commit d55086d6d); 3-way kind icons stay plain `<Icon>` with TODO(P1) for an n-ary variant.
- **Same-shape rotation → keep the transform**: a chevron rotating 180° is not an icon change — rotation is the shortest path. Do not morph what merely rotates.
- **Render-time selection → plain `<Icon>`**: icons picked by static facts (item type, configuration) never morph — there is no state flip to animate.
- **Why not MorphIcon for the sprite world**: `MorphIcon` (morphicons) renders a single stroke-interpolated path (lucide language); the app-wide sprite set is fill-based (Remix-style `<use>` shapes). A path morph turns filled icons into outlines — StateIcon is the sprite-world equivalent with the same reading. Use `MorphIcon` directly for stroke icons (onboarding step icon).
- API: `<StateIcon on={cond} pair={["nameWhenOn", "nameWhenOff"]} className="h-4 w-4" />` — `on` truthy shows `pair[0]`.

### Color pipeline verdicts (chroma.js PoC, spec board「色彩管线 · chroma.js 评估」)

- **chroma-js (guest-client)** owns: custom-accent derivation (`theme.ts deriveCustomAccent` — OKLCH hover ±0.07 away from resting, chroma-drop gamut clamp, contrast-picked foreground) and future contrast gating in ColorPicker (chroma.contrast, WCAG). Cold path: runs only when the accent preference changes (~19KB gzip, called once, not per frame).
- **CSS `color-mix(in oklab, …)` owns**: all per-frame runtime mixing — it is native and free; 60+ usages already. Never reach for a JS library there.
- **tokens.css hand-tuned oklch values own**: the static truth (presets, surfaces, chart colors). Do not generate them with a script — the values ARE the design decisions.
- **Regression lock**: `packages/client-core/test/derive-custom-accent.test.ts` — accent-fg ≥ 4.5:1 for 8 accents × both schemes; the previous sRGB derivation scored 2.2:1 on the brand gold itself.
