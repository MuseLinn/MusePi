## 1. 轨迹轴

### 1.1 记录族覆盖不全，且与 transcript 反相关（G1）

dsh 的轨迹台账明确覆盖 7 种记录 `system | user | context | compacted | message | tool | subtool`（`trajectory-record.ts:9-16`），并进一步覆盖：**嵌套 Subtool**（PTC 子派发，深度上限 256）、**compaction**（独立请求，按 `startSeq` 排在时间线，可出现在自己的「Between turns」段）、**失败记录带 error code**、**中断的 Tool 记录**（`error:{name:'Interrupted',code:'interrupted'}`）、**中断的 assistant step**（从已流式到达的 blocks 物化）、**in-history 系统提示变化**（逐位置对比最近 request state）、**tool-change 开发者消息**、**session-end 边界**把仍在跑的 compaction 标成 `COMPACTION_INTERRUPTED_ERROR`。（`trajectory-assistant-definition.ts:222-232`、`trajectory-tool-definition.ts:189-202`、`trajectory-snapshot-builder.ts:95-148`、`README.md:12,34,56-60`）

我方 `buildTrajectory` 只认四类：`message`(user/assistant/toolResult)、`custom_message`(仅 `isTurnStart` 的 advisor)、`model_change`、`thinking_level_change`（`trajectory-data.ts:170,182,298,335`）✅。wire 的 entry 联合体有六类（`wire/src/index.ts:200-206`），transcript 分类器有七种行（`row-kinds.ts:15-36`）并实际渲染：

| 记录 | transcript | 轨迹 | 来源 |
|---|---|---|---|
| `compaction` | 渲染（分割线 + 驱动「显示压缩前历史」折叠） | **无** | `wire/src/index.ts:174`；`Transcript.tsx:1053-1057,1256-1291` ✅ |
| `branch_summary` | 渲染（分割线） | **无** | `wire/src/index.ts:182`；`Transcript.tsx:1059-1064` ✅ |
| `retry_failure`（模型错误/重试） | 渲染 | **无** | `Transcript.tsx:826` ✅ |
| `async-result`（后台任务完成） | 渲染 | **无** | `Transcript.tsx:799` ✅ |
| `ttsr`（规则违规重写） | 渲染 | **无** | `Transcript.tsx:773` ✅ |
| `collab-prompt`（协作远端提示） | 渲染 | **无** | `Transcript.tsx:762` ✅ |
| hook 行 | 渲染（tail/hook 豁免） | **无** | `row-kinds.ts:39-45` ✅ |
| 失败/中断的 tool 记录 | 卡片内呈现 | 只有 160 字 `result` 预览 | `trajectory-data.ts:170-181` ✅ |
| `model_change` / `thinking_level_change` | **刻意不渲染**（return null，理由：composer chip 已表达） | **各占一条 system 事件** | `Transcript.tsx:1065-1074`；`trajectory-data.ts:335-346` ✅ |

**所以问题不是「不对称」而是「反相关」**：两个视图各自看到了对方看不见的东西，用户无法用一个校验另一个；而 `model_change` 恰恰是 transcript 判定为噪声的那一类。

后果：① 轨迹里看不到失败、重试、压缩点、后台任务；② `stats.turns/calls/durationSec`（`trajectory-data.ts:350-364`）建立在过滤后的时间线上，`durationSec` 是首末时间戳之差——既非活跃工作时长，又把被忽略记录的时段算进去（🔎 且被回退分支一并计入，与已按路径过滤的 `turns` 口径不一致）；③ Overview 泳道语义错位：`laneFor` 把 `system` 落回 lane 0（`TimelineOverview.tsx:35-40`），而 lane 0 图例是「用户消息」（`:163-165`）✅——model/thinking 变更的点画在「用户」泳道下。

**建议**：在 `trajectory-data.ts` 补 `compaction` / `branch_summary`（各成一条 system/boundary 事件并单独分组）、`retry_failure` / `async-result` / `ttsr` / `collab-prompt`（按 `row-kinds` 的 `TAIL_CUSTOM_TYPES` 口径），并把 `TrajectoryEvent.kind` 从 5 值扩到与 `TranscriptRowKind` 同构——否则两套词汇表必然继续分叉。同时决定 `model_change` 到底该不该出现在轨迹里（当前两个视图各执一词）。

### 1.2 装配层语义缺失（G3，结构性）

dsh 的会话装配是显式五件套（`conversation.md:11-28`）：Event Definition（按稳定 `(kind,id)` 关联 + 确定性 fold）、Context（start 未载入时更新保持 pending）、Location（引擎派生的 Session/Turn/**Step** 坐标）、View Definition（每会话一个增量 builder，持有该 target 的最终快照类型）、Group Definition（成员/分段/摘要/增量缓存，安装前整体校验）。热路径契约很硬（`:266-270`）：**append 只做 D 次 match + 常数时间 Context 查找；不得遍历完整事件窗口、全部 Context、`context.matches` 或已渲染 Node 集合**；发布节奏分 `immediate` / `animation-frame` / `none`。

我方对应物是三个同构的「全量 entries → 派生」纯函数层（`render-units.ts`、`round-collapse.ts`、`trajectory-data.ts`），靠**绝对下标**寻址，前插分页后用 `turn-derive.ts` 的 span 端点 id 签名缓存兜底（`render-units.ts:107-135`）。

这是设计水位差而非 bug，但代价具体：无 identity 层 → 流式与分页只能整表重算（G4/G5）；无 Location → Turn 坐标散落成三套互不相同的派生（`turnUnitSpan`、`depthOf`、`pathTurn`）；无 Group 校验 → 轨迹/画布/树各自维护分组语义。

**建议**：0.5.x 不照搬 engine 本体，只取两条约束——① 每个可见节点带稳定 `(kind,id)` 身份，派生产出「身份 → 节点」映射，前插/追加按身份增量合并；② 发布节奏集中到 store 层（`animation-frame` 合并 + `Object.is` 引用抑制）。这两条同时是 G4/G5 的解法。

### 1.3 轨迹视图与 Overview 无虚拟化（G2）

- 时间线模式靠「事件数 > 400 则默认全折叠」（`TrajectoryView.tsx:375-379`）换首帧，**展开任一轮即整轮 `EventRow` 全量挂载**；树模式是渐进挂载 300 + 哨兵每次 500（`:419-441`）——已挂载行永不回收，正是 `0.5.0-transcript-virtualization.md:75-79` 批评过、transcript 已改掉而轨迹未改的形态。🔎 而且代码注释声称的「行级 `content-visibility`」实际只落在轮组/树行级（`gui-workspace.css:2614,3004`），点「全部展开」（`:676`）仍会一次性挂满。
- `TimelineOverview` 对全部带 `tsMs` 的事件逐个渲染 `.traj-ov-dot`，同一批 turns 被 map 三遍（`:229-237` 边界、`:238-264` 段、`:267-295` 点）✅；`hover`/`hoverVisible` 是组件 state（`:90-92`），每次 pointer enter 都 set → **4 万条目会话挂 4 万个点，且鼠标每动一次全部重渲染** 🔎。它还同时出现在轨迹面板（`TrajectoryView.tsx:711`）与画布顶栏（`TurnMapCanvas.tsx:657`），两处各自承担这份成本。

dsh 的做法：初始只从尾部 50 个目标 Node 派生（`HISTORY_PAGE_NODES = 50`，`TrajectoryView.tsx:35,163-188`，只向后延长、不驱逐前缀），`useVirtualizer({ overscan: 12, anchorTo:'end', followOnAppend:'auto', scrollEndThreshold: 2 })`，行数 > 100 或存在更早记录时才启用（`TrajectoryTable.tsx:2170-2194`）；行高是**常量档**（内容 30 / 折叠摘要 20 / 终止分隔 9，`trajectory-virtual-rows.ts:6-8`），`requestOnly` 记录零高并进下一行；**语义行键（`trajectoryRecordId`）与 ARIA `aria-rowcount`/`aria-rowindex` 在前插后保持稳定**，纯内容流帧不改键不改高、不重复写尾部滚动。

**建议**：Overview 的每事件点改 canvas 或同像素列聚合；轨迹列表接入 transcript 同一套 `@tanstack/react-virtual`（`client-core` 已有 3.14.13），行键用稳定 recordId 而非序号，行高按档位取值（避免流式帧里逐行 `measureElement`）。

### 1.5 检视器只给截断预览（G8）

`InspectorCard`（`TrajectoryView.tsx:113-230`）的 Input/Output 全部来自构建期截断：tool 参数 160 字符、结果 160 字符（`trajectory-data.ts:58-65,180`）、消息正文 220 字符（`:54`）✅。

- 注释写「Input/Output/**Thinking** 明细」（`:113-114`），但 **thinking 从未渲染**——只被并进 assistant 标题的 `💭` 预览（`trajectory-data.ts:278`），`TrajectoryEvent` 也没有 thinking 字段 ✅。
- 无复制按钮、无语法高亮、无代码检视。dsh：`run_code` 行显示程序描述，检视器打开**编号高亮的源码**，Code 页签提供折行、`{}` 原始 JSON 切换与**精确复制（含尾随换行与记录时的 JSON 空白）**；页签集还按记录 kind 分化（system→prompt/tools、compacted→summary/rawOutput、message→summary/preview/raw/source、tool→payload/result/schema/timing）（`README.md:32`；`TrajectoryTable.tsx:972-1007,1927-1958`）。

### 1.6 轨迹面板每帧全量重算（G4）

`TrajectoryView.tsx:364-367` 的 memo 依赖 `[fullEntries, entries, roundDurations, activePathIds]`。`entries` 身份**每帧都变**：`MaterializedView.snapshot()` 返回 `entries: [...this.#entries]`（`sdk/src/materialized-view.ts:458`），`SessionStore.#buildSnapshot()` 每次 emit 都调它（`session-store.ts:472-473`）✅。

于是面板打开时每帧跑：`buildTrajectory`（`:95-136` 深度记忆化 + `:138-348` 事件构建）→ `buildTrajectoryTree`（`:406-452`）→ `buildMessageTree`（`:393`）与树模式展平（`:394-416`）。🔎 其中 `depthOf` 在**链断**时提前 return（`:124,127`）而跳过 `depthMemo.set`（`:131-134`）✅——尾窗里头部条目的父在窗外是常态，于是每个事件都重新走链到根，**单次重算退化为 O(n²)**；而 G12 又把这个 n 放大到全量会话。

dsh 的对应约束是 append 热路径不得遍历完整事件窗口（`conversation.md:268`），高频可见增量有专门的 `animation-frame` 发布档（`:270`）。

### 1.7 挂载即拉全量历史（G12）

`TrajectoryView.tsx:354-356` 挂载即调 `onEnsureFullHistory()`；`ChatView.ensureFullHistory`（`:1442-1476`）✅ 以 `maxMessages: 1000` **循环最多 60 轮**把整个会话拉进一个**独立本地数组** `fullEntries`（刻意不走 `store.prependEntries`），再与尾窗 live-merge（`:1504-1530`）。

后果：① 打开轨迹面板即让该会话在内存里存在**第二份完整副本**（按 M1.11 mem-bench：3,000 轮 ≈ 194MB 载荷 / 371MB 字符串），与 entry 级虚拟化换来的有界收益直接相抵；② G4 的全量重算从此跑在**全量**而非 200 条尾窗上；③ 该拉取按 `sessionId` **闩锁**（`:1444`）且 60k 上限封顶，任何一次 RPC 失败就 `setFullEntries(null)`（`:1471`）——**本会话生命周期内不再重试**，轨迹/地图此后长期只覆盖部分窗口，仅剩一行 loading 提示。

dsh 反向而行：初始窗口是挂载时尾部 50 个节点，`loadEarlierHistory` 先揭晓已驻留节点、再请求一页；台账在距顶 48px 内才请求更早页，并在前插后保留可见锚点（`TrajectoryView.tsx:163-188,504-508`；`TrajectoryTable.tsx:2528-2561`）。

**建议**：改成「统计/时间轴所需的最小元数据全量 + 明细按需」，或直接把轨迹的取数接到 `session.turns` 这类轻量索引上（daemon 已有 `session.turns`，每轮约 120B）；至少给失败加重试与显式降级提示。

## 2. 会话消息处理轴

### 2.1 两套分页键不一致：seq 水位 vs entry-id `findIndex`（G6）

我方其实**已有** seq 体系：journal 记录是 `{seq, ts, event}`，有点检（2000 事件 / 4MB 触发折叠）与 `catchupPlan` 区间校验（`daemon/journal.ts:21-59`）✅。但**历史回溯分页没挂到 seq 上**，而走 entry-id：

```
daemon:   session.history → entries.findIndex(e => e.id === beforeId)      // server.ts:2827（O(n)，取首个匹配）✅
client:   MaterializedView.prependEntries → 过滤已持有 id，全重叠时返回 null  // materialized-view.ts:417-439 ✅
          SessionStore.prependEntries → firstFresh===null 则不推进游标，
          但 hasMore = remaining > 0 && beforeId !== null 仍为 true          // session-store.ts:325-335 ✅
```

journal 里一旦出现**重复 entry id**（`materialized-view.ts:419-424` 注释明确承认实机发生过：重试、custom message 重发），`findIndex` 命中的是**更早**的副本，返回的整页可能全部已被持有 → `firstFresh === null` → 游标不动而 `hasMore` 仍真 → 客户端用同一 `beforeId` 反复请求同一页（只防了并发，没防「无进展重试」）。部分重叠时也只是靠「过滤后取首个新 id」侥幸前进。

**更常见的触发不是重复 id，而是 `findIndex` 落空**：`server.ts:2826-2830` ✅ 里 `idx === -1` 时 `start` 保持 `entries.length`，于是**静静地把最新一页当成「更早的一页」返回**。任何「客户端手里的 beforeId 已不在 daemon 当前快照里」的情形都会命中——journal 点检把旧记录折进 checkpoint 后裁剪（`journal.ts:298-320`）、resume 后换了视图、或跨版本快照——客户端把整页当重复丢弃、游标不动、`hasMore` 仍真，**每次上滚都重复同一请求且零进展**。这条比重复 id 路径更容易发生。

dsh 的契约正相反（`conversation.md:260`）：**Session journal 先校验逻辑 seq 区间互不重叠，Assembler 再按首个 seq 排序后重放**——键是单调 seq，重叠在入口即被拒绝。

**建议**：`session.history` 改 seq 游标（客户端持 `beforeSeq`，daemon 按 `seq < beforeSeq` 取页并返回 `nextBeforeSeq`/`remaining`），entry-id 仅留作展示与跳转；`findIndex` 落空应显式报错/回一个可判定的「游标失效」标记，而不是回最新页。顺带解掉 roadmap P1⑦ 的 `findIndex` O(n)。客户端在 `firstFresh === null` 时应换键或把该会话分页标记为不可用。

### 2.2 会话外壳每帧多次 O(n) 全量（G5）

`0.5.0-transcript-virtualization.md:131` 已点出这个瓶颈并列为「本稿要修」。**本次复核：仍未修**，且范围更大。`ChatView` 11 个依赖 `snap?.entries` 的 memo 全部在流式帧内重跑（`:1170` branchChildren、`:1210` leafWalk、`:1224` canvasRail、`:1267` visibleEntries、`:1509` overviewEntries、`:1563` buildTurnIndex…）✅。

🔎 另外三处此前未计入：
- `:1515` `overviewEntries` 每帧把全部条目 id `map().join(" ")` 成一个签名串做缓存比对——用 O(n) 字符串分配换缓存失效判定；
- `MessageTree.tsx:181-182` 的**常驻**树面板即使关闭也每帧跑 `buildTurnTree` + `filterTree`（O(n)），且全量渲染无虚拟化；
- `TurnMapCanvas` 的 `TmNodeCard` memo 被 ChatView 传入的内联箭头函数击穿（`ChatView.tsx:2004-2044`），每次渲染所有可见卡片重渲染。

即：**每条流式帧至少 5 次全量遍历**，这就是「长会话流式 CPU 第一来源」。

**建议**（与 G3 合并）：entries 身份改「版本号 + 追加段」而非整数组替换；`branchChildren` / `buildTurnIndex` / id→message 索引 / 树面板改 store 侧增量维护（append 只处理新条目）；关闭的常驻面板应订阅可见性。

### 2.3 分页游标可为 null 而静默不可回溯（G9）

`tailSnapshot`（`daemon/session-host.ts:605-616`）在 `entries.length > 200` 时无条件 `hasMore: true`，但 `beforeId` 取自 `firstKept?.id`，**非 string 时给 null**；客户端折算成 `remaining > 0 && beforeId !== null`（`session-store.ts:332`）→ false。结果：**历史明明存在，上翻却没有任何入口也没有提示**。而 `SessionEntry.id` 类型上是必填 `string`（`wire/src/index.ts:156`），所以这是「不可能路径」，正因如此长期潜伏。

### 2.4 跳转/导航以 timestamp 为键（G10）

`TurnIndexItem` 同时带 `entryId` 与 `timestamp`（`turn-index.ts:39-51`），但 rail 用 timestamp 建反查表（`TurnRail.tsx:206-211`，同刻后者覆盖前者）并以 `[data-turn-start-ts="…"]` 选择器定位（`:364-382`，取首个匹配）✅；跳转路径同样按 timestamp 轮询与 `findIndex`（`ChatView.tsx:1576-1595`、`Transcript.tsx:2037`）✅。两个 turn 起始时间戳一旦相同（advisor 注入与用户提问同毫秒、秒级精度历史会话、或乐观回显条目），**定位落到更早的轮次**；若目标始终未落进载入窗，请求还会被静默丢弃。🔎 另外该轮询本身是「最多 200 页 × 每页 O(n) 扫描」。

**建议**：键改 `entryId`（daemon 已下发，`session-host.ts:626`），找不到目标时给出可见失败反馈。

### 2.5 对照：实时推送路径已经是对的（§2.1 的修法成本因此很低）

值得记一笔：**同一条会话的「实时推送」路径已经完全实现了 dsh 那套 seq 语义**（`session-store.ts:544-640`）✅——

- 水位门 `#admitSeq`：`seq <= watermark` 视作回放并丢弃（防重复应用）、`seq > watermark + 1` 视作空洞并**拒绝越过空洞应用**（注释明确「the transcript must not show state built on missing frames」）、连续后严格按 `+1` 排空重排缓冲；
- 请求补推去重（`#catchupInFlight`），失败**不紧循环重试**；
- 空洞计时器兜底升级为整快照 resync，且 resync 后本实例只答 skip。

也就是说：**「seq 水位 + 非重叠校验 + 拒绝越过空洞」这套做法我们不仅已有，而且已经写在同一个文件里**。问题只在**历史回溯分页（§2.1）没有复用它**——同一份会话在「往后接」时用 seq、在「往回翻」时用 entry-id `findIndex`，两套寻址在同一 Map/数组上交叉。

这让 G6/A3 的修法从「引入新机制」降级为「把已有机制接上另一条路径」，是本稿里性价比最高的一项。

### 2.6 全局事件与 journal 水位共用一个通道（高，本稿已核对双方）

同一份 `kind:"event"` 承载了两类完全不同的东西，而客户端的水位门只认 `kind` + `seq`：

- **daemon 侧**：全局广播原语 `EventService.broadcast()` 发 `{kind:"event", seq: ++this.#seq, payload}`——**自有一个计数器、不带 sessionId**（`services/event-service.ts:112-117`）✅，`emitEvent` 原样转发（`session-host.ts:2961-2963`）；走这条路的包括 `models.changed`、扩展 HMR 通知，以及 **STT/TTS 模型下载进度**（`server.ts:3898,4034`、`610-633`、`5613-6603`）。
- **client 侧**：`app.tsx:1213` 的跨会话守卫只拦**带** sessionId 的信封（注释明说「no sessionId 的全局/UI 命令信封放行」），随后 `:1264` 无差别 `store.apply(event)` ✅；而 `session-store.ts:544-548` 的门是 `kind === "event" && Number.isInteger(seq) && seq > 0`，**没有载荷类型校验** ✅ → 全局事件被当成 journal 记录进入 `#admitSeq`。

后果（`#admitSeq` 的两条分支各自成立）：

1. **静默丢条目**：若全局事件的 seq 恰好等于 `watermark + 1`，它被放行、`#watermark` 前进（`:572`）并顺带推进视图 cursor（`materialized-view.ts:192`）；随后**真正的** journal 记录（seq 相同）到达时被判为「回放」丢弃（`:558-562`）——那一条真实消息就永久消失了。
2. **假空洞 → 整会话重开**：若 seq 大于 `watermark + 1`，它被塞进 `#reorder` 并武装 10s 空洞计时器（`:568-570,612-619`），最终升级为 `onResyncRequired` 整快照重开（`:631-640`）。
3. **下载期间成环**：STT 模型下载会连续推送进度，每一 tick 都重复触发 (1)/(2)——即一次语音模型下载足以把当前会话反复重开。

对照 dsh：它的实时增量与投影有明确的载荷类型与 `(kind,id)` 身份（`conversation.md:58-72`），producer 的类型面与消费端分离，不存在「同一个 kind 混装两种语义」。**建议**：全局事件换独立 kind（或加 `scope:"global"` 标记），客户端水位门只对本会话 journal 记录生效；`apply()` 对非 AgentEvent 载荷要么结构化忽略要么显式分流。

## 5. 明确不吸收 / 不照搬

- **dsh 的 Session 格式 v0→v4 迁移与 native 校验体系**（`docs/session-format-status.md`、`docs/persistence-changes/2026-09-16-session-format-v4.md`）：我们 wire 是独立血统（`@musepi/pi-wire`），照搬迁移代数与校验器成本远大于收益。**只吸收做法**：分页/补推一律走 seq 水位 + 非重叠区间校验（§2.1）。
