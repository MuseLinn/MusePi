## 2. A. 安装器品牌化

### 2.1 dsh 方案剖析与可行性

dsh 的品牌化安装器 = 三层投入（报告 §1.1-1.6）：

| 层 | 内容 | 可剥离性 |
|---|---|---|
| NSIS 自绘页（~1100 行 .nsh） | nsDialogs 布局 + GDI+ 圆角自绘控件 + 主题解析 + LangString i18n + 路径校验 | **可独立复用**，纯脚本无工具链要求 |
| window-frame.dll（~800 行 C++） | DWM 圆角壳 / 品牌化进度覆盖窗 / 7-Zip 管道进度 / 失败报告 / 卸载清理 | 强耦合 MSVC 工具链 + x86 stub 兼容 + 4 个原生回归测试 |
| 构建接线 | beforeBuild 编译+签名 DLL、PNG→BMP 资产、installer.nsh 宏接管各页 | 跟随 DLL 层 |

维护代价的核心在 C++ 层：Win32 消息循环、DPI、DWM 属性、MSVC 构建工具进 CI（dsh 还要求 VS C++ Build Tools，`prepare-windows-installer.ps1:11-14`）。我方 CI 目前是 bun+cargo（gui-release.yml:98-104 natives 已有 cargo），**增加一个 MSVC cl.exe 编译步骤可行但多一条平台专属失效面**；且 window-frame.cpp 里大量「NSIS 内部控件 ID / x86 NMCUSTOMDRAW 布局」这类对 electron-builder 版本敏感的假设（报告 §1.3），上游升级时是隐性破坏点。

### 2.2 分档建议

| 档 | 内容 | 工作量 | 收益 | 建议 |
|---|---|---|---|---|

## 3. B. 应用内更新 UX

### 3.1 更新状态机（对齐 dsh 语义，落在现有 updater.cjs 上）

现状状态（`electron/updater.cjs:53-62`）：`idle | checking | preparing | downloading | downloaded | error` + `mode`。目标状态机补三个显式相位与失败分类：

```
idle ──check──▶ checking ──有新版──▶ available ──用户点「下载更新」──▶ preparing
   ▲                │                     │ (可跳过此版本)                    │
   │             无新版                (toast 即是 available 的载体,             ▼
   │                ▼                      不新增 UI)                     downloading(percent)
   └───────────── idle ◀── not-available                                  │
                                                                          ▼
   error ◀──failedOperation: check/download/install ──任意相位失败      downloaded
     │ 分类 = {op} × {network} 九类语义（dsh update-presentation.ts:12-38 对齐）  │
     └── toast / 弹窗展示语义文案 + 重试 + 前往下载                    「立即重启」= install
                                                                        （安装确认从"下载完成"
                                                                          拆出，见 3.2-③）
```

改动点（全部在 `updater.cjs` / `main.cjs`，UI 契约向后兼容）：

1. **`available` 成为显式状态**：`update-available` 推送时 `state.status = "available"`（现状回 `idle`，updater.cjs:227-229），`version` 常驻 state——渲染层不再依赖两条事件流拼装。
2. **`verifying` 相位**：download-progress ≥100% 至 `update-downloaded` 之间置 `verifying`（dsh update-coordinator.ts:24-28 的语义），进度条末端不再有"假 100% 等待"。
3. **失败分类**：`state.error` 从裸 message 拆为 `{ kind, message, technicalDetails? }`，kind 走 dsh 式九类枚举（`check|download|install` × `network` + preparation 三类）；toast/弹窗按 kind 显示语义文案，原始 message 收进可折叠"技术详情"。
4. **轮询退避**：`main.cjs:3266-3283` 固定 1h setInterval 改为失败 ×2 退避（上限 6h）+ ±20% jitter（对齐 dsh update-schedule.ts:99-110；启动 12s 首查保留）。

### 3.2 界面形态分层：toast / 弹窗 / 强制整窗

**结论：与现有 UpdateToast 分层共存，不替换**（决策点 ②）。

| 层 | 承载状态 | 形态 | 现状 |
|---|---|---|---|
| **L-toast**（非模态，右下 320px） | available（有新版 + notes 预览）、preparing、downloading(percent)、downloaded | 保持现样（gui-widgets.css:4392-4428） | ✅ 已有 |
| **L-dialog**（模态，DialogFrame L3） | ① `downloaded` 超过 N 分钟未重启（用户切走/关了 toast）后的**待重启确认卡**；② `install` 失败 / `download` 连续失败 ≥2 次的**失败决策卡**（重试 / 前往下载 / 暂不） | 新组件 `UpdateDialog` = DialogFrame + `gui-dialog--confirm` 紧凑规格（380px），标题=状态语义，正文=版本 + notes 摘要，按钮=主操作(Enter) + 次操作(Escape) | 🆕 新增 |
| **L-mandatory**（系统级整窗） | 强制更新（策略服务端下发） | **本次不做**，仅预留：形态复用 GlobalPauseOverlay 的系统级先例（z 9999、动态玻璃 scrim、不可 Escape，gui-chat.css:1141-1171 已证明该形态成立）；触发器与服务端策略协议另立专项 | ⏸ 预留 |

分层理由：

- dsh 把可选更新的**每一步**都放进模态（检查→确认下载→确认安装），对我方过重——我方 toast 闭环已被 0.4.x 验证（UpdateToast.tsx:16-32 注释的完整状态流），日常"有新版"不打断是正确取舍。
- dsh 两条真正值得吸收的经验恰好落在模态层：**待重启不丢失**（我方现状：toast 被关后 `downloaded` 只能靠 1h 轮询的 `update-available` 复活，且 `autoInstallOnAppQuit=false` 意味着关掉 toast=更新丢失入口，UpdateToast.tsx:86-97 的复活只覆盖 preparing/downloaded 到达瞬间）与**失败需要一次明确决策**（现状错误只在 toast 里静置）。
- 强制更新通道依赖服务端策略接口（dsh 走 `/api/v0/check_client_update` + 40005 语义，报告 §2.2），我方无此基建——按"预留形态、不建通道"处理。

### 3.3 进度呈现与注意力

1. **进度条**：维持 toast 内进度条（已达标）；L-dialog 内不重复进度（弹窗只在无进度可看的静止态出现）。文案对齐 dsh 阶梯语义：`preparing → "正在准备更新…"`、`verifying → "正在校验安装包…"`。
2. **任务栏**：`setProgressBar` 已覆盖（updater.cjs:200-213），补 `flashFrame(true)` 一次（仅 `downloaded` 到达且窗口未聚焦时，点按任务栏即回；对齐 dsh update-attention.ts:38 但**不弹系统通知**——通知留给决策点 ④）。
3. **重启语义**：`立即重启` 触发的 `quitAndInstall` 期间（15s 宽限期，updater.cjs:460-507），toast/弹窗文案切换为不可点状态「正在安装更新，安装完成后将自动重启」——dsh mandatory-update.js:42-46 同语义，我方现状这一窗只显示旧按钮。

### 3.4 失败降级链

```
下载失败 → toast 内联错误(现状) → 再失败(累计≥2) → L-dialog 失败决策卡
  ↳ 卡内动作：重试(主) / 前往下载页(openExternal releases) / 暂不(Escape)
安装失败 → quitAndInstall reject(现状已回滚 downloaded, updater.cjs:472-484)
  → L-dialog 显示 kind=install 语义文案；macOS ad-hoc(otaCapable=false) 不进入此链
      (现状已走 downloadInstaller 手动路径, updater.cjs:139-169)
```

## 4. C. 弹窗动效与样式规范（并入 gui-design.md 的章节草案）

### 4.1 出入场动效阶梯

| 场景 | 曲线 | 时长档（M1.10 §3.2） | 现状对账 |

| 位移幅度 | — | 8px 下滑出、0px 滑入（scale 0.94→1 承担入场位移） | gui-dialog-out 已是 translateY(4px) → **改 8px 对齐阶梯**（or 保持 4px，见决策点 ⑥） |

### 4.2 scrim 规范（两档制）

| 档 | 配方 | 适用 | 现状 |
|---|---|---|---|
| **标准 scrim** | `color-mix(in oklab, var(--color-bg) 55%, transparent)` + `blur(6px)` | DialogFrame 系全部模态、TaskModal（blur 8→**6 归一**）、palette（黑 35% → **改 bg color-mix**） | DialogFrame 已是此配方（gui-composer.css:1458-1468） |
| **重玻璃 scrim** | bg 42-55% + `blur(24px) saturate(150%)` | 仅"接管全屏"的系统级/导览类：Onboarding、Announcement、Reward、GlobalPause、（预留）强制更新 | onboarding/GlobalPause 已是（gui-widgets.css:2440-2442、gui-chat.css:1164-1166） |

判据：**需要看清被覆盖内容并继续感知它的**用重玻璃（导览、冻结）；纯阻断注意力的用标准 scrim。禁止第三种配方（palette 的纯黑 35% 迁入标准档）。

### 4.4 z-index 层级表

| 带 | z | 内容 |
|---|---|---|
| 内容浮层 | ≤120 | TaskModal（120）等容器内模态 |
| 导览/系统覆盖 | 200 / 卡 210 | onboarding 系、GlobalPause 卡（GlobalPause 背板 9999 见下） |
| 非模态浮件 | 900 | UpdateToast |
| 模态弹窗 | **3000** | DialogFrame 系全部（含新 UpdateDialog） |

### 4.5 键盘契约汇总（现状已基本统一，此处成文）

1. **模态开启即拥有键盘**：Escape 一律在 `document` **capture 相位**认领（DialogFrame.tsx:52-53、prompt-dialog.tsx:134、AnnouncementOverlay.tsx:150 先例）。
2. **焦点进出**：打开移焦至首个可聚焦元素（prompt 类聚焦输入框，confirm 类聚焦确认键），关闭还原至 `prevActive`（DialogFrame.tsx:44-66、prompt-dialog.tsx:140-152）。
3. **confirm 弹窗 Enter=确认、Escape=取消**；prompt 输入框内 Enter=提交；**Destroy 级确认（删除会话/项目）Escape 仍=取消，Enter 需点击**（不启用"危险确认要打字"模式，维持现契约）。
4. **强制/系统级覆盖层吞 Escape**：GlobalPause 的 Escape=恢复（语义等价关闭），未来强制更新层 Escape 无效且需吞掉按住的 Enter/Space（dsh mandatory-update.js:108-110 先例）。
5. **DialogFrame 常驻挂载驱动 `open`**、prompt/confirm 关闭延迟 promise 至 180ms 出场完毕——AGENTS.md GUI 规则原样重申，作为本规范第 5 条。

### 4.6 材质与降级

- 弹窗卡片一律 **L3 overlay**（M1.10 §2 层级表）：`--glass-bg-strong` 底 + rim + `--glass-sheen` + `--glass-shadow` 双层——`.gui-dialog` 已达标（gui-composer.css:1525-1561）；**TaskModal、palette 卡是实底欠账**，随批次迁移到 L3（玻璃只给容器浮层，卡内内容保持纸面感）。
- 降级三件套照 §5s：`gui-motion-off` / `prefers-reduced-motion` → 出场免动画（onboarding 已有，gui-widgets.css:2474-2483，其余补齐同款）；`[data-platform="win32"]` blur 归零、sheen+rim 补强——玻璃 scrim 在 Windows 上的观感验收按 M1.10 §6.3 双平台截图流程走。
